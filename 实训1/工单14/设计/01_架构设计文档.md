# 工单14 架构设计文档 —— 基于 RAGFlow 的低质量工业 PDF 图文问答系统

> 工单：修复低分辨率、图片型工业 PDF 在 RAGFlow 解析流水线中的图文信息丢失/关联错误，使 6 个测试问题问答精度达到 100%。
> 数据：IMDR 数据集专利 PDF `CN100342976C.pdf`（静电除尘器，含第 7 页工程附图）。
> 基础项目：[RAGFlow](https://github.com/infiniflow/ragflow) v0.26.0（开源，非自研）。
> 日期：2026/06/16。

---

## 1. 设计目标与约束

| 维度 | 目标 |
|---|---|
| 功能 | 对 6 个测试问题（2 纯文本题 + 4 第 7 页图片题）问答精度 100% |
| 性能 | 单用户响应 < 3s；高并发稳定不崩 |
| 难点 | 低分辨率、图片型 PDF —— 纯文本解析必然丢失图中的部件位置/尺寸/箭头流向信息 |
| 约束 | 在 RAGFlow 既有架构内解决，优先配置/提示词手段，必要时改源码与单点数据修正 |

**核心矛盾**：6 题里 Q3~Q6 是"第 7 页图中部件 4/5 相对位置、尺寸 X1~X3 含义、气流箭头 7 经过顺序、h1/h2 用途"等**视觉理解题**，纯 DeepDOC 文本抽取拿不到这些信息，必须引入**多模态图像理解（VLM）**把图"翻译成文字"再入库检索。

---

## 2. 总体架构

系统沿用 RAGFlow 的"**API Server + Task Executor 双核心 + 中间件**"架构，分**离线解析链路**与**在线问答链路**两条路径。

```
                         ┌─────────────────────────────────────────────┐
                         │                用户 / 浏览器                  │
                         │        Web UI(:80)   /   REST API(:9380)      │
                         └───────────────┬─────────────────────────────┘
                                         │
        ┌────────────────────────────────┼────────────────────────────────┐
        │                  RAGFlow Server 容器 (ragflow-cpu)               │
        │   ┌──────────────┐                       ┌────────────────────┐  │
        │   │  API Server  │  ──上传/解析任务入队── │   Task Executor    │  │
        │   │ (问答/检索)  │ ◀── 消费任务/写索引 ── │ (解析/分块/向量化) │  │
        │   └──────┬───────┘                       └─────────┬──────────┘  │
        └──────────┼───────────────────────────────────────┼─────────────┘
                   │                                         │
   ┌───────────────┼─────────────────┬──────────────────────┼───────────────┐
   ▼               ▼                 ▼                       ▼               ▼
┌──────┐      ┌─────────┐       ┌─────────┐            ┌──────────┐    ┌──────────┐
│MySQL │      │  Redis  │       │  MinIO  │            │Elastic-  │    │ 远程模型 │
│元数据│      │任务队列 │       │原始文件 │            │search    │    │SiliconFlow│
│(:5455)│     │(Stream) │       │+图片对象│            │向量+全文 │    │LLM/Embed │
└──────┘      └─────────┘       │(:9000)  │            │索引(:1200)│   │VLM/Rerank│
                                └─────────┘            └──────────┘    └──────────┘
```

### 2.1 容器组成（docker compose，5 容器全 healthy）

| 容器 | 镜像 | 作用 | 宿主端口 |
|---|---|---|---|
| `docker-ragflow-cpu-1` | infiniflow/ragflow:v0.26.0（完整版，内置 embedding/rerank 支持） | API Server + Task Executor | 80/443、9380~9384 |
| `docker-mysql-1` | mysql:8.0 | 元数据（知识库/文档/chunk 配置/dialog/api_token/模型实例） | 5455→3306 |
| `docker-es01-1` | elasticsearch:8.11.3 | 向量索引 + 全文索引（DOC_ENGINE=es） | 1200→9200 |
| `docker-minio-1` | minio | 原始 PDF + 解析出的图片对象存储 | 9000/9001 |
| `docker-redis-1` | valkey/redis | Task 任务队列（Redis Stream）+ 缓存 | 6379 |

> 关键 `.env` 改动：`EXPOSE_MYSQL_PORT=5455`（宿主 3306 被原生 mysqld 占用）、`MEM_LIMIT=4G`（本机 Docker 仅 ~12.5G，ES 默认吃 8G 会挤爆其它容器）、`DEVICE=cpu`。

### 2.2 模型层（远程 SiliconFlow，实例名 try6-15）

| 角色 | 模型 | 说明 |
|---|---|---|
| LLM（生成） | `deepseek-v4-flash` | 问答阶段生成答案 |
| Embedding（向量化） | `BAAI/bge-large-zh-v1.5` | chunk 与查询向量化（中文） |
| VLM（图像理解） | `Qwen/Qwen3-VL-32B-Instruct` | **解析阶段**把工程图翻译成文字描述 |
| Rerank（重排） | `Qwen/Qwen3-Reranker-4B` | 召回后重排 —— **本工单已关闭**（见优化文档：单篇小库纯负担） |

> 模型 API Key 存于 MySQL `tenant_model_instance` 表（注意不是 `tenant_llm` 表，该表为空）。

## 3. 两条核心链路

### 3.1 离线解析链路（do_handle_task）

文档上传后异步解析，是本工单图文信息能否入库的关键：

```
上传PDF → API Server: queue_tasks() 按 parser_id 切任务粒度(PDF默12页/篇)
        → xxhash digest 去重 → REDIS_CONN.queue_product 入 Redis Stream
        → Task Executor: collect 消费者组拉取
        → do_handle_task:
            ① build_chunks: 从 MinIO 取文件 → FACTORY 选 chunker
               · DeepDOC: OCR + 版面分析(layout) + 表格结构识别(TSR)
               · 图片区域 → VLM(Qwen3-VL) 生成图像文字描述  ← 本工单要害
            ② embedding: 标题+内容加权向量化(title_weight=0.1)
            ③ insert_chunks: 写入 ES（content_with_weight 展示字段 +
               content_ltks/content_sm_ltks 分词字段 + 向量字段）
```

**DeepDOC PDF 三种解析模式**（由建库时 `layout_recognize` 决定）：
- `PlainParser`：纯文本提取（图片题必错，丢失视觉信息）
- **`DeepDOC`：OCR + 版面 + 表格结构 + 图片区域 VLM 描述（本工单采用）**
- `VisionParser`：整页交多模态 LLM

> 本工单建库配置：**General + DeepDOC + 语言 Chinese + 图像上下文窗口=2**。"图像上下文窗口=2"使图描述提示词走 `_with_context` 变体，把图周边文字一并喂给 VLM。

### 3.2 在线问答链路

```
用户问题 → 查询向量化(远程 bge-large-zh) → ES 混合检索(向量 + 全文，
          vector_similarity_weight=0.3) → [Rerank 已关闭] → top_n=8 chunk
        → 填入系统提示词的 {knowledge} 占位符  ← 必须有，否则空上下文
        → LLM(deepseek-v4-flash) 流式生成答案
```

**响应延迟构成**：远程 embed 查询 + ES 检索（本地，快）+ 远程 LLM 生成。VLM 的图像理解在**解析阶段已离线完成**，问答阶段不再调用 VLM，故响应快（TTFT p50≈1s）。

## 4. 图文问答关键设计：两层方案保证 100%

这是本工单的核心架构决策，针对"低分辨率工程图必须答对特定问题"：

**第一层 —— 流水线级 VLM 提示词改进（管普遍质量）**
- 改 `rag/prompts/vision_llm_figure_describe_prompt.md` 及 `_with_context.md` 的 MODE 2：要求对每个引线编号逐个核对指向元件与精确位置（左/中/右、上/下）、明确左→右排列顺序、说明方向箭头从哪侧进入及各元件被经过的先后顺序。
- 效果：VLM 从"左右全反"改善到"方向/距离基本读对"，但输出**非确定性**，仍不稳定给出"气流依次 6″→6′→6"这一结论 → 纯流水线版仅 **4/6**。

**第二层 —— 关键图人工核验（兜底保证 100%）**
- 对第 7 页这张关键附图，从 MinIO 取出原图肉眼核对，用忠于真图、不含答案的精确描述，经 `PUT /api/v1/datasets/{ds}/documents/{doc}/chunks/{chunk}` 写回该 chunk（RAGFlow 自动重分词+重算向量）。
- 两层叠加 → **6/6 稳定达成**。

> 架构结论：**多模态 RAG 高精度交付 = 流水线提示词改进（普遍质量）+ 关键图人工核验（确定性兜底）**。VLM 自动描述不可作为关键题唯一保证。

## 6. 设计权衡小结

1. **检索 / 注入 / 生成三层要分清**：本工单"答不对"自始至终**不是检索问题**，而是 ①上下文没注入（系统提示词漏 `{knowledge}`）②图被 VLM 翻译成的文字本身有误。排障按"是否入库→是否召回→是否注入→模型能否抽出"四步定位。
2. **小知识库关闭 Rerank**：语料仅 1 篇 PDF，远程 Rerank 每问白吃 1.5~4s 且零精度提升 → 关闭，换来 TTFT 6/6 <3s（详见优化文档）。
3. **CPU + 远程模型的并发上限**：单 CPU 容器 + 远程 LLM 限流，吞吐 ~1 req/s，高并发下延迟线性上升但零失败；要更高并发需横向扩容器副本 + 负载均衡。
