## 2. 按时间线的完成过程

### 阶段 0：建目录 + clone 源码（06/14）

- 建项目目录 `E:/rag后续工单/`，`git clone` RAGFlow 源码到 `ragflow/`。
- 通读 README 与 docker compose，确定走 **完整版镜像 v0.26.0**（含内置 embedding/rerank，省去单独拉模型）。

### 阶段 1：部署 RAGFlow（06/14—06/15）

- **代理坑**：git/docker 都依赖代理；Clash 实际端口是 **7897**（不是惯例的 7890），验证 `curl -m6 -x http://127.0.0.1:7897 .../generate_204` 返回 204 才算通。
- **端口冲突**：本机已有一套 Milvus 栈 + 原生 mysqld 占 3306。解法：`.env` 里 `EXPOSE_MYSQL_PORT=5455` 避让，必要时停 Milvus 栈。
- **内存约束**：Docker 仅 ~12.5G，ES 默认吃 8G 会挤爆其它容器 → `MEM_LIMIT=4G`。
- **拉镜像**：ragflow:v0.26.0 约 9GB，hub 代理不稳，靠 VPN 代理断点续传拉完。
- **最终**：5 容器全 healthy（ragflow-cpu / es01 / mysql / minio / redis），`DOC_ENGINE=es`，`DEVICE=cpu`。
- **模型**（SiliconFlow）：LLM=deepseek-v4-flash、Embedding=BAAI/bge-large-zh-v1.5、VLM=Qwen/Qwen3-VL-32B-Instruct、Rerank=Qwen/Qwen3-Reranker-4B。

### 阶段 一(并行)：源码分析（任务一文档）

读源码梳理出三条主线（详见 `docs/任务一_技术总结/RAGFlow技术实现方案总结.md`）：

1. **分块入队**：`queue_tasks`（`task_service.py:358`）按 `parser_id` 切 task 粒度——PDF 默认 12 页 / paper 22 页 / one+知识图谱整篇 / table 每 3000 行；用 xxhash digest 做复用判重，`REDIS_CONN.queue_product` 入 Redis Stream。
2. **消费流程**：`do_handle_task`（`task_executor.py:1359`）——消费者组拉取 → `build_chunks`（MinIO 取文件 + FACTORY 选 chunker）→ embedding（标题+内容加权，title_weight=0.1）→ `insert_chunks` 写 ES/Infinity。
3. **DeepDoc 解析器**：PDF 三模式由 `layout_recognize` 决定——PlainParser（纯文本）/ DeepDOC（OCR+版面+表格结构识别 TSR）/ VisionParser（多模态 LLM）；`RAGFlowPdfParser.__call__` 8 步流水线。

### 阶段 2：建库 + 6 问调优至 100%（06/15）

建库配置：General + DeepDOC + 语言 Chinese + 图像上下文窗口 2。
调优是**四步定位 + 两层修复**：

1. **修"全答未找到"**：系统提示词漏了 `{knowledge}` 占位符 → 检索正常但无处注入 → 模型收到空知识库。补上后 Q1/Q2 纯文本题立即答对。**这是最大的坑**。
2. **图描述提示词工程化**：低分辨率工程图，默认 VLM 把孔盘左右读反。改容器内 `vision_llm_figure_describe_prompt.md` 的 MODE 2，要求逐个引线编号核对位置/左右顺序/箭头经过顺序，`docker cp` + restart + 重解析。→ 改善但**非确定性，纯流水线版仅 4/6**。
3. **关键图人工核验兜底**：第 7 页关键附图从 MinIO 取原图肉眼核对，写忠于真图、不含答案的描述，经 `PUT .../chunks/{chunk}` 写回（自动重 embed），存 `fig7_fix.json`。→ 两层叠加 **6/6 稳定**。

### 阶段 3：性能验证（任务三，06/16）

- **关键优化**：单篇小库去掉 Rerank（dialog `rerank_id` 置空）——它每问做一趟远程重排白吃 1.5~4s、精度零提升。
- **结果**：流式 TTFT 从 4/6<3s 改善到 **6/6 全 <3s（0.8~1.3s，p50≈1s）**，整段 5/6<3s，精度保持 6/6。
- **并发**：1/4/8/12 路成功率 **100% 零失败**，延迟随并发近似线性，吞吐 ~1 req/s。
- 脚本：`perf_test.py` / `perf_stream.py` / `perf_concurrency.py`。

## 3. 关键技术决策与权衡

| 决策 | 选择 | 理由 / 权衡 |
|---|---|---|
| 镜像版本 | 完整版 v0.26.0 | 内置 embedding/rerank，省去单独部署模型；代价是镜像大（9GB） |
| 文档引擎 | ES（非 Infinity） | 生态成熟、诊断工具多；代价是吃内存，需限 `MEM_LIMIT` |
| 知识库范围 | **只入目标 1 篇 PDF** | 6 问全针对该篇；单篇库召回纯净、无相似专利抢召回，是关闭 Rerank 压到 <3s 的前提（详见优化文档二·补充） |
| 图文修复 | 流水线提示词 + 关键图人工核验**双层** | 纯提示词仅 4/6（VLM 非确定性）；人工核验兜底确定性达 6/6 |
| Rerank | 单篇库**关闭** | 小库重排无收益、白吃延迟；大库扩展时应重开 |

## 4. 我在这个工单里学到的（知识沉淀）

1. **RAG"答不对"要分层定位**：是否入库 → 是否召回 → 是否注入 → 模型能否抽出。`{knowledge}` 那个坑表象像"检索失败"，实为"注入失败"，分层排查才不会南辕北辙。
2. **多模态 RAG 的高精度交付是非确定性的**：通用提示词改进能提普遍质量，但**不保证关键图答对特定问题**。交付级方案 = 流水线改进（管面）+ 关键图人工/投票核验（管点）。
3. **小库与大库的检索取舍相反**：小库要的是纯净（关 Rerank、降噪），大库要的是排序质量（开 Rerank）。没有放之四海的配置，要按库规模重测。
4. **性能瓶颈常在"白吃的远程调用"**：本工单 <3s 的关键不是优化检索，而是砍掉一趟无收益的远程 Rerank。先量化每段耗时再优化，别凭感觉。
5. **诊断要用系统自己的接口**：裸查 ES（自定义分词器）会误判"没入库"；要用 RAGFlow `/api/v1/retrieval` 看真实 similarity/vector/term 分数。
6. **工程纪律**：临时 `api_token` 用完即删（已归零）；重解析会重置 chunk、覆盖人工修正，须重贴 `fig7_fix.json`——这类隐性状态要么自动化、要么写进文档。

## 5. 踩坑清单（精简版，完整见优化文档第三节）

1. 系统提示词必须含 `{knowledge}` —— 否则空上下文全答未找到（最大的坑）。
2. Windows Git-Bash 发中文 JSON 给 curl 会按 GBK 编码 → RAGFlow 按 UTF-8 解报 `0xb8`。解法：写 UTF-8 文件 `curl --data-binary @file.json`。
3. 裸查 ES 不可靠（自定义分词器）→ 用 `/api/v1/retrieval` 看真实检索。
4. Python 在 Windows 控制台打印 emoji 报 GBK 错 → 前置 `PYTHONIOENCODING=utf-8 PYTHONUTF8=1`。
5. 临时 `api_token` 诊断完务必删除。
6. 评测：单选题只发问题不带选项；提示词不能泄露页码。
