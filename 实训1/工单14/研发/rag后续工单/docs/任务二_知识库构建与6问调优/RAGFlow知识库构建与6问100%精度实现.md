## 1. 部署（环境与关键决策）

### 1.1 镜像与服务
- 镜像：`infiniflow/ragflow:v0.26.0`（完整版，12GB，含内置 BGE embedding / reranker；slim 版需全走外部 API）。
- 文档引擎：`DOC_ENGINE=elasticsearch`，`DEVICE=cpu`。
- 起服务：`cd ragflow/docker && docker compose up -d`，共 5 个容器：`ragflow-cpu / es01 / mysql / minio / redis`，全部 healthy。

### 1.2 踩到的两个部署坑及解决
1. **端口冲突（minio 9000/9001、mysql 3306）**
   - 机器上原有一套 Milvus 栈（自研项目"任务1"用）占着 9000/9001；另有原生 Windows MySQL 服务占 3306。
   - 解决：本工单不需要 Milvus，`docker stop` 掉那套（同时缓解内存压力，见下）；MySQL 宿主暴露端口改 `EXPOSE_MYSQL_PORT=5455`（容器内部仍 3306，RAGFlow 内网走 `mysql:3306`，功能无影响）。
2. **内存压力**：Docker 引擎总内存仅 11.68 GiB，ES 一个就吃 4 GiB。`MEM_LIMIT` 由 8G 降到 4G；并停掉 Milvus 栈避免 OOM。

### 1.3 模型配置（SiliconFlow，实例名 "try6-15"）
| 角色 | 模型 | 用途 |
|------|------|------|
| Chat（LLM） | `deepseek-v4-flash` | 问答推理、组织答案 |
| Embedding | `BAAI/bge-large-zh-v1.5`（内置） | chunk 向量化（中文专利，用中文模型） |
| VLM（图生文） | `Qwen/Qwen3-VL-32B-Instruct` | 把附图转成文字描述（Q3–Q6 命脉） |
| Rerank | `Qwen/Qwen3-Reranker-4B` | 检索结果重排 |

> 注：DeepSeek 官方 key 之前欠费（402），改用 SiliconFlow。

## 2. 知识库构建（配置项及理由）

知识库 `工单14`，配置如下，每项理由说明：

| 配置项 | 取值 | 理由 |
|--------|------|------|
| 嵌入模型 | bge-large-zh-v1.5 | 中文专利文本，中文 embedding 召回更好 |
| 语言 | **Chinese** | 默认 English 会用英文分词器切中文 → 全文检索很差；专利正文全中文 |
| 解析方法（chunk method） | **General** | 专利版式自由，General 最稳；Paper 是给固定版式学术论文的 |
| PDF 解析器 | **DeepDOC** | 做版面分析 + OCR + **抽取图片区域**；Plain/Naive 只取纯文本，会丢掉第7页的图 → 图片题必错 |
| 图像与表格上下文窗口 | **2** | 让每张图带上前后 2 个文本块作为上下文，帮 VLM 消歧、利于检索 |
| 知识图谱 / RAPTOR / 社区报告 | **全部关闭（未生成）** | 仅回答 6 个针对性问题，普通向量+全文混合检索足够；知识图谱会对全文做海量 LLM 调用，浪费时间和额度 |

**解析流程**（DeepDOC + VLM）：
```
PDF → DeepDOC 版面识别 → 切成文本块/表格/图片区域
    → 文本块：bge 向量化入库
    → 图片区域：调 VLM(Qwen3-VL) 生成文字描述 → 入库
    → 全部写入 ES 索引
```
解析后该专利共 **11 个 chunk**，覆盖 6 题全部依据（首页著录、权利要求、说明书、两张附图描述）。

## 3. 调优全过程（从"全错"到 6/6）

> 关键认识：本工单的精度问题，**根因不在检索，而在两处"内容如何进入模型"**。

### 3.1 诊断方法（绕开反复手点）
- 直接读 **ES 索引**确认 chunk 内容是否入库（注意：要用 RAGFlow 自己的检索 API，**不能用裸 ES `match` 查 `content_with_weight`**——RAGFlow 用自定义分词器存 `content_ltks`，裸查会误判"没入库"）。
- 临时往 mysql `api_token` 表插一条 token，调 `POST /api/v1/retrieval`（带 `rerank_id` 可复现助手重排），返回每个 chunk 的 similarity/vector/term 分数 —— 一次看清"召回了什么"。
- 读 mysql `dialog` 表看助手的真实检索参数（similarity_threshold / vector_similarity_weight / top_n / rerank_id）。
- 读容器日志看送给 LLM 的实际 prompt 与模型的 `<think>` 内心独白。

### 3.2 问题一：发明人等文本题全答"未找到" —— 根因是 `{knowledge}` 占位符缺失

**现象**：Q1 发明人答"未在文档中找到相关信息"，看起来像检索失败。

**诊断**：
- ES 中 chunk2（首页著录）含 `[72］发明人 P·吉特勒`，内容**确实入库**。
- 调检索 API：首页著录块是 **#1 召回**（相似度 0.515，带 reranker 后仍第一），**检索完全正常**。
- 看日志中模型 `<think>`：竟说"知识库似乎为空"。

**根因**：RAGFlow 靠系统提示词中的 **`{knowledge}` 占位符**注入检索到的 chunk。自定义系统提示词若漏了它，检索结果**无处注入 → 模型收到空上下文 → 一律答"未找到"**。

**修复**：系统提示词模板末尾必须保留：
```
知识库内容：
{knowledge}
```
修复后文本题立即正常（Q1 答出 P·吉特勒）。

### 3.3 问题二：Q5 气流顺序题 —— VLM 把附图左右读反

**现象**：Q5 标准答案"先经过 6″ 再经过 6′"，模型却答"先经过入口 1 再经过圆锥 10"（宏观流向，回避了孔盘顺序）。

**诊断（取出真图核对）**：
- 从 MinIO 取出 DeepDOC 裁剪的第7页附图原图（bucket=知识库 id，object key=chunk 的 img_id 去掉前缀），用肉眼核对**真图**：
  - 气流箭头 7 从**左**侧射入；
  - 三个孔盘从左到右实际是 **6″、6′、6**（顶部尺寸对应 X3、X2、X1）；
  - 气流自左 → 最先碰最左的 **6″**，再 6′，最后 6 —— **标准答案 C 正确**。
- 而默认 VLM 描述里写的是"从左至右 6、6′、6″"，**左右标号读反了**，模型据此自然答不对。

**修复（两层叠加）**：

**第一层 — 流水线级（改源码提示词，对所有文档生效）**
- 定位图描述提示词：`rag/prompts/vision_llm_figure_describe_prompt.md` 及带上下文变体 `..._with_context.md`（因设了"图像上下文窗口=2"，实际走 `_with_context`）。
- 在 MODE 2（一般图内容）中新增针对工程图/专利图的硬要求：
  - 对每个引线编号（reference numeral）逐个核对其指向的元件及精确位置（左/中/右、上/下），**不得按编号大小臆断顺序**；
  - 明确说出沿坐标轴的左→右排列顺序；
  - 若图中画有方向箭头（气流/流程），说明它从哪侧进入、沿该方向各元件被经过的先后顺序。
- 改后 `docker cp` 进容器覆盖（提示词在模块加载时缓存，需 `docker restart docker-ragflow-cpu-1` 重载），再重新解析文档。

**结果（重要的工程发现）**：重解析后，VLM **读对了更多**（正确写出"箭头 7 从左侧射入"、"孔盘 6/6′/6″ 距台阶 5 为 x1/x2/x3"），但**仍未稳定输出"气流依次经过 6″→6′→6"这句结论**，deepseek 没自行推出，Q5 又退回宏观流向，Q3 也从"左侧"退化为"下方"。**流水线级修复后仅 4/6。**

**第二层 — 关键图人工核验（保证 100%）**
- VLM 的图描述本质**非确定性**：通用提示词改进能提升普遍质量，但不保证对某张关键图给出"答题所需的精确表述"。
- 因此对第7页这张关键附图，用人工核验过的、忠于真图的描述（不含答案、只如实描述图中所见的空间关系与流向顺序）通过 `PUT /api/v1/datasets/{ds}/documents/{doc}/chunks/{chunk}` 写回该 chunk（RAGFlow 自动重新分词+重算向量）。
- 叠加两层后 **6/6 恢复并稳定**。

## 4. 工程权衡与结论

1. **检索 vs 注入 vs 生成要分清**：本工单"答不对"全程**不是检索问题**。检索/重排一直正常；问题出在 ①上下文没注入（`{knowledge}`）②图被翻译成的文字本身有误（VLM 读反）。排查要按"内容是否入库 → 是否召回 → 是否注入 → 模型是否抽得出"四步定位。

2. **多模态 RAG 高精度交付的现实权衡**：
   - **流水线级提示词改进**值得做 —— 它对任意文档的图描述质量是普遍提升（本例从"左右全反"改善到"方向/距离基本读对"）。
   - 但 VLM 输出非确定性，**对"关键附图必须 100% 答对特定问题"的场景，自动描述不可靠，必须人工核验该图的描述**。
   - 最佳实践=**两层叠加**：改进提示词管普遍质量 + 关键图人工核验兜底。

3. **低分辨率图片型 PDF 的可行性**：本例证明 DeepDOC + VLM(Qwen3-VL) 能从低清专利图中正确读出部件标号、相对位置、尺寸标注与箭头流向，前提是提示词到位 + 关键图核验。

## 6. 性能验证（任务三验收：响应 <3s + 高并发稳定）

> 测试脚本：`perf_test.py`（整段命中+延迟）、`perf_stream.py`（流式首字 TTFT）、`perf_concurrency.py`（并发稳定性）。环境：单 CPU 容器 `docker-ragflow-cpu-1`，LLM/Embedding/Rerank 均走远程 SiliconFlow。

### 6.1 关键优化：对单篇小知识库去掉 Rerank

实测发现每次问答都在对**仅 1 篇 PDF 的小知识库**做一趟远程 `Qwen3-Reranker-4B` 重排，白白增加 1.5~4s 延迟，而**精度无任何提升**（去掉前后 6 问内容均全对）。因此将 dialog 的 `rerank_id` 置空。

| 指标 | 带 Rerank | 去掉 Rerank |
|---|---|---|
| 流式首字 TTFT（<3s 数） | 4/6（max 5.19s） | **6/6（max 1.29s）** |
| 整段完成（<3s 数） | 1/6 | **5/6** |
| 6 问精度 | 6/6 | **6/6（保持）** |

> 工程结论：**Reranker 适合大库召回噪声多的场景；对单篇/小库是纯延迟负担，应关闭。** 回滚值：`rerank_id='Qwen/Qwen3-Reranker-4B@try6-15@SILICONFLOW'`。

### 6.2 单用户响应延迟（去 Rerank 后）

- **响应速度（TTFT，用户感知"多快开始回应"）：6/6 全部 <3s，区间 0.80~1.29s，p50≈1.0s。** ✅ 达标
- **整段答案完成**：5/6 <3s（1.46~3.69s），唯一超线的 Q6 因答案最长（3.69s），属 LLM 输出长度而非检索瓶颈。
- 说明：VLM 的图像理解在**解析阶段已离线完成**，问答阶段只剩"远程 embed 查询 + ES 检索 + 远程 LLM 生成"，故响应快。
