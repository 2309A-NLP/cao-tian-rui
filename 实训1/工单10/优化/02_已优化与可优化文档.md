# 金融问答系统 Docker 部署 — 已优化项 与 可优化项

> 工单10。记录本次部署中**已经做到的优化**，以及**后续仍可改进的方向**，便于评估与迭代。

---

## 一、已优化项（本次已完成并验证）

### 1. 镜像体积优化：CPU 版 torch 分层构建
- **做法**：Dockerfile 先单独装 CPU 版 torch（`--index-url .../whl/cpu`），再装 requirements；torch 单独成层便于缓存。
- **效果**：避免 pip 默认拉入 CUDA 包（约 4G），镜像从约 6G 降到 **3.3G**；构建改代码时只重跑 COPY 层（秒级），不重下依赖。

### 2. 依赖版本锁定，消除不兼容风险
- **问题**：`requirements.txt` 用 `>=` 导致 pip 拉到 pymilvus 3.0 / transformers 5.x（破坏性大版本），与代码（2.4.x/4.x API）不兼容。
- **优化**：收紧为 `pymilvus>=2.3.0,<2.5`、`transformers>=4.36.0,<5`，对齐宿主验证可用版本，确保连接与模型加载稳定。

### 3. torch 版本适配 BGE-M3 加载
- **问题**：transformers 4.57 加载 BGE-M3 的 `pytorch_model.bin` 走 `torch.load`，要求 torch≥2.6，而 CPU 索引默认解析到 2.5.1，启动报错。
- **优化**：追加一层精确安装 `torch==2.6.0`（保留 requirements 缓存层），并加 `--timeout/--retries` 适配慢网。

### 4. 复用宿主已有镜像，规避慢网
- **优化**：compose 改用宿主机已有且验证可用的镜像（milvus v3.0-beta、etcd v3.5.25、minio 2024、mariadb 10.11），`up` 时几乎零下载，秒级起栈。

### 5. 中文乱码修复（流式问答）
- **问题**：流式 `/api/ask/stream` 答案乱码（"根据"→"æ ¹æ®"）。根因：`requests` 对 `text/event-stream` 默认按 ISO-8859-1 解码 UTF-8。
- **优化**：返回流式响应前显式 `resp.encoding="utf-8"`（`llm_provider.py`）。这是**通用修复**，非容器特有，对宿主直跑也有益。

### 6. LLM 容灾切换
- **问题**：DeepSeek 官方 key 欠费报 402。
- **优化**：通过 `.env` 的 `APP_LLM_*` 一键切到备用 SiliconFlow（OpenAI 兼容），无需改代码/重建镜像。

### 7. 配置与密钥治理
- host 全部走服务名（`config.docker.json`）+ 环境变量覆盖；密钥经 `.env` 注入，不写死镜像；`.env`/`config.docker.json` 纳入 `.gitignore`。

### 8. 启动健康编排
- 依赖服务配 healthcheck，rag-app `depends_on: service_healthy`，消除"应用先于数据库启动"的连接竞态；rag-app 自身健康检查 + `start_period:90s` 容纳模型加载。

### 9. 数据持久化与隔离
- 5 个命名卷持久化有状态数据；模型/数据宿主挂载共享；只暴露 8010，依赖服务内网隔离，与宿主开发容器互不影响。

### 10. 检索性能（沿用既有成果）
- BM25 metadata 字典化（O(N)→O(1)）、`max_rewrites` 7→3、LLM 上下文裁剪到 8 块 → 端到端 **2.75s（<3s）**，fulltext 模式答案准确（招股书 94%、银行年报 100%）。

## 二、可优化项（后续建议，按优先级）

### P1 — 体验/正确性

| 项 | 现状 | 建议 |
|----|------|------|
| **前端"知识库为空"误解** | 面板只统计 Milvus 向量数（fulltext 下为 0） | 让 `/api/knowledge` 在 fulltext 模式同时上报 BM25 块数（18443），面板不再显示空。纯显示层改动，几分钟。 |
| **统一索引 / 启用 hybrid** | Milvus 空，仅 fulltext | 用 `rebuild_unified_index.py` 把 all_chunks.json 灌入 Milvus（向量与 BM25 共用全局 chunk_id），RRF 才能真正融合，hybrid 有望修复"军用收入≈国防销售额"这类语义匹配题。**需 GPU 环境跑嵌入**（CPU 太慢）。 |
| **流式计时显示** | 前端流式"总耗时:0ms" | 流式结束时回填 total 耗时。 |

### P2 — 部署工程化

| 项 | 现状 | 建议 |
|----|------|------|
| **镜像再瘦身** | 3.3G（含 torch 2.5.1 残留层 + 2.6.0） | 直接把首装 torch 改为 2.6.0 单层（去掉 2.5.1），或用多阶段构建，减约 200M。 |
| **GPU 版可选 profile** | 仅 CPU | 提供 `docker-compose.gpu.yml` override（`deploy.resources.devices` + CUDA 版 torch），有 GPU 服务器时一键切换，加速嵌入/建索引。 |
| **一键脚本** | 手动多命令 | 提供 `deploy.sh`/`deploy.ps1` 封装 build/up/health 校验/灌库。 |
| **配置模板化** | 密钥在 .env | 接入 docker secrets 或外部密钥管理，生产更安全。 |
| **健康检查增强** | 仅 /api/health | 增加就绪探针（BM25/模型加载完成才算 ready），与存活探针分离。 |

### P3 — 可观测与运维

| 项 | 建议 |

### P4 — 检索质量（属算法线，非部署线）
- 评估体系已具备（`eval_quick.py` + `eval_compare.py`，16 题招股书 + 10 题年报）。
- 后续可在 GPU 环境完成统一索引重建 → 量化对比 hybrid vs fulltext，确认更优后再让容器切 hybrid。

## 三、当前取舍说明

| 取舍 | 原因 | 影响 |
|------|------|------|
| 用 CPU 而非 GPU | Docker Desktop GPU 直通复杂、易踩坑 | 建索引慢（但问答无感）；适合稳定交付验收 |
| Milvus 留空、走 fulltext | 保证一次起栈即可问答、最稳 | 暂不支持语义向量检索；面板显示"空" |
| 复用 v3.0-beta 等镜像 | 慢网下零下载、宿主已验证可用 | 版本非最新稳定版，但功能验证通过 |

> 以上取舍均为「优先保证工单验收通过、可手动复现」的工程选择，后续可按 P1→P4 逐步增强。
