# RAG 系统 Docker 部署 — 实施过程问题记录

记录将 RAG 金融问答系统容器化过程中遇到的问题、原因与解决方案。

---

## 1. 依赖服务梳理：哪些要进容器？

**问题**：系统跑起来依赖什么外部服务，不清楚就无法设计编排。

**排查**：
- `requirements.txt` + 代码：FastAPI(8010)、Milvus(向量)、MySQL(历史)、Redis(会话)、本地 BGE-M3 模型、远程 LLM API。
- 本机现状 `docker ps`：已有 `milvus-standalone`(+etcd+minio)、`mariadb`(3307)；Redis 在宿主机 6379（非容器）。

**结论**：编排 rag-app + milvus(+etcd+minio) + mysql + redis 共 5+ 服务；LLM 走外网不进容器；模型走卷挂载。

---

## 2. CPU 版 vs GPU 版镜像选择

**问题**：torch 默认装会拉进 CUDA 包（~4G），镜像巨大；且 Docker Desktop 用 GPU 需额外配 WSL2 + nvidia-container-toolkit，易踩坑。

**分析**：系统真正吃 GPU 的只有"批量建索引"（一次性）；日常问答每次只嵌一句话，CPU 几百毫秒，瓶颈本是远程 LLM 生成(~2.9s)。

**解决**：选 CPU 版。Dockerfile 先单独装 CPU 版 torch（`--index-url .../whl/cpu`），再装 requirements，pip 见 torch 已满足会跳过，不会改装 GPU 版。镜像从 ~6G 降到 ~2G。

**代码零改动验证**：`embedding_provider.py:91` 用 `torch.cuda.is_available()` 判断，CPU 版 torch 返回 False → 自动回落 CPU。

---

## 3. config 缺 Redis / 嵌入设备的环境变量映射

**问题**：`config.py:_apply_env_overrides` 的 `env_map` 只有 `APP_DB_*`/`APP_MILVUS_*`，**没有 Redis、embedding_device、model_path**。容器里改不了 Redis 主机名 → 连不上。

**解决**：给 `env_map` 补 `APP_REDIS_HOST/PORT/PASSWORD`、`APP_EMBEDDING_DEVICE`、`APP_EMBEDDING_MODEL_PATH`、`APP_RETRIEVAL_MODE`，并把 `redis_port` 加进 `_INT_FIELDS`。这是本次唯一的代码改动（最小侵入）。

---

## 4. 与宿主机现有容器端口冲突

**问题**：本机已有 milvus-standalone 占 19530、mariadb 占 3307，新编排若也发布这些端口会冲突。

**解决**：compose 里 milvus/mysql/redis **都不发布端口到宿主机**，只在 `rag-net` 内部用服务名互通；仅 rag-app 暴露 8010。新栈与现有开发容器完全隔离、互不影响。用独立 project name `rag-deploy` + 独立命名卷进一步隔离。

---

## 5. 数据初始化：空库能不能跑？

**问题**：新编排的 MySQL/Milvus 是空的，担心起不来。

**排查**：
- MySQL：`database.py:_init_tables()` 首启自动建库建表 → 无需手工 SQL。
- Milvus：`api.py:129-144` 只要连上（哪怕空集合），就从挂载的 `output/chunks/all_chunks.json` 构建 BM25。生产默认 `retrieval_mode=fulltext`（纯 BM25）→ **Milvus 空也能跑通问答**。

**解决**：默认 fulltext 模式即可验收通过；vector/hybrid 模式提供容器内 `rebuild_unified_index.py` 灌数据的可选步骤。

---

## 6. 前端 API 地址会不会写死 localhost？

**问题**：前端若硬编码 `localhost:8010`，容器化后跨域失败。

**排查**：`api/static/index.html:339` `const API = ''`（同域相对路径），FastAPI 同域托管前端 → **零改动**。

---

## 7. 模型中文路径挂载

**问题**：模型在 `F:\...\2-6--专高6\bge-m3`，含中文，Windows→容器挂载可能失败。

**解决**：把路径抽成 `.env` 的 `MODEL_PATH` 变量，compose 用 `${MODEL_PATH}` 引用。Docker Desktop 一般支持中文路径；若挂载失败，文档提示把模型拷到纯英文路径再改 `.env`。

---

## 8. 依赖版本漂移：pip 装了 pymilvus 3.0 / transformers 5.x（不兼容）

**问题**：`requirements.txt` 用的是 `>=` 下限约束，构建时 pip 拉了**最新大版本**：`pymilvus 3.0.0`、`transformers 5.12.0`。但本机可用环境(gpu_env)实测是 `pymilvus 2.4.8`、`transformers 4.57.6`，代码也是按 2.4.x / 4.x API 写的。

**风险**：
- pymilvus 3.0 客户端连 Milvus 2.4 服务端协议不兼容 → 连接/检索失败。
- transformers 5.x 改了 `AutoModel` 加载行为，BGE-M3（`trust_remote_code`）大概率加载报错。

**排查依据**：`docker inspect milvus-standalone` 现有可用服务是 `v3.0-beta`，宿主 gpu_env 用 pymilvus 2.4.8 连它正常；`embedding_provider.py:83` 用 `transformers.AutoModel.from_pretrained` 直接加载 BGE-M3。

**解决**：`requirements.txt` 收紧为 `pymilvus>=2.3.0,<2.5`、`transformers>=4.36.0,<5`，钉到与可用环境一致的大版本。compose 的 Milvus server 用 `v2.4.15`（与 pymilvus 2.4.x 天然匹配）。重建时耗时的 torch 层有缓存，只重跑 requirements 层。

## 9. 复用本机已有镜像，避免慢网重下 1GB+

**问题**：compose 初版指定 milvus:v2.4.15 / mysql:8.0 / etcd:v3.5.5 / minio:2023，`up` 时要从零拉取 1GB+，慢网（~200-700kB/s）下极慢且易超时。

**解决**：本机已有经验证可用的 `milvusdb/milvus:v3.0-beta`、`rancher/mirrored-coreos-etcd:v3.5.25`、`minio:2024-05-28`、`mariadb:10.11`。改 compose 复用它们（pymilvus 2.4.x ↔ milvus v3.0-beta 在宿主 gpu_env 已实证可用；db 服务名保持 `mysql`，用 mariadb 镜像，pymysql/`mysqladmin` 兼容）。etcd/minio 的 `depends_on` 改 `service_started`（milvus 内部会重试连接），避免其健康检查误判卡住 milvus。

## 10. BGE-M3 加载报错：transformers 4.57 要求 torch>=2.6

**问题**：rag-app 启动时 `AutoModel.from_pretrained` 报 `ValueError: ... require users to upgrade torch to at least v2.6 ... unless loading safetensors`。原因：pip 在 CPU 索引把 torch 解析成 2.5.1，而 BGE-M3 只有 `pytorch_model.bin`（无 safetensors），transformers 4.57 走 `torch.load` 强制要求 torch≥2.6（宿主 gpu_env 用 torch 2.11 故无此问题）。

**解决**：Dockerfile 在 requirements 之后追加一层 `pip install "torch==2.6.0" --index-url .../cpu`（保留耗时的 requirements 缓存层；精确钉 2.6.0 而非 `>=2.6` 避免解析到更大版本超时；加 `--timeout 180 --retries 10` 适配慢网）。重启后 BGE-M3 正常加载，BM25 索引 18443 文档构建完成。

## 11. LLM 生成 402 Payment Required

**问题**：端到端问答时检索正常（返回 15 条来源），但 LLM 报 `402 Client Error: Payment Required`——DeepSeek 官方 key 余额不足。

**解决**：非部署缺陷，是 LLM 账户欠费。切到配置中的备用 provider（SiliconFlow，OpenAI 兼容）：经 `.env` 注入 `APP_LLM_PROVIDER=openai`、`APP_LLM_BASE_URL=https://api.siliconflow.cn/v1`、`APP_LLM_MODEL=deepseek-ai/DeepSeek-V3`、`APP_LLM_API_KEY=<key2>`（config.py 的 `APP_LLM_*` 覆盖生效）。重启后端到端问答 HTTP 200、2.75s（<3s）、答案正确（兴图新科注册资本 5,520万元）。
