# 金融问答系统 Docker 部署 — 架构设计文档

> 工单10：将 RAG 金融问答系统以 Docker 容器形式部署到服务器并运行成功。
> 本文档说明系统的整体架构、容器编排设计、关键技术决策与数据流。

---

## 1. 系统概述

本系统是一套**金融文档 RAG（检索增强生成）问答系统**：用户提问 → 系统从金融文档知识库（招股说明书、银行/券商/保险年报）中检索相关内容 → 交给大模型（LLM）生成带出处的答案。

部署目标：把原本散落在宿主机（Python 进程 + 多个本地服务）的系统，整体收敛为一套 **Docker Compose 编排**，做到「一条命令启动、数据持久化、容器间隔离通信、可移植复现」。

## 2. 总体架构

### 2.1 架构图

```
                      宿主机 (Win11 + Docker Desktop)
  ┌──────────────────────────────────────────────────────────────┐
  │  浏览器  ──HTTP :8010──►  ┌────────────────────────────────┐   │
  │                           │   docker network: rag-net       │   │
  │                           │  ┌──────────┐                   │   │
  │                           │  │ rag-app  │  FastAPI+前端      │   │
  │                           │  │  :8010   │  BGE-M3(CPU)/BM25  │   │
  │                           │  └────┬─────┘                   │   │
  │                           │   服务名互通(内部)               │   │
  │                           │   ┌───┼───────┬─────────┐        │   │
  │                           │   ▼   ▼       ▼         ▼        │   │
  │                           │ milvus mysql redis  (milvus 依赖)│   │
  │                           │  :19530 :3306 :6379  etcd/minio  │   │
  │                           │   └─┬──────────────────┘         │   │
  │                           └─────┼──────────────────────────┘   │
  │  宿主目录挂载 ───────────────────┘                              │
  │   F:/.../bge-m3 (模型,只读)  ./output  ./logs  ./knowledge_base │
  └──────────────────────────────────────────────────────────────┘
                                  │
                          远程 LLM API (SiliconFlow / DeepSeek)
```

### 2.2 服务清单

| 服务 | 镜像 | 角色 | 对外端口 | 持久化卷 |
|------|------|------|---------|---------|
| **rag-app** | 自建 `rag-app:cpu` | FastAPI 后端 + 前端页面 + BGE-M3 嵌入 + BM25 检索 | **8010** | 挂载宿主 output/logs/kb |
| **milvus** | milvusdb/milvus:v3.0-beta | 向量数据库（语义检索） | 内部 | milvus-data |
| **etcd** | rancher/mirrored-coreos-etcd:v3.5.25 | Milvus 元数据存储 | 内部 | etcd-data |
| **minio** | minio/minio:RELEASE.2024-05-28 | Milvus 对象存储 | 内部 | minio-data |
| **mysql** | mariadb:10.11 | 对话历史/用户/反馈 | 内部 | mysql-data |
| **redis** | redis:7-alpine | 会话缓存/多轮上下文 | 内部 | redis-data |

> LLM 是**远程 API**（SiliconFlow DeepSeek-V3 / DeepSeek 官方），不进容器。

## 3. 容器编排设计

### 3.1 网络设计

- 所有服务接入同一自定义 bridge 网络 **`rag-net`**。
- 容器之间用 **服务名做 hostname** 通信：rag-app 通过 `milvus:19530`、`mysql:3306`、`redis:6379` 访问依赖，无需 IP。
- **只有 rag-app 发布 8010 到宿主机**；milvus/mysql/redis/etcd/minio 一律不发布端口 → 既安全（数据库不外露），又避免与宿主机上已有的同类容器（milvus-standalone:19530、mariadb:3307）端口冲突。
- 扩展：若需与其他服务（如 RTMP 服务器）互通，将对方加入 `rag-net`（或 `docker network connect rag-net <容器>`）即可用服务名互访。

### 3.2 启动顺序与健康检查

```
etcd / minio  ──(service_started)──►  milvus ──┐
                                               ├──(service_healthy)──► rag-app
mysql ────────────────────────────────────────┤
redis ────────────────────────────────────────┘
```

- milvus / mysql / redis 配 `healthcheck`，rag-app 用 `depends_on: condition: service_healthy` 等它们就绪后才启动，避免连接竞态。
- etcd / minio 用 `service_started`（milvus 内部会自行重试连接），避免它们的健康检查误判阻塞整条链。
- rag-app 自身 `healthcheck` 探测 `GET /api/health`，`start_period:90s` 给足模型加载时间。

### 3.3 数据持久化设计

| 类型 | 内容 | 方式 | 目的 |
|------|------|------|------|
| 命名卷 | milvus/etcd/minio/mysql/redis 数据 | docker named volume | 容器删除后数据不丢 |
| 宿主绑定挂载 | BGE-M3 模型（4.3G，只读） | bind mount | 模型不进镜像，镜像精简、可移植 |
| 宿主绑定挂载 | output（含 all_chunks.json）、logs、knowledge_base | bind mount | 数据/产物在容器间共享、宿主可直接管理 |

## 4. 应用内部架构（rag-app）

```
请求 /api/ask(/stream)
   │
   ├─ 查询处理（可选改写）
   ├─ 检索层
   │    ├─ BM25 全文检索（jieba 分词，索引来自 all_chunks.json，18443 块）  ← 当前默认 fulltext
   │    └─ 向量检索（BGE-M3 嵌入 + Milvus）                              ← vector/hybrid 模式
   ├─ 重排（adaptive，可选）
   ├─ 上下文拼装（MAX_CONTEXT_CHUNKS 控制）
   └─ LLM 生成（远程 API，流式 SSE 返回）→ 带页码出处
```

- **嵌入模型**：BGE-M3，本地加载（`transformers.AutoModel`），容器内强制 `device=cpu`。
- **检索模式**：`retrieval_mode` 可选 `fulltext`(默认) / `vector` / `hybrid`，由 `.env` 的 `APP_RETRIEVAL_MODE` 控制。
- **前端**：单页 `api/static/index.html`，由 FastAPI 同域托管，相对路径调 API，零跨域配置。

## 5. 关键技术决策

| 决策 | 选择 | 理由 |
|------|------|------|
| torch 版本 | **CPU 版**（torch 2.6.0+cpu） | Docker Desktop GPU 直通配置复杂；日常问答仅嵌入一句话，CPU 足够；镜像从 ~6G 降到 ~3.3G。瓶颈是远程 LLM 生成（~2.9s），CPU 嵌入无感。 |
| 模型存放 | **只读卷挂载宿主目录** | 4.3G 不进镜像，镜像可移植、构建快；换机只需复制模型目录。 |
| 依赖服务镜像 | **复用宿主已有且验证可用的版本** | pymilvus 2.4.x ↔ milvus v3.0-beta 在宿主 gpu_env 实证可用；避免慢网重下 1GB+。 |
| 数据库 | **MariaDB 10.11**（服务名仍叫 mysql） | pymysql 协议兼容，宿主已有镜像；`database.py` 启动自动建库建表，无需手工 SQL。 |
| 配置注入 | **config.docker.json + 环境变量覆盖** | host 指向服务名；密钥/模式经 `.env` 注入，不写死镜像。 |
| 初始数据 | **fulltext 优先**（Milvus 可空） | 只要挂载 all_chunks.json，BM25 启动即可用，问答立即通过验收；向量灌库作为可选增强。 |

## 6. 配置与环境变量

`config.py` 支持 `APP_*` 环境变量覆盖 JSON 配置，容器化关键项：

| 环境变量 | 作用 |
|----------|------|
| `APP_MILVUS_HOST=milvus` | 向量库主机名（服务名） |
| `APP_DB_HOST=mysql` | 数据库主机名 |
| `APP_REDIS_HOST=redis` | 缓存主机名 |
| `APP_EMBEDDING_DEVICE=cpu` | 嵌入设备 |
| `APP_RETRIEVAL_MODE=fulltext` | 检索模式 |
| `APP_LLM_PROVIDER/API_KEY/BASE_URL/MODEL` | LLM 提供商与密钥（覆盖配置，便于切换 SiliconFlow/DeepSeek） |
| `RAG_CONFIG_PATH=/app/config.docker.json` | 指定容器内配置文件 |

---

## 7. 安全与隔离

- 数据库/向量库/缓存**不暴露端口**，只在内网用服务名访问。
- 密钥经 `.env` / 环境变量注入，`.env`、`config.docker.json` 已加入 `.gitignore`，不进版本库/镜像。
- 本部署栈（项目名 `rag-deploy`）与宿主机已有的开发容器（milvus-standalone/mariadb 等）**完全隔离、互不影响**。
