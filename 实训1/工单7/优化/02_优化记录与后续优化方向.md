## 第一部分：已完成的优化

### 总体效果（招股书 16 题测试集）

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 答案通过率 | 25% | **94%** |
| 检索命中率 Hit@5 | 0.25 | **0.94** |
| 平均倒数排名 MRR | 0.21 | **0.74** |
| 检索平均耗时 | 2385 ms | **686 ms** |
| 端到端 <3s 达标率 | 31% | **94%** |

### 年报 10 题测试集（功能测试工单）
- 答案通过率 90–100%、Hit@5 = 1.00、Hit@10 = 1.00、检索均值 ~108ms。

### 逐项优化明细

#### 1. 修复混合检索失效（根因级，收益最大）
- **问题**：hybrid 模式通过率仅 25%，低于其任一组件（fulltext 56%）。
- **根因**：向量检索（Milvus）与 BM25（all_chunks.json）跑在两套不同的 chunk_id 上，RRF 按 chunk_id 对齐两路结果时永远对不上，融合从未发生，分数塌缩成噪声。
- **措施**：① 默认检索模式切到当前最优的 fulltext，立即恢复可用；② 编写统一索引重建方案（向量与 BM25 共用全局 chunk_id），从根上修融合。

#### 2. 修复 BGE-M3 查询前缀
- **问题**：`encode_query` 给查询加了 bge-large-zh 的指令前缀「为这个句子生成表示…」，而 BGE-M3 是 instruction-free 模型，且文档侧未加前缀，导致 query/doc 向量不对称。
- **措施**：删除前缀，query 与 doc 同方式编码。零成本提升召回。

#### 3. 修复评估器误判（提升度量可信度）
- **问题**：① "5,520 万元" 因空格/markdown 星号匹配不上关键词 "5,520万"；② 答案含"知识库未包含"即早退判 0，哪怕前面已答对。
- **措施**：改为归一化匹配（去空格/逗号/星号）+ 移除错误早退。修复后通过率从 56% 还原到真实的 94%。

#### 4. 检索延迟优化
- **同义词变体 7 → 3**：每个变体都要全量 BM25 检索（18443 文档），变体过多是 >3s 主因。砍到 3 后 Hit@5 保持 0.94、检索耗时 1208 → 650 ms。
- **BM25 元数据 O(N) → O(1)**：原 `search_bm25` 每命中一条都全量线性扫描 18443 条 metadata，改为预建 chunk_id→metadata 字典查表。
- **LLM 上下文 15 → 8 块**：Hit@5≈0.94 说明答案几乎都在前几块，裁剪上下文减少 prefill，端到端 <3s 达标率 69% → 94%，且多答案题未掉分。

#### 5. 建立评估框架（一切优化的前提）
- 纯检索指标：Hit@k、MRR、Recall@k、Precision@k（不依赖 LLM、可复现）。
- 延迟指标：retrieval/llm/total 分段 + p50/p95 + <3s 达标率。
- 结果归档 `output/eval_history/`，`eval_compare.py` 跨运行算 delta、标注逐题翻转。
- RAGAS 集成（faithfulness / answer_relevancy / answer_correctness）。
- 支持外部测试集 `--testset` 与多模式对比 `--retrieval-mode`。

## 第二部分：可进一步优化的方向

### A. 统一索引重建（已备脚本，待执行）
- **目标**：让向量与 BM25 共用 all_chunks.json 的全局 chunk_id，RRF 真正融合，9 篇年报也进入向量检索。
- **收益**：hybrid 生效，补上 BM25 词不匹配的语义召回（如"军用收入"≈"国防销售额"），预计提升跨文档/语义类问题召回。
- **脚本**：`backend/rebuild_unified_index.py`（不调外部 API，可回滚）。

### B. 表格识别（冲召回率 95%）
- **问题**：页面分类只看文字密度（阈值 0.08）+ 有无图片，缺"是否表格"维度，导致财务表格被判为纯文字、经 pymupdf 拍平、行列结构丢失；个别表格数据（如某年度值）未进索引。
- **方向**：用 pymupdf `find_tables()` 做结构检测，表格转 markdown 保留行列；把 Qwen3-VL 配额从目录/封面页让给真正的财务表页。

### C. 多文档综合检索（跨文档题短板）
- **问题**：top-k 检索被单一高相关文档主导，"对比多家银行+保险"这类题覆盖不均（实测 Recall@10 仅 0.33）。
- **方向**：① 检索按文档/实体配额（保证每家公司至少 N 块进候选）；② 引入 GraphRAG / 知识图谱按实体-关系聚合；③ Agentic RAG：复杂题拆子查询分别检索再综合。

### D. LLM 生成延迟（端到端 <3s 的真瓶颈）
- **现状**：检索仅百毫秒，但分析型长答案 LLM 生成达 5–11 秒，拖垮端到端达标率。
- **方向**：① 流式输出（首 token <1s，体感秒回，系统已有 ask_stream 接口）；② 限制 max_tokens、对分析题进一步裁上下文；③ 切换更快的推理端点（config 已配 provider_2 / SiliconFlow）。

### E. 重排增强
- 当前 reranker 路径为空，自适应重排实际未启用交叉编码器。可接入 BGE-Reranker 做精排，提升 top 结果相关性（注意延迟预算）。

### F. 可扩展性（数据量/并发增长后）
- **向量索引**：当前数据量小，IVF_FLAT 足够；增长到百万级应换 HNSW，更大规模用 IVF_PQ / DiskANN，参数用评估当"召回标尺"标定。
- **全文检索**：当前 BM25 为纯 Python、单机、O(N)，高并发会先成为瓶颈；可迁移 Elasticsearch 或 Milvus 原生稀疏检索。
- **嵌入服务**：单卡串行，并发下需 batch / 多实例。
- 配套：用 Locust/k6 做负载测试找拐点，Prometheus/Grafana 监控延迟分位与资源利用。

### G. 评估自动化
- 分析/评价类问题用 RAGAS / LLM-as-judge 替代关键词评分；扩充测试集到 50+ 题（含全部 11 文档）以使 90%/95% 指标在统计上可靠。

## 优化优先级建议

| 优先级 | 方向 | 解决的问题 |
|---|---|---|
| 高 | D. 流式输出 | 端到端 <3s 达标 |
| 高 | A. 统一索引重建 | hybrid 生效、语义召回 |
| 中 | B. find_tables 表格 | 召回率冲 95% |
| 中 | C. 多文档配额/GraphRAG | 跨文档综合题 |
| 低 | E/F/G | 精排、可扩展性、评估自动化 |
