### P1：LightRAG 冷启动延迟高（首次约 10 秒）

**严重程度：中** | **影响范围：系统初次使用体验**

**现象描述：**  
rag-app 容器启动后，首次调用 LightRAG 接口需等待约 8-12 秒，因为 LightRAG 实例采用懒加载策略，首次调用时才加载 `.graphml` 文件（5479 节点）、BGE-M3 模型、三个 VDB（实体/关系/chunk）。

**根因分析：**  
```python
# api.py 中的懒加载逻辑
_lightrag_instance = None

def _query_lightrag_instance(query, mode):
    global _lightrag_instance
    if _lightrag_instance is None:            # 首次调用才初始化
        _lightrag_instance = create_lightrag(...)  # 约 8-12 秒
    return query_lightrag(_lightrag_instance, query, mode)
```

**优化方案：**  
在 API 启动时（`_init_resources()` 函数内）预热 LightRAG：
```python
# 在 _init_resources() 末尾添加预热
def _init_resources():
    # ... 原有初始化逻辑 ...
    
    # LightRAG 预热（异步，不阻塞启动）
    import threading
    def _warmup_lightrag():
        try:
            _query_lightrag_instance("系统预热", mode="hybrid")
            logger.info("LightRAG 预热完成")
        except Exception as e:
            logger.warning(f"LightRAG 预热失败（不影响使用）: {e}")
    
    threading.Thread(target=_warmup_lightrag, daemon=True).start()
```

**预期效果：** 容器启动后约 15 秒内完成预热，之后首次用户调用响应时间 < 500ms。

### P2：Answer Correctness 偏低（66-67%）

**严重程度：中** | **影响范围：RAGAS 评估指标**

**现象描述：**  
两套系统的 `answer_correctness` 均约 66-67%，未能突破 70%。该指标综合了语义相似度和事实覆盖率，而测试集中大量题目要求精确数字（如"31.28%""8,400 万元"），模型有时表述为近似值或单位不一致。

**根因分析：**

1. **精确数字表述差异**：
   ```
   ground_truth: "4200万股"
   actual answer: "4,200 万股"（带千位逗号）
   → RAGAS 字面匹配失败，但语义正确
   ```

2. **参考答案过于简短**：
   ```
   ground_truth: "IC设计"（2字）
   actual answer: "主要应用于IC设计领域..." （完整句子）
   → answer_correctness 因长度不对等而偏低
   ```

3. **RAGAS 版本差异**：不同版本 answer_correctness 计算权重不同。

**优化方案：**

方案A（推荐）：优化 ground_truth 设计
```python
# 改为完整句子形式的参考答案
{
    "id": 1,
    "question": "武汉力源信息发行了多少股？",
    # 原来
    "expected_answer": "4200万股",
    # 优化后
    "expected_answer": "武汉力源信息技术股份有限公司本次公开发行4,200万股人民币普通股（A股）",
}
```

方案B：对数字归一化后再计算
```python
import re
def normalize_numbers(text: str) -> str:
    # 去除千位逗号，统一万/亿/元等单位
    text = re.sub(r'(\d),(\d)', r'\1\2', text)
    return text
```

### P3：LightRAG Rerank 警告（未配置 Rerank 模型）

**严重程度：低** | **影响范围：日志噪音**

**现象描述：**  
每次 LightRAG 查询都会输出警告：
```
WARNING | Rerank is enabled but no rerank model is configured.
```

**根因分析：**  
LightRAG 默认 `enable_rerank=True`，但未提供 rerank 模型路径。

**优化方案：**  
在 `lightrag_integration.py` 的 `create_lightrag()` 中显式关闭：
```python
rag = LightRAG(
    working_dir=working_dir,
    llm_func=llm_func,
    embedding_func=embedding_func,
    enable_rerank=False,    # 无 rerank 模型时显式关闭
)
```

**进阶方案：** 配置 BGE-reranker-v2-m3 作为 rerank 模型，进一步提升检索精度：
```python
from lightrag.rerank import BgeReranker
rag = LightRAG(
    ...,
    enable_rerank=True,
    rerank_model=BgeReranker("/models/bge-reranker-v2-m3"),
)
```

### P4：评估面板 RAG 逐题回答显示为命中详情（非完整回答）

**严重程度：低** | **影响范围：前端展示效果**

**现象描述：**  
"逐题对比" Tab 中，RAG 侧的"回答"列显示的是关键词命中详情（如 `[命中:3/3] 4200万股 | 发行比例 | 比例`），而非完整回答文本。

**根因分析：**  
`eval_quick.py` 的早期版本在 `results` 中未保存 `answer` 字段，历史评估 JSON 缺少该字段。

**修复状态：** `eval_quick.py` 已在工单14 中修复，新增 `"answer": answer`。**需重跑一次评估**才能看到完整回答：
```bash
python eval_quick.py --ragas
```

### P5：LightRAG 静态评估数据（无实时更新）

**严重程度：低** | **影响范围：评估面板实用性**

**现象描述：**  
评估面板反映的是上次手动运行评估脚本的结果，不会随实际对话数据自动更新。

**优化方案：**

方案A（轻量）：在面板显示最后更新时间，提醒用户数据是静态的：
```javascript
// 前端已实现：summaryRow 中显示 timestamp
summaryRow = `<div>📚 RAG 评估时间: ${rag.timestamp}</div>`;
```

方案B（重量）：添加后台定时评估任务（APScheduler），每天凌晨自动跑一次评估：
```python
from apscheduler.schedulers.background import BackgroundScheduler

def auto_eval():
    import subprocess
    subprocess.run(["python", "backend/eval_quick.py", "--ragas"])

scheduler = BackgroundScheduler()
scheduler.add_job(auto_eval, 'cron', hour=3, minute=0)
scheduler.start()
```

## 二、中期优化路线

### O1：增加 Rerank 模型提升检索精度

**优先级：高** | **工作量：中（1天）**

配置 BGE-reranker 对 LightRAG 检索结果进行二次排序：
- 预期提升：Faithfulness +3-5pt，ctx_recall +5pt
- 依赖：下载 `BAAI/bge-reranker-v2-m3` 模型（约 1GB）

---

### O2：RAGAS 评估接入 LightRAG 在线对话数据

**优先级：中** | **工作量：中（1-2天）**

将用户实际对话（question + answer + sources）异步写入 RAGAS 评估队列，每日生成在线评估报告：
```
用户对话 → 记录 {q, a, ctx} → 队列 → 后台 RAGAS 评估 → 写入 eval_history
```

---

### O3：知识图谱增量更新

**优先级：中** | **工作量：高（3-5天）**

当前知识图谱固定来自两份招股说明书，不支持增量添加新文档。

**实现思路：**
1. 检测新上传的 PDF（对比 `doc_status.json`）
2. 仅对新 chunk 运行实体/关系抽取
3. 将新节点/边 merge 到已有图谱（去重+权重更新）
4. 触发 GPU 增量向量化

---

### O4：LightRAG 模式参数前端可配置

**优先级：低** | **工作量：小（0.5天）**

当前模式固定为 `hybrid`，在前端暴露模式选择器（local/global/hybrid/naive），让用户可以根据场景灵活切换。

```html
<!-- 在"知识库来源"选择器下方添加 -->
<select id="lightrag-mode-select" onchange="setLightRAGMode(this.value)">
    <option value="hybrid">hybrid（默认，推荐）</option>
    <option value="local">local（细节查询）</option>
    <option value="global">global（宏观查询）</option>
    <option value="naive">naive（对照组）</option>
</select>
```

## 三、性能优化建议

### 延迟优化

| 优化点 | 当前状态 | 优化方向 | 预期收益 |
|--------|---------|---------|---------|
| LightRAG 冷启动 | 首次 10s | 启动预热（P1方案）| 首次 < 0.5s |
| LLM 缓存命中率 | 约 95%（固定测试集）| 实际对话缓存存储位置分离 | 维持高命中率 |
| BGE-M3 向量化 | cuda:0 | 批量推理 batch_size=32 | 单次节省约 30% 时间 |
| Rerank 延迟 | 未启用 | 若启用，用 cuda 加速 | 控制在 +50ms 以内 |

### 成本优化

| 优化点 | 当前状态 | 优化方向 |
|--------|---------|---------|
| RAGAS 评估频次 | 手动触发 | 每周一次自动评估（而非每次问答）|
| LightRAG 建图 LLM | DeepSeek → SiliconFlow | 仅增量更新时调用，已建完无额外成本 |
| 评估结果 JSON 大小 | 每份约 300KB | 截断 contexts 字段（限 2000 字符）减小文件体积 |
