## 一、项目背景与目标

### 1.1 竞赛背景

本次任务旨在参与 **阿里云天池算法大赛** 的特定赛题。该赛题要求参赛者在阿里云 **PAI-LangStudio** 平台上，**不通过模型微调**，仅凭 **Agent 工程能力**（规划、工具调用、提示词优化等），构建一个能完成复杂信息检索与推理任务的 Research Agent，并最终将其部署为标准的 **PAI-EAS HTTP 服务** 以供官方评测。

竞赛强调 **"规划 + 工具集成 + 工程落地"** 的综合能力。

### 1.2 核心约束

| 约束类型 | 具体要求 |
|----------|----------|
| **禁止微调** | 禁止任何形式的模型微调（包括 LoRA、Adapter、自训练权重等） |
| **模型白名单** | 仅允许使用 PAI Model Gallery 部署的 Qwen 基础模型 或 阿里云百炼提供的 Qwen 系列模型服务 |
| **禁止作弊** | 禁止在提示词、Python 节点、配置文件中硬编码评测题答案（包括哈希映射、关键词触发返回固定答案等） |
| **工具限制** | 允许使用阿里云 IQS、SerpAPI、Bing 等搜索引擎；允许使用 MCP；禁止调用第三方 Agent 服务 |
| **实现范围** | 所有 Agent 逻辑必须在 LangStudio 项目包中实现 |

### 1.3 项目目标

| 目标 | 说明 |
|------|------|
| **掌握平台** | 掌握 PAI-LangStudio 应用开发全流程（工作流模式/代码模式） |
| **最大化模型能力** | 在禁止微调的约束下，通过工具策略、提示词优化等方式，最大化基础模型在复杂任务上的表现 |
| **可量化评测** | 建立可量化、可复现、可审计的评测机制 |
| **正确率上榜** | 在100道验证集题目上达到可上榜的正确率 |

## 二、评测数据集

### 2.1 数据规模

- **题目数量**: 100 道公开验证集题目
- **数据格式**: JSONL（`question.jsonl`）
- **答案格式**: JSONL（`answer.jsonl`）

### 2.2 题目类型

| 题目类型 | 说明 | 示例 |
|----------|------|------|
| **事实验证** | 验证某个陈述是否正确 | "北京是中国的首都吗？" |
| **多步推理** | 需要多步逻辑推导的问题 | "A比B大，B比C大，谁最小？" |
| **单位换算** | 涉及数值和单位转换 | "1英里等于多少公里？" |

### 2.3 答题规范

| 规范 | 要求 |
|------|------|
| **答案唯一性** | 每题拥有唯一答案 |
| **格式要求** | 如题目中声明了回答格式，请严格遵循，否则会被判断为错误回答 |
| **语言一致** | 如题目中没有特殊声明，则答案和问题的语言保持一致（中文问题→中文答案，英文问题→英文答案） |
| **联网搜索** | 所有题目仅需联网搜索即可解答 |

### 2.4 评测机制

```
评测脚本
    │
    ├── 加载 100 道验证集问题及其参考答案
    │
    ├── 加载参赛者提交的 answer.jsonl
    │
    ├── 对答案进行归一化匹配
    │   ├── 去除多余空格、标点
    │   ├── 统一大小写（英文）
    │   └── 数值精度处理
    │
    ├── 逐题对比：提交答案 vs 参考答案
    │
    └── 统计成功回答的题目数，计算正确率
        └── 正确率要达到上榜标准
```

### 3.2 Agent 核心架构：ReAct 模式

本项目采用 **ReAct（Reasoning + Acting）** 模式作为 Agent 的核心架构：

```
输入问题
    │
    ▼
┌──────────────┐
│   Thought    │  ← 分析题目类型、确定解题策略
│   (思考)     │  ← "这是一个多步推理问题，需要...
└──────────────┘
    │
    ▼
┌──────────────┐
│   Action     │  ← 调用工具（搜索/计算/转换）
│   (行动)     │  ← Action: Search["关键词"]
└──────────────┘
    │
    ▼
┌──────────────┐
│ Observation  │  ← 获取工具返回结果
│   (观察)     │  ← "搜索结果：..."
└──────────────┘
    │
    ├── 需要更多信息？ → 回到 Thought
    │
    └── 足够回答？ → 生成最终答案
              │
              ▼
        ┌──────────────┐
        │    Answer    │  ← 归一化、格式化输出
        │    (答案)    │
        └──────────────┘
```

### 4.2 第二阶段：Research Agent 设计与开发

#### 4.2.1 架构设计

**核心组件**:

| 组件 | 职责 | 实现方式 |
|------|------|----------|
| **规划器 (Planner)** | 分析题目类型，确定解题策略 | System Prompt + LLM |
| **工具选择器 (Tool Selector)** | 根据需求选择合适工具 | ReAct 循环中的 Action |
| **执行器 (Executor)** | 调用工具并获取结果 | 工具节点/自定义代码 |
| **推理器 (Reasoner)** | 基于观察结果进行推理 | LLM 推理 |
| **答案生成器 (Answer Generator)** | 归一化并格式化最终答案 | Prompt + 后处理 |

#### 4.2.2 工具集成

**允许使用的工具**:

| 工具 | 类型 | 用途 |
|------|------|------|
| **阿里云 IQS** | 搜索引擎 | 中文搜索、实时信息查询 |
| **SerpAPI** | 搜索引擎 | Google 搜索结果获取 |
| **Bing** | 搜索引擎 | 微软搜索 API |
| **MCP** | 协议 | 连接外部工具和服务 |

**工具调用策略**:

```python
# 工具选择逻辑示例
def select_tool(question_type, query):
    if question_type == "事实验证":
        return search_engine.search(query)
    elif question_type == "多步推理":
        return multi_step_reasoning(query)
    elif question_type == "单位换算":
        return unit_converter.convert(query)
    else:
        return search_engine.search(query)
```

#### 4.2.3 提示工程 (Prompt Engineering)

**System Prompt 设计要点**:

| 要素 | 说明 |
|------|------|
| **角色定义** | 你是一个专业的 Research Agent，擅长通过搜索和推理回答问题 |
| **思考方式** | 要求模型先分析题目类型，再制定解题策略 |
| **工具使用** | 明确工具的调用方式和返回格式 |
| **答案格式** | 严格遵循题目要求的回答格式 |
| **语言一致** | 中文问题用中文回答，英文问题用英文回答 |
| **归一化** | 去除多余空格、标点，统一格式 |

**示例 System Prompt 框架**:

```
你是一个 Research Agent，你的任务是通过联网搜索和逻辑推理来回答用户的问题。

【约束】
- 禁止在回答中硬编码任何预设答案
- 必须使用搜索工具获取信息
- 回答必须与问题语言保持一致
- 如题目声明了回答格式，必须严格遵循

【思考流程】
1. 分析题目类型（事实验证/多步推理/单位换算）
2. 确定需要的搜索关键词或计算步骤
3. 调用工具获取信息
4. 基于获取的信息进行推理
5. 生成最终答案并归一化格式

【工具说明】
- Search[query]: 使用搜索引擎查询信息
- Calculate[expression]: 执行数学计算

【输出格式】
Thought: [你的思考过程]
Action: [调用的工具]
Observation: [工具返回结果]
...
Answer: [最终答案]
```

## 七、开发建议

1. **使用 AI 编程工具**: 建议使用 Cursor、Trae 等 AI 编程工具辅助实现提示工程和调试
2. **分阶段迭代**: 先实现基础搜索回答，再逐步增加多步推理和复杂逻辑
3. **Prompt 版本管理**: 记录每次 Prompt 修改和对应的正确率变化
4. **错题分析**: 对答错的题目进行分类分析，针对性优化策略
5. **工具组合策略**: 尝试不同搜索引擎的组合使用，提升搜索覆盖率
6. **答案后处理**: 实现统一的答案归一化函数（去空格、统一标点、数值格式化等）

## 八、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 搜索工具限制 | 信息获取不全 | 组合使用多个搜索引擎，使用 MCP 扩展工具 |
| 模型推理错误 | 错误答案 | 增加验证步骤，多轮搜索确认 |
| 格式不匹配 | 被判错误 | 严格实现格式解析和输出控制 |
| 网络超时 | 服务不稳定 | 增加超时重试机制 |
| 正确率不达标 | 无法上榜 | 持续迭代优化 Prompt 和工具策略 |
