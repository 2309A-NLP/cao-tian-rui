# 日程提醒智能体 — 实现步骤与过程问题记录

工单编号：人工智能 NLP-Agent 数字人项目-日程提醒智能体任务

---

## 一、实现步骤

### 第1步：确定架构方案

**选型决策：**
- LLM：硅基流动（SiliconFlow）DeepSeek-V3，OpenAI 兼容接口
- 交互模式：Function Calling（工具调用），LLM 决策调哪个工具、传什么参数
- 后端：FastAPI + SSE 流式推送
- 数据库：MySQL 8.0 + PyMySQL
- 提醒：后台线程定时扫描 + 前端 15s 轮询

**核心选型理由：**
Function Calling 比纯 Prompt 更可靠——LLM 不是"说"要做什么，而是返回结构化的工具调用请求，代码层确保数据库被调用，实现100%数据库调用率。

---

### 第2步：数据库设计与建表

设计 `schedules` 表，包含：
- 基础字段：id、title、schedule_date、schedule_time
- 循环规则：repeat_type（枚举）+ repeat_rule（JSON字符串）
- 状态管理：status（active/completed/cancelled）
- 提醒控制：remind_before、last_reminded

`DatabaseManager` 类封装所有 CRUD 操作，`connect()` 时自动建库建表。

---

### 第3步：定义 Function Calling 工具 Schema

定义 4 个工具的 OpenAI 格式 Schema：
- `add_schedule`：添加，带字段校验和循环规则说明
- `query_schedules`：查询，支持日期/关键词/状态过滤
- `update_schedule`：修改，仅更新传入字段
- `delete_schedule`：删除，含 confirmed 两阶段确认

每个工具的 `description` 字段写入详细规则，引导 LLM 正确使用。

---

### 第4步：实现 Agent Engine

Function Calling 循环逻辑（最多5轮）：
```
用户消息 → 调 LLM（携带工具）→ 有 tool_calls？
    是 → 执行工具 → 结果加入消息链 → 继续循环
    否 → 输出文本回复 → 结束
```

同时实现：
- `Session` 对象管理多用户会话
- 防重复调用机制（`called_tools_this_turn`）
- System Prompt 动态生成（每次 Session 创建时用当前时间）

---

### 第5步：实现 LLM 真实流式输出

`LLMProvider.chat_stream()` 使用 `stream=True` 调用 API，逐块解析 SSE：
- 文本 token：直接 yield 到前端，实现打字效果
- tool_calls：跨 chunk 聚合完整后再执行

`AgentEngine.chat_stream()` 重写为消费 `llm.chat_stream()`，不再等全部响应再模拟逐字输出。

---

### 第6步：实现后台提醒线程

`ReminderThread` 作为守护线程：
- 每30秒调用 `get_due_schedules()` 查到期日程
- 调 `mark_reminded()` 防止同一天重复提醒
- 结果写入 `deque` 内存队列

`get_due_schedules()` 支持4种循环规则判断，最终加 `self.conn.commit()` 解决事务快照问题。

---

### 第7步：实现前端聊天界面

纯原生 JS，功能点：
- SSE 流式接收，逐 token 拼接显示
- 工具调用状态显示（"正在查询日程..."）
- 15s 轮询提醒队列，滑入横幅 + 浏览器通知
- localStorage 保存 session_id，刷新不丢会话

---

### 第8步：安全加固

- API Key 和 DB 密码移至 `.env`
- `config.json` 删除敏感字段
- `.gitignore` 添加 `.env`
- `config.py` 集成 `python-dotenv`

---

### 第9步：测试与修复

按验收标准逐条测试，记录问题并修复（详见优化文档）。

## 二、关键过程问题记录

### 问题记录1：启动报 UnicodeEncodeError（Windows GBK 终端）

**时间节点：** 第一次成功启动服务后

**现象：**
```
UnicodeEncodeError: 'gbk' codec can't encode character '\U0001f514'
```

**原因：** `reminder.py` 日志中使用了 emoji `🔔`，Windows 控制台默认编码 GBK 无法编码 Unicode emoji。

**解决：** 删除日志信息中的 emoji 字符，改为纯文字。

---

### 问题记录2：删除调试代码遗留

**时间节点：** 调试 auto-map 功能时

**现象：** `tools.py` 中遗留了调试用的文件写入代码：
```python
with open("e:/debug_automap.txt", "w") as f:
    f.write(...)
```

**解决：** 清理所有调试用临时代码，生产代码不应有文件 side effect。

---

### 问题记录3：`__pycache__` 混用导致旧代码生效

**时间节点：** 修改代码后重启服务，改动不生效

**原因：** Python 3.10 和 3.12 混用，旧版本的 `.pyc` 缓存覆盖了新代码。

**解决：** 清空 `__pycache__` 目录，强制重新编译。

---

### 问题记录4：LLM 忽略工具返回的映射提示

**时间节点：** 实现序号→DB_ID 映射功能时

**现象：** 工具返回"请用 schedule_id=28 调用删除"，LLM 仍然用序号 1 调用。

**原因：** LLM（DeepSeek Chat）对工具结果中的"再次调用指令"遵从率不高，更倾向于直接总结回复。

**解决：** 将映射逻辑内置到 ToolExecutor 中，而不依赖 LLM 二次理解工具返回值。同时在 System Prompt 中多层次强化序号≠DB_ID 的规则。

---

### 问题记录5：循环日程 `repeat_rule` 字段 JSON 反序列化

**时间节点：** 测试循环日程提醒时

**现象：** 存入数据库的 `repeat_rule` 是字符串 `'{"weekdays":[1,2,3,4,5]}'`，提醒线程读出后需要解析，但有时 LLM 传入格式不规范（单引号、多余空格等）导致 `json.loads` 失败。

**解决：** 用 `try/except` 包裹所有 `json.loads(repeat_rule)` 调用，解析失败时使用空字典 `{}`，避免整个提醒线程崩溃。

---

### 问题记录6：title 字段规范化问题

**时间节点：** 用户发现"17:00 开会"和"17:00 提醒您开会"同时出现

**原因：** 用户说"提醒我下午5点开会"，LLM 把 title 解析为"提醒您开会"，而非纯事项名"开会"。两条看似不同的记录本质相同。

**解决：**
1. System Prompt 规则7加强：明确要求去掉"提醒我/您/帮我/别忘了"等前缀
2. 重复检测同时检查"同名"和"同时间段"两种情况
3. 清理已有的重复数据
