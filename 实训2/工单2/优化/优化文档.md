## 问题1：System Prompt 时间固化，LLM 永远说"今天是启动那天"

**现象：**
服务启动后运行了几个小时，LLM 仍然报告错误的当前时间（始终是服务启动时的时间）。

**根本原因：**
`SYSTEM_PROMPT` 定义为模块级常量，Python 在 `import` 时执行一次 `datetime.now()`，之后就固化了：
```python
# 错误写法
SYSTEM_PROMPT = f"现在是 {datetime.now().strftime('%H:%M')}"  # 永远是启动时间
```

**解决方法：**
将 System Prompt 改为函数，每次创建 `Session` 时动态生成：
```python
def _build_system_prompt() -> str:
    now = datetime.now()  # 每次调用时取当前时间
    return f"现在是 {now.strftime('%Y年%m月%d日 %H:%M')}"

class Session:
    def __init__(self):
        self.messages = [{"role": "system", "content": _build_system_prompt()}]
```

## 问题2：PyMySQL 返回 TIME 字段为 timedelta，JSON 序列化失败

**现象：**
查询日程时，时间字段显示为 `54900.0`（秒数）而非 `"17:00"`。

**根本原因：**
MySQL TIME 类型通过 PyMySQL 返回的是 `datetime.timedelta` 对象，不是 `time` 对象。`json.dumps` 不知道如何序列化 `timedelta`，默认转为秒数浮点值。

**解决方法：**
在 `_serialize()` 方法中专门处理 `timedelta`：
```python
elif isinstance(val, timedelta):
    total_secs = int(val.total_seconds())
    record[key] = f"{total_secs // 3600:02d}:{(total_secs % 3600) // 60:02d}:{total_secs % 60:02d}"
```

## 问题3：端口 8000/8001 被占用，服务无法启动

**现象：**
启动报 `[Errno 10048] error while attempting to bind on address ('0.0.0.0', 8001)`

**根本原因：**
上次服务没有正常关闭，进程仍在后台占用端口。Windows 下 `Ctrl+C` 有时不能完全杀死 uvicorn 进程。

**解决方法：**
```bash
# 查找占用端口的进程
netstat -ano | findstr 8001
# 强制结束进程
taskkill /F /PID <PID>
```
后将默认端口从 8000 改为 8001 避免与其他常见服务冲突。

## 问题4：提醒线程 WinError 10038（在非套接字上执行套接字操作）

**现象：**
启动日志中出现：
```
ERROR | 提醒线程扫描异常: [WinError 10038] 在一个非套接字上尝试了一个操作
```
提醒线程随即停止工作。

**根本原因：**
`DatabaseManager` 持有单个 `pymysql.Connection`（本质是 TCP socket）。FastAPI 主线程（处理 API 请求）和提醒线程共用同一个连接，两个线程同时操作同一个 socket，Windows 报 `WinError 10038`。

PyMySQL 连接**不是线程安全的**。

**解决方法：**
在 `api.py` 中为提醒线程创建独立的 `DatabaseManager` 实例：
```python
# 主线程连接
db = DatabaseManager(...)
db.connect()

# 提醒线程独立连接（两者互不干扰）
_reminder_db = DatabaseManager(...)
_reminder_db.connect()
reminder_thread = ReminderThread(db_getter=lambda: _reminder_db, interval=30)
```

## 问题5：LLM 调用硅基流动 API 返回 400 Bad Request（第2轮）

**现象：**
第1轮 LLM 调用工具成功，第2轮（工具结果回填后再调 LLM）报 400 错误：
```
ERROR | LLM 流式请求失败: 400 Client Error: Bad Request for url: .../chat/completions
```

**根本原因：**
流式聚合出的 `tool_calls` 缺少 `"type": "function"` 字段。OpenAI Function Calling 规范要求每个 tool_call 必须有此字段，硅基流动严格校验：
```python
# 错误：缺少 type 字段
accumulated_tool_calls[idx] = {"id": "", "function": {"name": "", "arguments": ""}}

# 同时：assistant 消息 content=null，部分提供商不接受
"content": "".join(content_buf) or None  # 错误
```

**解决方法：**
1. 初始化 tool_call 时加入 `"type": "function"`：
```python
accumulated_tool_calls[idx] = {
    "id": "", "type": "function",
    "function": {"name": "", "arguments": ""}
}
```
2. 将 `content: null` 改为 `content: ""`：
```python
"content": "".join(content_buf) or ""  # 正确
```

## 问题6：序号与数据库 ID 混淆，删除错误日程

**现象：**
用户说"删除日程1"，LLM 直接把 `schedule_id=1` 传给工具，实际上 `1` 是用户看到的显示序号，而数据库 ID 可能是 28、30 等任意值，导致删除失败或删错。

**根本原因：**
数据库自增 ID 是全局递增的，不等于用户眼中的"第1条、第2条"。LLM 没有区分这两种概念。

**解决方法（多层保障）：**
1. **查询结果格式**带 DB_ID 提示：`#1 [DB_ID=28] 17:00 开会`
2. **System Prompt 规则2**明确区分：序号是排列顺序，DB_ID 是数据库真实 ID
3. **工具描述**中重复警告：`用户说的'1'是显示序号，不是DB_ID`
4. **ToolExecutor 自动映射兜底**：传入 schedule_id 找不到 DB 记录时，自动把它当作序号去列表里找

## 问题7：重复日程被静默添加

**现象：**
用户无意间两次输入相似内容（如"提醒我开会"和"添加下午5点开会"），系统添加了两条相同时间的日程，查询结果出现重复。

**根本原因：**
LLM 有时将"提醒我开会"解析为 `title="提醒您开会"`，与已有的 `title="开会"` 不完全相同，绕过了精确匹配的重复检测。

**解决方法：**
1. **规范化 title**：在 System Prompt 规则7中明确要求去掉"提醒我/您/帮我"等前缀
2. **双重检测**：`_add_schedule` 工具检查同名 AND 同时间段两种情况，任一命中则询问确认
3. **force 参数**：用户确认要重复添加时，传 `force=true` 跳过检测

## 问题8：提醒线程无法感知新添加的日程（核心 bug）

**现象：**
添加了一条时间已到的日程，等待超过30秒，提醒仍未触发。检查日志发现提醒线程在服务启动时扫描了一次，之后即使有新日程到期也不提醒。

**根本原因：**
MySQL InnoDB 默认隔离级别为 **REPEATABLE READ**。PyMySQL 默认不开启 autocommit，第一次 SELECT 即开启了一个隐式事务。在这个事务的生命周期内，所有 SELECT 读到的都是**事务开始时的数据快照**——无论其他连接之后写入了多少新数据，提醒线程都看不见。

提醒线程在服务启动时做了第一次 SELECT，之后没有 commit/rollback，事务一直悬挂，所有后续扫描看到的都是服务启动时的库状态。

**验证方法：**
查看日志，提醒线程第一次扫描正常，之后加入的日程无论多久都不触发。查数据库 `last_reminded IS NULL` 的日程明明时间已过。

**解决方法：**
在 `get_due_schedules()` 方法结尾加 `self.conn.commit()`，结束隐式事务，确保下次扫描开启新事务读最新数据：
```python
def get_due_schedules(self) -> list:
    ...
    # 结束隐式事务，确保下次扫描读到最新数据
    self.conn.commit()
    return results
```

## 问题9：循环日程第二天不触发提醒

**现象：**
设置了"每个工作日早上9点站会"，当天能收到提醒，第二天不提醒。

**根本原因：**
原 `get_due_schedules()` 查询条件为 `schedule_date = 今天`，而循环日程的 `schedule_date` 存的是**创建当天的日期**（如 2026-06-23），第二天（2026-06-24）查询时条件不满足，日程就被跳过了。

**解决方法：**
重写 `get_due_schedules()`，先用 `schedule_time <= 当前时间` 获取候选行，再在 Python 代码中根据 `repeat_type` 分别判断是否应该今天触发：
- `none`：只在 `schedule_date == 今天` 触发
- `daily`：`schedule_date <= 今天` 即可触发
- `weekly`：判断今天星期几是否在 `repeat_rule.weekdays` 列表中
- `monthly`：判断今天日期数是否等于 `repeat_rule.day`
- `yearly`：判断今天月份和日期是否匹配 `repeat_rule.{month, day}`

## 问题10：API Key 明文存储在 config.json 存在泄露风险

**现象：**
`config.json` 包含 `"llm_api_key": "sk-xxx..."` 和 `"db_password": "xxx"`，如果代码提交到 Git 或上传到服务器，密钥直接暴露。

**解决方法：**
1. 创建 `.env` 文件存放敏感信息，`.gitignore` 屏蔽它
2. 从 `config.json` 删除 `llm_api_key` 和 `db_password` 字段
3. `config.py` 使用 `python-dotenv` 自动加载 `.env`
4. 提供 `.env.example` 模板让新部署者知道需要填哪些值

```
# .env（不提交）
AGENT_LLM_KEY=sk-真实key
AGENT_DB_PASS=真实密码
```
