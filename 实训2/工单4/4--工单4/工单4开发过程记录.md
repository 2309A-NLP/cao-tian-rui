## 一、设计

### 1.1 需求分析

- 输入：1000道自然语言问题（`question.jsonl`），涵盖基金/股票/债券历史数据查询
- 输出：自然语言回答（`outputs/answers.jsonl`）
- 额外要求：暴露 LangChain Tool 接口供工单6调用；提供 Gradio 网页演示

### 1.2 技术选型

| 组件 | 选择 | 理由 |
|---|---|---|
| 数据库 | SQLite（只读模式） | 数据为静态文件（1.46GB .db），无需服务器 |
| NL2SQL 模型 | DeepSeek-V3（硅基流动 API） | MoE 架构，SQL 生成能力强，激活约 37B 参数 |
| 回答生成 | Qwen2.5-7B-Instruct | 格式化简单结果，比 72B 快约 2s |
| Tool 接口 | LangChain Tool | 工单6统一要求 |
| Web UI | Gradio | 快速搭建演示页面 |

### 1.3 整体架构

```
用户问题
  ↓
[预分类器] 关键词规则，零 API 成本
  ├─ 招股书类 → 返回 "__PROSPECTUS__"，转工单5
  └─ 数据库类 ↓
       [NL2SQL] DeepSeek-V3 生成 SQL
         ↓
       [SQL 执行] SQLite 只读，30s 超时
         ├─ 执行失败 → 带错误重新生成（最多3次）
         └─ 执行成功 ↓
              [回答生成] 直接格式化（无 LLM）或 7B 模型
                ↓
              返回自然语言答案
```

### 1.4 数据库结构

10张表，数据覆盖 2019-2021 年：

| 表名 | 说明 |
|---|---|
| A股票日行情表 | 股票每日收盘价、涨跌等行情 |
| A股公司行业划分表 | 中信行业分类，关联股票 |
| 基金基本信息 | 基金代码、简称、管理人、类型 |
| 基金股票持仓明细 | 基金季报持股明细 |
| 基金债券持仓明细 | 基金季报持债明细 |
| 基金可转债持仓明细 | 可转债持仓，列名特殊（见问题5） |
| 基金日行情表 | 基金净值行情 |
| 基金规模变动表 | 申赎规模 |
| 基金份额持有人结构 | 机构/个人投资者占比 |
| 港股票日行情表 | 港股行情 |

## 二、实现

### 2.1 核心模块

**`src/config.py`**
- 从项目根目录 `.env` 加载配置
- `_resolve_path()` 将相对路径转为绝对路径，避免工作目录不同引发问题

**`src/db_utils.py`**
- 以只读模式（`mode=ro`）打开 SQLite，防止意外写入
- `get_full_schema()` 用 `@lru_cache` 缓存 Schema，避免重复 IO
- `set_progress_handler` 实现 30 秒查询超时

**`src/nl2sql.py`**
- 18 条提示规则，约束 LLM 生成合法 SQL
- `temperature=0.0` 保证确定性输出
- `extra_body={"enable_thinking": False}` 关闭 Qwen3 系列的思考链（省时）
- `_extract_sql()` 清洗模型输出的 Markdown 包装

**`src/sql_executor.py`**
- 执行失败时调用 `generate_sql_with_error_hint()` 携带错误信息重试
- 最多重试 `MAX_RETRY`（默认3）次

**`src/answer_gen.py`**
- `_try_direct_format()` 对简单结果直接格式化，跳过 LLM：
  - 单行（≤6列）→ 拼接 `字段：值`
  - 多行单列 → `字段名：值1、值2、值3`
  - 多行两列（≤10行）→ 编号列表
- 复杂结果调用 7B 模型生成摘要

**`src/fund_agent.py`**
- 预分类器：DB 强信号词优先，招股书词次之，8位日期兜底
- `FundAgent.query()` 串联完整流程
- 导出 `fund_db_tool`（LangChain Tool）供工单6使用

**`batch_process.py`**
- 断点续跑：读已有答案 ID，跳过已处理题目
- 熔断器：连续 10 次 API 错误后停止
- 每题立即写盘（flush），不丢中间结果
- 限流：题目间隔 `REQUEST_INTERVAL`（默认 5 秒）

**`app.py`**（Gradio UI）
- 预加载 Schema，避免首次查询卡顿
- 直接调用各子模块（NL2SQL → SQL执行 → 回答生成），不走 `agent.query()`，避免双重 NL2SQL 调用
- 显示逐步耗时：`NL2SQL Xs  SQL Xs  回答 Xs  共 Xs`

## 五、优化

### 5.1 API 调用次数优化

| 优化措施 | 效果 |
|---|---|
| 预分类器拦截招股书问题 | 节省约 400 次 API 调用（无须调 NL2SQL） |
| 直接格式化简单结果 | 单行/列表结果跳过第二次 LLM，节省 3s |
| 换用 DeepSeek-V3（MoE） | NL2SQL 比 72B Dense 稳定，SQL 错误重试减少 |
| 回答模型换为 7B | 复杂摘要比 72B 快约 2s |

### 5.2 SQL 执行性能优化

- 对全部 10 张表的高频查询字段建立索引（28个索引）
- `行业划分标准` 用精确匹配（`=`），不用 `LIKE '%中信%'`（前置通配符无法使用索引，导致全表扫描，执行时间从 6s → 0.3s）
- 30 秒查询超时，防止复杂 JOIN 永久卡死

### 5.3 批量处理可靠性优化

- 断点续跑：每题立即写盘，重启后自动跳过已完成题目
- 熔断器：连续 10 次 API 错误自动停止，避免余额耗尽
- 429 限流：等待 60 秒后重试，最多 3 次

### 5.4 最终响应时间

| 问题类型 | NL2SQL | SQL执行 | 回答生成 | 总计 |
|---|---|---|---|---|
| 招股书类 | 0s | 0s | 0s | <0.1s |
| 数据库类（单行） | ~6-9s | ~0.3s | 0s（直接格式） | ~7-10s |
| 数据库类（多行） | ~6-9s | ~0.3s | ~2s（7B） | ~9-12s |

## 六、问题与解决方法

### 问题1：只读数据库报写入错误

**现象**：`sqlite3.OperationalError: attempt to write a readonly database`

**原因**：`db_utils.py` 在打开 SQLite 后执行了 `PRAGMA journal_mode=WAL`，WAL 模式需要写权限，但数据库以只读模式打开。

**解决**：删除 `PRAGMA journal_mode=WAL` 语句，只读模式下无需设置日志模式。

---

### 问题2：数据库文件找不到

**现象**：`FileNotFoundError: data\博金杯比赛数据.db`

**原因**：`config.py` 中相对路径以**当前工作目录**为基准，从项目子目录运行脚本时路径解析出错。

**解决**：在 `config.py` 加入 `_BASE_DIR = Path(__file__).resolve().parent.parent`，所有相对路径统一以**项目根目录**为基准转换为绝对路径。

---

### 问题3：SQL 列名歧义导致执行失败

**现象**：`ambiguous column name: 股票代码`（多表 JOIN 时列名冲突）

**原因**：SQL 中 `SELECT 股票代码` 未指定表别名，SQLite 无法判断来自哪张表。

**解决**：重试机制自动将错误信息反馈给 LLM，LLM 在下一次生成时加上表别名（如 `a."股票代码"`）。

---

### 问题4：列名含括号导致 SQL 错误

**现象**：`no such column: 收盘价`

**原因**：数据库实际列名为 `收盘价(元)`，含括号需要用双引号包裹；LLM 生成时漏掉了括号部分。

**解决**：在 NL2SQL 提示词中明确列出所有含括号的列名（规则9、11），并给出完整示例：`"收盘价(元)"、"昨收盘(元)"`。

---

### 问题5：基金可转债持仓明细列名错误

**现象**：SQL 使用 `股票代码`、`股票名称`，报 `no such column`，触发重试，SQL 步骤耗时 6s+。

**原因**：该表没有这两个列，正确列名为 `对应股票代码`（对应 A 股代码）和 `债券名称`（可转债名称），与其他持仓表不同。LLM 凭经验猜测了错误列名。

**解决**：在提示词中加入规则 11b，明确说明该表无 `股票代码` 列，正确列名为 `对应股票代码` 和 `债券名称`。重试频率从每5题1次降至几乎为零。

---

### 问题6：基金代码硬编码导致答案错误

**现象**：查询某基金历史数据时，LLM 直接猜测了一个 6 位基金代码（如 `000298`），与实际代码（`007604`）不符，查不到数据。

**原因**：LLM 凭训练数据"记忆"了基金代码，但数据库中实际存储的代码可能不同。

**解决**：提示词规则13明确要求：**禁止猜测或硬编码基金代码**，必须通过基金名称 LIKE 匹配 `基金基本信息` 表来获取基金代码。

---

### 问题7：行业查询使用 LIKE 导致全表扫描

**现象**：SQL 执行从 0.3s 变为 6s。

**原因**：提示词将行业划分标准过滤从精确匹配改为 `LIKE '%中信%'`，前置 `%` 通配符使索引失效，触发全表扫描。

**解决**：改回精确匹配 `= '中信行业分类'`，执行时间恢复到 0.3s。同时在提示词中明确说明不能使用前置通配符。

---

### 问题8：Gradio 页面 NL2SQL 调用两次

**现象**：总耗时约 17-23s，远超预期。

**原因**：`app.py` 在展示 SQL 时先调用一次 `generate_sql()`，随后 `agent.query()` 内部又调用一次，NL2SQL 共执行两次（每次约 5-8s）。

**解决**：重构 `app.py`，不再调用 `agent.query()`，改为直接按步骤调用：`generate_sql()` → `run_sql_with_retry()` → `generate_answer()`，NL2SQL 只执行一次。总耗时降低约 5-8s。

---

### 问题9：7B 小模型幻觉输出错误答案

**现象1**：单行2列结果（股票代码+涨跌幅），7B 模型将 `300178` 输出为 `3031778`（乱改数字），涨跌幅从 4.62% 改为 4.60%。

**现象2**：多行单列结果（3条债券名称），7B 模型忽略数据，输出"未查询到相关数据"。

**原因**：7B 模型参数量少，对精确数字和代码的复现能力差，易产生幻觉。

**解决**：扩展 `_try_direct_format()`，覆盖更多直接格式化场景（单行多列、多行单列、多行两列），这类结果完全跳过 LLM，由代码直接拼接输出，准确率 100%。

---

### 问题10：预分类器未能拦截部分招股书问题

**现象**：`id=1`（上海华铭智能终端设备·首发战略配售）未被预分类器拦截，进入了 NL2SQL 流程。

**原因**：预分类器关键词列表中没有"首发"、"战略配售"等 IPO 相关词汇。

**解决**：在 `_PROSPECTUS_KEYWORDS` 中添加：`"首发"、"首次公开"、"战略配售"、"网上发行"、"网下发行"、"超额配售"`。修复后该类问题 0 API 成本直接返回提示。

---

### 问题11：批量处理限流间隔逻辑 Bug

**现象**：`REQUEST_INTERVAL` 设置了 5 秒间隔，但批量处理时每题实际无间隔。

**原因**：`batch_process.py` 中判断条件为 `if i < total - 1 and not skipped`，而 `skipped` 是已跳过数量（int 类型），非零时 `not skipped` 为 False，导致间隔永远不触发。

**解决**：将判断条件改为 `if i < total - 1 and current_id not in existing_ids`，改用布尔值判断当前题是否跳过。

---

### 问题12：模型不可用（403 Model disabled）

**现象**：切换到 `Qwen3-30B-A3B`、`Qwen2.5-Coder-32B-Instruct` 后报 `Error code: 403 - Model disabled`。

**原因**：部分模型在硅基流动平台当前账号套餐下不可调用。

**解决**：通过硅基流动模型广场确认可用模型列表，最终改用 `deepseek-ai/DeepSeek-V3`（MoE 架构，SQL 能力强，账号可用）。

---

### 问题13：Gradio 6.0 参数变更警告

**现象**：启动时警告 `theme parameter has been moved from Blocks constructor to launch()`。

**原因**：Gradio 6.0 将 `theme` 参数从 `gr.Blocks()` 移至 `demo.launch()` 方法。

**解决**：将 `theme=gr.themes.Soft()` 从 `gr.Blocks()` 移到 `demo.launch()` 中。

---

### 问题14：端口占用无法启动

**现象**：`OSError: Cannot find empty port in range: 7860-7860`

**原因**：上次启动的 `app.py` 进程未关闭，或其他 Gradio 应用占用了 7860 端口。

**解决**：将 `server_port` 改为 `7861`，或先 `Ctrl+C` 关闭旧进程。
