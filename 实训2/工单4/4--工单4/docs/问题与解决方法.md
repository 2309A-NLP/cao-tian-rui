# 工单4：基金数据问答智能体 · 问题与解决方法

## 问题1：只读数据库报写入错误

**阶段**：实现

**现象**：
```
sqlite3.OperationalError: attempt to write a readonly database
```

**原因**：`db_utils.py` 打开 SQLite 后执行了 `PRAGMA journal_mode=WAL`，该语句要求数据库具有写权限，但连接以只读模式（`mode=ro`）打开。

**解决**：删除 `PRAGMA journal_mode=WAL` 语句。只读模式下无需设置日志模式，SQLite 默认 DELETE 模式读取时不需要写入。

## 问题2：数据库文件路径找不到

**阶段**：部署

**现象**：
```
FileNotFoundError: data\博金杯比赛数据.db
```

**原因**：`config.py` 使用相对路径读取数据库，相对路径以**当前工作目录**为基准。从项目子目录（如 `src/`）运行脚本时，相对路径解析出错。

**解决**：`config.py` 中引入 `_BASE_DIR`，统一以**项目根目录**为基准：

```python
_BASE_DIR = Path(__file__).resolve().parent.parent

def _resolve_path(env_key, default):
    raw = os.getenv(env_key)
    p = Path(raw)
    return p if p.is_absolute() else (_BASE_DIR / p).resolve()
```

## 问题3：SQL 列名歧义导致执行失败

**阶段**：测试

**现象**：
```
OperationalError: ambiguous column name: 股票代码
```

**原因**：多表 JOIN 时，`SELECT 股票代码` 未指定表别名，SQLite 无法判断字段归属哪张表。

**解决**：SQL 重试机制自动将错误信息反馈给 LLM，LLM 在修正版本中加入表别名（如 `a."股票代码"`）。无需手动干预。

## 问题4：列名含括号导致 SQL 语法错误

**阶段**：测试

**现象**：
```
OperationalError: no such column: 收盘价
```

**原因**：数据库实际列名为 `收盘价(元)`，含括号，LLM 生成 SQL 时漏掉了括号，或未加双引号导致 SQLite 无法识别。

**解决**：在 NL2SQL 提示词规则9、11中明确示例所有含括号列名：

```
A股票日行情表列名：
"股票代码","交易日","昨收盘(元)","今开盘(元)","最高价(元)",
"最低价(元)","收盘价(元)","成交量(股)","成交金额(元)"
```

并强调所有列名**必须用双引号包裹**。

## 问题5：基金可转债持仓明细列名错误导致频繁重试

**阶段**：测试 / 优化

**现象**：SQL 执行步骤耗时 6s+（正常应 <0.5s），日志显示：
```
WARNING SQL 执行失败（第1次）: no such column: t1.股票代码
WARNING SQL 执行失败（第2次）: no such column: t1.股票名称
INFO    SQL 第 2 次重试成功
```

**原因**：`基金可转债持仓明细` 表无 `股票代码` 和 `股票名称` 列，正确列名为 `对应股票代码`（A股代码）和 `债券名称`（可转债名称）。LLM 按照其他持仓表的列名猜测，导致首次 SQL 必然失败，触发两次 LLM 重试（每次 ~3s）。

**解决**：在提示词中加入规则 11b，明确指出该表的正确列名：

```
【重要】基金可转债持仓明细没有"股票代码"和"股票名称"列！
正确列名为：
- "对应股票代码"（对应 A 股代码）
- "债券名称"（可转债名称）
```

修复后，该类 SQL 首次即可成功执行，重试频率从每5题1次降至接近零。

## 问题6：基金代码硬编码导致答案错误

**阶段**：测试

**现象**：查询某基金历史数据时，LLM 生成的 SQL 直接写入了一个猜测的基金代码（如 `WHERE 基金代码 = '000298'`），与数据库中实际代码（`007604`）不符，查不到任何数据。

**原因**：LLM 可能从训练数据中"记住"了某些基金代码，但这些代码在本数据库中未必正确或对应的是不同份额（A/C份）。

**解决**：提示词规则13明确要求：

```
【重要】查询基金相关数据时，禁止猜测或硬编码基金代码！
必须通过基金名称 JOIN 基金基本信息表来获取基金代码：
    WHERE i."基金简称" LIKE '%基金名%'
```

## 问题7：涨跌幅计算用自连接导致结果不稳定

**阶段**：测试 / 优化

**现象**：同一道涨跌幅问题，多次查询给出不同的股票代码或涨跌幅数值。

**原因**：
1. `A股票日行情表` 本身有 `昨收盘(元)` 列，无需自连接查前一日数据
2. LLM 有时未识别到 `昨收盘(元)` 列，试图用 `LAG()` 函数或自连接计算，生成方式不同导致结果不稳定
3. 问题描述中公式括号有歧义（`（收盘价 - 前一日收盘价 / 前一日收盘价）`），LLM 有时按字面理解

**解决**：提示词规则5固定公式写法，禁止自连接：

```
【重要】A股涨跌幅计算公式（固定写法，不允许偏差）：
("收盘价(元)" - "昨收盘(元)") / "昨收盘(元)" * 100
"昨收盘(元)"列就是前一日收盘价，禁止再做自连接查前一日数据。
若题目公式括号有歧义，一律以本规则为准。
```

## 问题8：行业查询使用 LIKE 导致全表扫描

**阶段**：优化（引入新问题后修复）

**现象**：SQL 执行时间从 0.3s 劣化到 6s。

**原因**：将提示词中行业划分标准过滤从精确匹配改为 `LIKE '%中信%'`，前置通配符 `%` 使 `行业划分标准` 字段上的索引完全失效，SQLite 被迫全表扫描数百万行。

**解决**：恢复精确匹配，并在提示词规则16中明确说明原因：

```
行业划分标准精确匹配：中信行业用 "行业划分标准" = '中信行业分类'
（不要用 LIKE，前置通配符会导致全表扫描，查询变慢10倍以上）
```

## 问题9：app.py 双重 NL2SQL 调用

**阶段**：优化

**现象**：总耗时 17-23s，远超预期的 8-10s。添加逐步计时日志后发现：`NL2SQL 13s  SQL 6s  回答 0s  共 19s`，NL2SQL 时间异常偏高。

**原因**：`app.py` 中逻辑错误：

```python
# 第1次调用：用于在页面展示 SQL
sql = generate_sql(question, schema=schema)   # ~5s

# 第2次调用：agent.query() 内部再次调用 generate_sql
answer = agent.query(question)                # 内含第2次 NL2SQL ~5s
```

NL2SQL 实际执行了两次，但显示的耗时计时器只从 `agent.query()` 开始，掩盖了第一次调用的时间。

**解决**：重构 `app.py`，不调 `agent.query()`，直接按步骤串联：

```python
t0 = time.time()
sql = generate_sql(question, schema=schema)        # 只调1次
t1 = time.time()
rows, final_sql = run_sql_with_retry(question, sql)
t2 = time.time()
answer = generate_answer(question, rows, sql=final_sql)
t3 = time.time()
# 显示每步耗时：NL2SQL Xs  SQL Xs  回答 Xs  共 Xs
```

**效果**：节省约 5-8s，总耗时从 19s 降至 6-12s。

## 问题10：7B 模型回答存在幻觉

**阶段**：优化

**现象1**：股票代码 `300178` 被输出为 `3031778`（多出一位数字），涨跌幅 `4.62%` 被改为 `4.60%`。

**现象2**：查询到3条债券名称后，模型仍返回"未查询到相关数据"（完全忽略数据）。

**原因**：7B 参数量的模型对精确数字的复现能力弱，在"转述"数据时容易产生幻觉，改变数值或丢失信息。

**解决**：扩展 `_try_direct_format()` 的覆盖范围，对单行、多行单列、多行两列结果全部由代码直接格式化，完全跳过 LLM：

```python
# 单行：字段1：值1，字段2：值2
# 多行单列：字段名：值1、值2、值3
# 多行两列：值A：值B（每行）
```

**效果**：绝大多数查询结果（单行+列表）不再经过任何模型，输出 100% 准确。

## 问题11：预分类器未拦截部分招股书问题

**阶段**：测试

**现象**：`id=1`（华铭智能首发战略配售）被分类为"数据库类"而非"招股书类"，走了 NL2SQL 流程（约 1.7s），问题类型显示错误。

**原因**：`_PROSPECTUS_KEYWORDS` 关键词列表缺少 IPO 相关词汇，如"首发"、"战略配售"等。

**解决**：在关键词列表中补充：

```python
"首发", "首次公开", "战略配售", "网上发行", "网下发行", "超额配售",
```

**效果**：此类 IPO 问题在预分类阶段拦截，响应时间从 1.7s 降至 <0.1s，零 API 成本。

## 问题12：批量处理限流间隔逻辑 Bug

**阶段**：实现

**现象**：设置了 `REQUEST_INTERVAL=5`，但批量处理时题目之间实际没有间隔，导致频繁触发 429 限流。

**原因**：`batch_process.py` 中判断逻辑错误：

```python
# 原代码：skipped 是 int 类型，非零时 not skipped 为 False
if i < total - 1 and not skipped:
    time.sleep(REQUEST_INTERVAL)
# 效果：只要跳过过任何题，之后的间隔全部失效
```

**解决**：改为判断当前题是否被跳过：

```python
if i < total - 1 and current_id not in existing_ids:
    time.sleep(REQUEST_INTERVAL)
```

## 问题13：模型不可用（403 Model disabled）

**阶段**：优化

**现象**：切换模型后报：
```
Error code: 403 - {'code': 30003, 'message': 'Model disabled.', 'data': None}
```

**原因**：硅基流动平台部分模型对当前账号套餐不开放。尝试不可用的模型：
- `Qwen/Qwen3-30B-A3B`（403）
- `Qwen/Qwen2.5-Coder-32B-Instruct`（403）

**解决**：到硅基流动模型广场（cloud.siliconflow.cn/open/models）确认账号可用模型，选择 `deepseek-ai/DeepSeek-V3`（账号可用且 SQL 能力强）。

**预防**：更换模型前先在控制台确认可用性，避免修改代码后才发现不可用。

## 问题14：Gradio 6.0 兼容性问题

**阶段**：部署

**现象**：
```
UserWarning: The parameters have been moved from the Blocks constructor
to the launch() method in Gradio 6.0: theme.
```

**原因**：Gradio 6.0 将 `theme` 参数从 `gr.Blocks(theme=...)` 移至 `demo.launch(theme=...)`。

**解决**：
```python
# 修改前
with gr.Blocks(title="...", theme=gr.themes.Soft()) as demo:
    ...
demo.launch(...)

# 修改后
with gr.Blocks(title="...") as demo:
    ...
demo.launch(theme=gr.themes.Soft(), ...)
```

**阶段**：部署

**现象**：
```
OSError: Cannot find empty port in range: 7860-7860.
```

**原因**：上次启动的 `app.py` 进程仍在后台运行，或其他 Gradio 应用占用了 7860 端口。
