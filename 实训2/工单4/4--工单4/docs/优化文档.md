# 工单4：基金数据问答智能体 · 优化文档

| 优化方向 | 优化前 | 优化后 | 提升 |

| 单次查询总耗时 | 17-23s | 6-12s | 降低 40-60% |

## 2. 性能优化

### 2.1 数据库索引优化

**问题**：JOIN 查询在千万行数据上需要全表扫描，耗时 3-10s。

**措施**：为全部 10 张表的高频查询字段建立 28 个索引（`create_indexes.py`）。

**关键索引效果**：

| 索引 | 查询场景 | 优化效果 |
|---|---|---|
| A股票日行情表（股票代码, 交易日） | 按股票+日期过滤 | 全表扫描→索引点查 |
| A股公司行业划分表（一级行业名称） | 按行业过滤 | 行业查询快 10x |
| A股公司行业划分表（行业划分标准） | 按分类标准过滤 | 需用精确匹配才生效 |
| 基金基本信息（基金简称） | 通过名称查代码 | JOIN 速度提升 |

**注意**：`行业划分标准` 索引只在 `=` 精确匹配时生效，使用 `LIKE '%中信%'`（前置通配符）会导致索引失效，全表扫描，SQL 执行时间从 0.3s 劣化到 6s。

---

### 2.2 消除重复 NL2SQL 调用

**问题**：Gradio `app.py` 的 `answer_question()` 函数中，先调用一次 `generate_sql()` 用于在页面展示 SQL，随后 `agent.query()` 内部又调用一次，NL2SQL 共执行两次，多消耗 5-8s。

```python
# 优化前（错误逻辑）
sql = generate_sql(question, schema=schema)   # 第1次
answer = agent.query(question)                # 内部第2次（浪费）
```

**措施**：重构 `app.py`，不调用 `agent.query()`，直接串联各子模块：

```python
# 优化后
sql = generate_sql(question, schema=schema)       # 只调1次
rows, final_sql = run_sql_with_retry(question, sql)
answer = generate_answer(question, rows, sql=final_sql)
```

**效果**：节省一次完整的 NL2SQL API 调用（5-8s）。

---

### 2.3 Schema 预加载缓存

**问题**：每次查询时动态加载数据库 Schema（需扫描10张表+抽样数据），首次耗时约 2s。

**措施1**：`get_full_schema()` 加 `@lru_cache`，进程生命周期内只加载一次。

**措施2**：`app.py` 启动时立即调用 `get_full_schema()` 预热缓存，用户第一次提问不会有额外延迟。

### 2.4 NL2SQL 模型选型优化

**演进过程**：

| 阶段 | 模型 | NL2SQL 耗时 | 问题 |
|---|---|---|---|
| 初始 | Qwen2.5-72B-Instruct | 8-13s | 慢，Dense 模型 |
| 尝试1 | Qwen3-30B-A3B | — | 账号不可用（403） |
| 尝试2 | Qwen2.5-Coder-32B | — | 账号不可用（403） |
| 最终 | DeepSeek-V3 | 6-9s | MoE架构，SQL能力强 |

**DeepSeek-V3 优势**：
- MoE 稀疏激活架构，每次推理激活约 37B 参数
- 对代码/SQL 生成能力强，列名错误率更低
- 减少 SQL 重试次数，从每5题1次重试降至几乎为零

### 2.5 回答生成策略优化

**问题**：所有结果都调用 LLM 生成自然语言回答，产生两个问题：
1. 耗时：额外 2-5s（7B模型）或 3-8s（72B模型）
2. 幻觉：小模型会改数字（如把 300178 改成 3031778）或忽略数据（返回"未查询到相关数据"）

**措施**：实现 `_try_direct_format()` 直接格式化策略，对确定性结果完全跳过 LLM：

```
单行结果（≤6列）  →  直接拼接：字段1：值1，字段2：值2
多行单列          →  直接列表：字段名：值1、值2、值3
多行两列（≤10行）→  编号列表：值A：值B（每行）
COUNT/聚合       →  固定格式：共 N 条
以上均不满足      →  调用 7B 模型
```

**效果**：
- 单行结果（最常见）：回答耗时 0s，无幻觉风险
- 多行列表（债券名称等）：回答耗时 0s，准确输出所有值
- 复杂摘要：仍调 7B，但占比降低

## 2.6 结果缓存（进程内 LRU）

**问题**：工单9 数字人要求响应时间 ≤3s，但 NL2SQL API 本身耗时 6-9s，无法绕过。Session 内重复提问（相同问题）是常见场景。

**措施**：在 `fund_agent.py` 模块级维护 `_answer_cache: dict[str, str]`，最多500条 FIFO 淘汰：
- `query()` 开头先查缓存，命中直接返回
- 成功答案（含 `__PROSPECTUS__` 标记）写入缓存
- 错误回答不缓存（不污染缓存）

**效果**：
- 缓存命中：<0.1s，零 API 调用
- 未命中：流程不变，6-12s

**适用场景**：工单9 数字人 session 内同一用户重复提问，展示环节多次演示同一题。

## 2.7 流式输出（Gradio 生成器）

**问题**：Gradio UI 提问后界面空白等待 6-12s，用户不知道进度，体验差。

**措施**：`FundAgent.query_stream()` 生成器逐步产出事件：
```
yield "status", "正在生成 SQL…"    → 状态栏立即更新
yield "sql",    <sql>              → SQL 框即时填入（此时 NL2SQL 已完成）
yield "status", "正在执行查询…"   → 告知用户已进入 SQL 执行阶段
yield "answer", <answer>          → 最终答案
```

`app.py` 的 `answer_question()` 改为 Gradio 生成器函数，每个 `yield` 触发一次界面刷新，需 `demo.queue()` 开启队列。

**效果**：NL2SQL 完成时（≈6-9s）界面已显示 SQL，用户知道系统在工作；总耗时不变，感知等待时间大幅降低。

---

## 2.8 异步接口

**问题**：工单6 调用工单4/5 是串行的，未来若需并发调用两个工具（如同时检索 DB 和招股书）无法实现。

**措施**：新增 `FundAgent.query_async()` 和模块级 `query_async()`，使用 `asyncio.run_in_executor` 在线程池中运行同步代码，对调用方呈现 `async def` 接口。

**工单6** `tools/fund.py` 新增 `call_async()`，用法：
```python
result = await fund.call_async(query)
```

**当前工单6 agent.py 仍是同步**——异步接口为后续并发调用预留，无需立即重构 agent.py。

## 3. 成本优化

### 3.1 预分类器（最大收益优化）

**措施**：在 NL2SQL 之前用关键词规则分类，招股书类问题直接返回标记，不调任何 API。

**效果**：1000题中有 63题为招股书类，节省了 63次 NL2SQL + 63次 answer_gen 调用。每题约节省 2次 API 调用，共节省约 126次 API 调用。

### 3.2 批量处理限流控制

**措施**：题目间设置 `REQUEST_INTERVAL` 间隔（默认5秒），429 限流时等待 60s 后重试，最多3次。

**Bug修复**：原代码中 `not skipped` 条件判断有误（`skipped` 是 int 类型，非零时始终为 False），导致间隔从未生效。修复后批量处理触发 429 的频率显著降低。

### 3.3 熔断器（成本保护）

**措施**：连续 10 次 API 错误（包括 403 余额不足）自动停止处理，避免在 API 不可用时持续空跑。

## 4. 可靠性优化

### 4.1 断点续跑

每道题答案立即写入磁盘（`flush=True`），重启后读取已有答案 ID，自动跳过已处理题目。即使程序异常退出，也不丢失已完成的工作。

### 4.2 SQL 查询超时

为 SQLite 连接设置 30 秒查询超时（`set_progress_handler`），防止复杂 JOIN 查询永久卡死进程。超时后抛出异常，触发 SQL 重试或返回查无数据。

### 4.3 SQL 错误自动修复

SQL 执行失败时，将错误信息（如 `no such column: 股票代码`）反馈给 LLM，LLM 据此生成修正后的 SQL 再次执行。此机制处理了大量因列名猜测错误导致的首次失败，最终成功率接近 100%。

## 5. 各阶段耗时对比

### 优化前（初始版本）

```
生成SQL（第1次）：~5s  ← 不计入耗时显示
agent.query()   ：~17s（含第2次NL2SQL+SQL+回答）
总显示耗时      ：17s
实际总耗时      ：~22s
```

### 优化后（当前版本）

```
问题类型       NL2SQL   SQL执行   回答生成    总计      感知延迟
─────────────────────────────────────────────────────────────
招股书类         0s       0s        0s        <0.1s    即时
DB类·缓存命中    0s       0s        0s        <0.1s    即时
DB类·单行      6-9s    0.1-0.3s   0s        6-10s    NL2SQL后即时显示SQL
DB类·多行      6-9s    0.1-0.3s   ~2s       8-12s    分步显示进度
```

> NL2SQL 的 6-9s 是硅基流动 API 网络延迟，属于外部因素，本地部署可降至 1-2s。
