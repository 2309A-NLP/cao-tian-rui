## 二、逐项技术栈决策

### 2.1 MCP 协议实现

**选择**：官方 Python SDK `mcp[cli]==1.28.1`

**理由**：

- 工单原文要求"MCP Server + MCP Client"，官方 SDK 是行业标准
- 兼容 Claude Desktop / Cursor / Cline / n8n 等主流 MCP 客户端，方便工单验收时演示
- 手写 JSON-RPC 通信可行但重造轮子，SDK 自带工具注册、类型校验、错误处理
- 与 Anthropic 官方标准一致，长期可维护

**备选**：

- ❌ 自造 JSON-RPC 协议 —— 兼容性差，无生态
- ❌ LangChain Tools —— 不是 MCP 标准，无法被外部客户端使用

### 2.2 MCP 传输方式（Transport）

| Server | 传输方式 | 理由 |
|---|---|---|
| registration_mcp / knowledge_mcp / imaging_mcp / voice_mcp | **stdio** | 本地子进程，Windows 无端口冲突，MCP 官方推荐本地默认方案 |
| amap_mcp | **SSE** | 高德官方只提供 SSE，无选择 |

**为什么不用 HTTP transport？** MCP 也支持 streamable-http，但那需要每个 Server 占一个端口，配置成本高；stdio 由 Client 自动拉起子进程，最省心。

### 2.3 上游工单代理方式

**选择**：**HTTP 代理**（MCP Server 用 httpx 调上游 FastAPI）

**理由**：

- **解耦**：上游工单改包结构、改依赖，MCP Server 不受影响。旧项目采用"进程内 import"导致每次上游改动都要同步改 MCP，运维成本高
- **独立 venv**：01/02 各有自己的 `.venv` 和 `requirements.txt`（依赖冲突严重时无法合并），HTTP 代理让每个工单独立运行
- **可观测**：HTTP 层可以打日志、加超时、限流，比函数调用更可控
- **未来容器化友好**：每个工单一个容器，MCP Server 只是编排层

**代价**：

- 多一层 HTTP 开销（本机通信 ~1-3ms，可忽略）
- 上游必须先启动 MCP 才能真正工作 —— 通过启动脚本编排解决

**备选**：

- ❌ 进程内 import（旧项目做法）—— 强耦合
- ❌ gRPC —— 需要 protobuf，且上游工单已经用 FastAPI，切换成本大

### 2.4 后端 Web 框架

**选择**：FastAPI + uvicorn

**理由**：

- 与所有上游工单（01/02）保持一致，团队熟悉
- 异步支持（httpx 调上游、并发调多个 MCP Server 时优势明显）
- 自动生成 OpenAPI 文档，前端联调方便
- Pydantic 类型校验，减少参数错误

**备选**：

- ❌ Flask —— 同步，异步支持弱
- ❌ Django —— 太重，本项目不需要 ORM/admin

### 2.5 路由 Agent 的 LLM

**选择**：硅基流动 `Qwen/Qwen2.5-72B-Instruct`

**理由**：

- 与 01/02 保持一致，避免多套密钥
- 硅基流动定价低（Qwen72B ¥4.13/M tokens），路由分类每次 tokens 不多（~500）
- Qwen 中文能力强，工单场景全中文
- API 兼容 OpenAI 格式，代码可迁移

**备选**：

- ❌ DeepSeek —— 便宜但意图分类偶尔漂移
- ❌ 本地 Ollama —— 需 GPU 常驻，成本高
- ❌ 直接用 embedding 分类 —— 无法处理多意图组合（比如"医院附近有酒店吗顺便帮我挂号"）

### 2.6 前端方案

**选择**：**Alpine.js CDN（3KB）** + 高德 JS API + 原生 HTML/CSS

**理由**：

- 新原型 `prototype.html` 有双面板、4 类周边 tab、搜索、路线切换 —— 用纯 vanilla JS 手写 `document.querySelector` 会很啰嗦
- Alpine.js 提供 `x-data / x-show / x-on / x-for` 声明式绑定，学习 5 分钟即可
- CDN 引入，**无构建工具、无 npm、无 node_modules**，符合"简单优先"原则
- 高德 JS API 直接嵌入，无需封装

**备选评估**：

- Vanilla JS（旧项目）：状态管理弱，事件绑定多
- Vue3 CDN（无构建）：40KB，功能过剩
- Vue3 + Vite：需装 Node、构建产物，部署复杂，不符合本项目"边做边讲"节奏
- React CDN：JSX 需要 Babel 转换，或改用 hyperscript，反而更复杂

### 2.7 认证

**选择**：可选的 API Key（`X-API-Key` header）

**理由**：

- 与 01/02 的 `auth.py` 保持一致，方便未来门户统一鉴权
- 开发模式（`.env` 里 API_KEY 留空）不校验，减少调试摩擦
- 生产模式启用，防止 MCP 网关被外部滥用

### 2.8 端口规划

| 服务 | 端口 | 说明 |
|---|---|---|
| 00 门户 | 8000 | 统一入口 |
| 01 挂号 | 8011 | 已确定 |
| 02 健康咨询 | 8012 | 已确定 |
| 03 影像 | 8013 | 预留 |
| **04 MCP 网关** | **8014** | 本工单 |
| 05 语音 | 8015 | 预留 |

**规则**：工单编号 + 8000。既保持规律又与旧项目历史一致（旧项目 wt14 也用 8014）。

### 2.9 测试

**选择**：`tests/eval_routing.py`（20 用例路由精度评测）+ pytest（可选）

**理由**：

- 工单验收明确要求"检索精度 ≥ 80%"，20 用例覆盖 5 类意图（挂号/咨询/位置/影像/语音）
- 评测脚本比 pytest 更直观，可直接输出精度报告
- 已开工的 01/02 有自己的 pytest，本工单不重复

## 五、什么时候容器化

**当前阶段：不容器化**。理由：
- 各工单还在推进中，反复修改代码 → 反复重建镜像浪费时间
- 本地跑通、测试通过、需求稳定后，再统一为所有工单打包
- Docker 是"部署产物"，不是"开发工具"

**统一打包时机**：11/12/13/14/15 全部通过本地测试后，一次性建 docker-compose。
