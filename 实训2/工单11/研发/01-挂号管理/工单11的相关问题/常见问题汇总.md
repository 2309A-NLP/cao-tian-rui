# **一**

问题：有个问题，工具里面的sql语句是预先写好的，如果直接用大模型生成sql会不会更快更准？只讨论问题，不做实际代码改动？给我原因



有个问题，工具里面的sql语句是预先写好的，如果直接用大模型生成sql会不会更快更准？只讨论问题，不做实际代码改动？给我原因

好问题，直接说结论：**不会更快更准，预写SQL在这个场景下是正确选择。** 原因如下。

------

## 为什么"LLM生成SQL"看起来吸引人

理论上LLM理解用户意图后直接生成SQL，省掉工具层，一步到位。工单4（基金问答Agent）用的正是这个方案（NL2SQL）。

------

## 但在挂号这个场景，预写SQL更好

### 原因1：查询模式是有限且固定的

挂号系统的数据操作就这几种：

- 查号源（按科室/日期/医生筛选）
- 查历史记录
- 写挂号（INSERT + UPDATE号源数量）
- 取消挂号（UPDATE两张表）

这些模式完全可以穷举，没有开放性。LLM生成SQL的优势在于**查询模式无法预知**的场景（比如用户随意问财务报表），用在这里是大炮打蚊子。

------

### 原因2：LLM生成SQL引入不确定性，挂号是写操作

查询错了顶多数据不准，但挂号涉及写库：



```sql
-- LLM可能生成这种危险SQL
UPDATE schedule SET sch_available = sch_available - 1
-- 忘了加 WHERE sch_id = ?，导致所有号源全部-1
```

预写SQL + 参数化查询（`%s`占位符）是完全可控的，LLM生成的SQL需要额外的审查层才能用于写操作，复杂度反而更高。

------

### 原因3：速度反而更慢

当前架构：`LLM选工具+填参数` → `预写SQL直接执行`

NL2SQL架构：`LLM生成完整SQL` → `（需要审查）` → `执行`

LLM生成SQL和LLM选工具填参数消耗的token量差不多，但NL2SQL还需要把表结构全部塞进prompt（表名、字段名、关系），token更多，延迟反而更高。

------

### 原因4：SQL注入风险上升

预写SQL用参数化查询，用户输入永远是参数，不可能改变SQL结构：



```python
cur.execute("SELECT ... WHERE dep_Name = %s", (dept,))
```

LLM生成SQL如果直接把用户输入拼进去，就有注入风险。加防护层又增加复杂度。

------

## 什么时候NL2SQL才合适

| 场景                                 | 适合方案                   |
| ------------------------------------ | -------------------------- |
| 查询模式固定（挂号/取消/查询）       | 预写SQL + Function Calling |
| 查询模式开放（任意分析报表、BI查询） | NL2SQL                     |
| 有写操作                             | 预写SQL（安全可控）        |
| 纯只读查询                           | NL2SQL可以考虑             |

工单4的基金问答是只读+查询模式开放（用户可以问任意维度的基金数据），所以NL2SQL合适。挂号是写操作+模式固定，所以预写SQL是正确选择。

------

**一句话**：这个项目用Function Calling把LLM的职责限定在"理解意图、选工具、填参数"，SQL执行交给预写的安全代码——职责边界清晰，LLM做它擅长的，数据库操作做可控的。







# 二

问题：""" 工单11 医疗挂号Agent - 数据库连接管理 (MySQL 版) 连接池：DBUtils.PooledDB  - maxconnections=20  应对 50+ 并发请求时的连接复用  - DictCursor          保证 row["字段名"] 用法与 SQLite 版一致，tools.py 无需改访问方式 事务：db_transaction() 上下文管理器，自动 commit/rollback """为什么能应对并发请求？是真的并发还是其它的？

## 先说结论

**是伪并发，不是真并发。** Python 有 GIL（全局解释器锁），任意时刻只有一个线程在执行 Python 字节码。

------

## 但它确实能应对高并发，原因是这个

这个项目的请求几乎全是 **I/O 等待**，不是 CPU 计算：



```
一次挂号请求的时间分布（约5-8秒）：
  等LLM返回         ≈ 3-6秒   ← 等网络
  等MySQL查询        ≈ 几毫秒  ← 等网络
  Python自身计算     ≈ 极少    ← 真正占CPU
```

**GIL 在 I/O 等待期间会主动释放**，让其他线程趁机运行。所以：



```
线程1：发LLM请求 → [等待3秒，GIL释放] → 收到结果继续
线程2：              [趁GIL释放，执行] → 发DB查询 → [等待，GIL释放]
线程3：                                              [趁GIL释放，执行] ...
```

多个线程"轮流"在 I/O 间隙执行，看起来像并发，本质是交替执行。

------

## 连接池解决的是另一个问题

没有连接池时，每个请求都要：



```
1. TCP三次握手连MySQL       ← 10-50ms
2. MySQL认证                ← 几ms
3. 执行SQL
4. 断开连接
```

**每次建连接本身就很慢**。连接池的作用是：



```
启动时预建2个连接（mincached=2）
请求来了 → 直接借一个连接用 → 用完归还（.close()不是真关闭）
                                          ↓
                              下次请求直接拿现成的连接，跳过建连耗时
```

`maxconnections=20` 的意思是：**最多同时有20个请求在持有数据库连接**，超过的请求因为 `blocking=True` 会排队等，而不是报错崩溃。

------

## "应对50+并发"的真实含义



```
50个请求同时进来：
  → FastAPI用线程池分配线程处理
  → 每个线程大部分时间在等LLM（几秒）
  → 等待期间不占DB连接（连接已归还）
  → 实际同时持有DB连接的请求远少于50
  → 所以20个连接够用
```

打个比方：50个人去银行，但每人只在柜台前站10秒，大部分时间在填表（等LLM），20个柜台完全够用。

## 当前时间从哪里来？

**完全来自服务器本地系统时钟**，没有任何网络请求。

代码里用的全是 Python 标准库：



```python
# utils.py:101
now = datetime.now()    # 本地系统时间（精确到秒）
today = now.date()      # 本地系统日期

# agent_prompts.py:30
today = date.today()    # 本地系统日期

# agent.py:257
today = date.today()    # 同上
```

没有调 NTP、没有请求任何 API，就是操作系统的系统时钟。所以如果服务器时间错了，挂号日期判断就全错了。





# 四utils.py的作用是什么？

看代码已经读过了，直接回答。

[utils.py](F:\kimi  project\医疗agent1\01-挂号管理\backend\src\utils.py) 是**纯工具函数库**，专门存放"无副作用的纯计算函数"——不连数据库、不调LLM、不写文件，只做输入→输出的计算。

具体包含四类函数：

------

**1. 时间解析 `parse_time()`** 把用户说的自然语言时间转成具体日期。 `"明天下午2点"` → `(date(2026-07-08), "14:00")`

分三步降级：快速正则（今天/明天/后天）→ dateparser库（更复杂的表达）→ 失败返回None。

------

**2. 日期范围校验 `validate_date_range()`** 判断目标日期是否在 `[今天, 今天+14天]` 之间。 过去的日期或超出14天 → 返回错误字符串，`_pre_validate()` 直接拿来告诉用户。

------

**3. 科室/号源模糊匹配 `fuzzy_match_dept()` / `fuzzy_match_title()`** 从用户原文里提取科室名和号源类型。 `"帮我挂内科专家号"` → dept=`"内科"`, title=`"专家"`

用于 `_pre_validate()` 的科室白名单校验，以及LLM完全失败时的规则兜底。

------

**4. 日期范围构建 `build_date_range()`** 给定起始日期和跨度，返回 `(start_iso, end_iso)` 字符串对，供 `query_schedule` 的参数使用。

------

**为什么单独一个文件？**

这些函数被 `agent.py`、`llm_client.py`、`_pre_validate()` 多处复用。放在独立文件里，改时间解析逻辑只动这一个文件，不影响其他模块。
