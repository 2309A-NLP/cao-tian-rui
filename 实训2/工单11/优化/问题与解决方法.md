## P1 — MySQL date 对象无法 JSON 序列化（根因：所有 LLM 调用退回简易模式） ⚠️

**现象**  
所有经过 Agent 的对话均返回 `[简易模式]` 前缀的降级回复，LLM 完全不工作。

**根因分析**  
```
工具函数返回 → agent.py:330 json.dumps(result) →
TypeError: Object of type date is not JSON serializable →
_dispatch_tool 抛异常 → LLM 轮次中断 → 简易模式兜底
```
MySQL DictCursor 返回的 `schedule.sch_date` 是 Python `datetime.date` 对象，不是字符串，而标准 `json.dumps` 不支持序列化 `date`/`datetime`。

**解决方法**  
在 `agent.py` 的 `_dispatch_tool` 函数中，为 `json.dumps` 添加自定义编码器：

```python
# 修复前（agent.py:330）
content = json.dumps(result, ensure_ascii=False)

# 修复后
content = json.dumps(result, ensure_ascii=False, cls=logger._DateEncoder)
```

`_DateEncoder` 定义（logger.py）：
```python
class _DateEncoder(json.JSONEncoder):
    def default(self, obj):
        from datetime import date, datetime
        if isinstance(obj, (date, datetime)):
            return obj.isoformat()
        return super().default(obj)
```

**验证**  
修复后用户输入"取消我的挂号记录，挂号编号是 3"，返回正常 LLM 回复，无 `[简易模式]`。

## P2 — DBUtils PooledDB 不支持 `conn.execute()` ⚠️

**现象**  
```
AttributeError: 'SteadyDBConnection' object has no attribute 'execute'
```
出现在 `agent.py` 的 `_pre_validate` 函数。

**根因分析**  
原代码从 SQLite 迁移时遗留 `conn.execute(sql, ?)` 写法，SQLite 的连接对象直接支持 `.execute()`，但 DBUtils.PooledDB 返回的是 `SteadyDBConnection`，必须先 `conn.cursor()` 再调用游标的 `.execute()`。

**解决方法**  
```python
# 修复前（agent.py:343）
row = conn.execute("SELECT ua_id FROM user_account WHERE ua_id = ?", (user_id,)).fetchone()

# 修复后
cur = conn.cursor()
cur.execute("SELECT ua_id FROM user_account WHERE ua_id = %s", (user_id,))
row = cur.fetchone()
```
同时将占位符从 `?` 改为 `%s`（pymysql 规范）。

## P3 — 前端 onclick 中 JSON 双重序列化导致参数损坏

**现象**  
点击"预约"按钮时，`openBookDialog` 接收到的参数是一个 JSON 字符串的字符串（双层引号），导致解析失败。

**根因分析**  
```javascript
// 问题代码
onclick="openBookDialog(${JSON.stringify(JSON.stringify(s))})"
// 生成 HTML: onclick="openBookDialog("{\"sch_id\":1,...}")"
// 字符串内的双引号直接破坏了 HTML 属性引号
```

**解决方法**  
引入 `_slotRegistry` 全局注册表，onclick 只传 ID，函数内从注册表读完整对象：

```javascript
// 渲染时
_slotRegistry[s.sch_id] = s;
// ...
onclick="openBookDialog(${s.sch_id})"

// 函数内
function openBookDialog(schId) {
  const s = _slotRegistry[schId];  // 直接读对象，无序列化问题
  // ...
}
```

## P4 — 端口 8011 被占用（旧 Docker 容器或进程残留）

**现象**  
启动 uvicorn 时报：
```
ERROR: [Errno 10048] error while attempting to bind on address ('127.0.0.1', 8011)
```

**解决方法**  
```powershell
# 查找占用进程
netstat -ano | findstr ":8011"

# 找到 PID 后杀掉（替换 <PID>）
Stop-Process -Id <PID> -Force

# 再次启动后端
cd "F:\kimi  project\医疗agent1\01-挂号管理\backend"; .\venv\Scripts\python.exe -m uvicorn src.app:app --host 127.0.0.1 --port 8011 --reload
```

## P8 — 挂号/取消后前端号源数量不更新

**现象**  
通过 AI 对话完成挂号或取消后，号源表格中的剩余数量没有刷新，需手动点击刷新才能看到变化。

**根因分析**  
`sendRegChat` 函数在收到 LLM 回复后，只刷新了统计卡片和预约列表，没有刷新号源表格和排班表。

**解决方法**  
在 `sendRegChat` 的回复处理中增加对号源和排班的刷新调用：

```javascript
// 修复前
loadRegStats();
loadMyAppointments();

// 修复后
loadRegStats();
loadMyAppointments();
loadSlots();                          // 刷新号源表
if (doctorInput.value.trim()) {        // 如果医生输入框有内容
    loadDoctorSchedule();             // 同步刷新排班
}
```

## P9 — Qwen3 系列默认开启 CoT 导致响应变慢 ⚠️

**现象**  
从硅基流动 Qwen2.5-32B 切换到百炼 qwen3.7-plus 后，Agent 每次回复耗时从约 2s 增加到 5~8s。

**根因分析**  
Qwen3 系列（包括 qwen3.7-plus、qwen3-235b-a22b 等）默认开启 CoT（Chain-of-Thought）思考模式，模型在输出最终回复前会先进行大量内部推理（thinking tokens），这些 thinking token 不计入计费但增加了时间延迟。

**解决方法**  
在 `_call_llm` 中检测到 Qwen3 系列模型时，通过 `extra_body` 传入 `enable_thinking=False` 关闭 CoT：

```python
# llm_client.py — _call_llm 内
if "qwen3" in model.lower():
    kwargs["extra_body"] = {"enable_thinking": False}
```

**验证**  
关闭后 qwen3.7-plus 响应时间恢复至约 2~3s，与硅基流动 Qwen2.5-32B 相当。

## P10 — 测试后 reg_status=0，取消流程无法测试

**现象**  
运行取消案例时，Agent 报告：消化内科记录 reg_status=0（已取消），无法再次取消。

**根因分析**  
种子数据脚本使用 `INSERT IGNORE` 写入演示挂号记录，如果之前的测试已将该记录状态改为 0，重新运行 `init_db.py` 不会覆盖（`IGNORE` 的作用是冲突时跳过），导致旧的已取消状态残留。

**解决方法**  
`init_db.py` 新增 `--reset` 参数，按外键依赖顺序清空业务表后重建：

```powershell
cd "F:\kimi  project\医疗agent1\01-挂号管理\backend"
.\venv\Scripts\python.exe scripts\init_db.py --reset
```

> `--reset` 清空顺序：register → schedule → doctor → department → family_relation → patient → user_account（反外键依赖），再重新 INSERT 全套种子数据。

## P11 — Agent 最终回复暴露内部推理过程

**现象**  
Agent 在最终回复中包含如"让我确认一下取消的条件…"、"我需要先查一下您的历史记录…"等推理性文字，交互感差。

**根因分析**  
LLM 将 Function Calling 轮次间的中间思考直接输出为用户可见文本，未被 System Prompt 明确禁止。

**解决方法**  
在 `agent_prompts.py` 的 System Prompt 输出格式规则末尾追加：

```python
"- 【禁止】在最终回复中暴露内部推理过程（如\"让我确认一下…\"\"我需要判断…\"等），直接给结论"
```

**验证**  
修复后 Agent 取消流程直接输出"已为您取消挂号编号 X 的消化内科普通号"，无推理过程暴露。
