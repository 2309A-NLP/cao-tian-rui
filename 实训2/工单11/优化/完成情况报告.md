## 一、技术栈选型

| 层级 | 技术 | 选型原因 |
|---|---|---|
| LLM | 百炼 qwen3.7-plus（主）+ 硅基流动 Qwen2.5-32B/14B（兜底） | qwen3.7-plus MoE架构速度快，Function Calling强；三级fallback保障可用性 |
| 后端框架 | FastAPI + uvicorn | 异步高性能，自带 OpenAPI 文档，Pydantic 数据验证 |
| 数据库 | MySQL 8.0（本地） | 模拟真实生产技术栈；InnoDB 行锁保障并发挂号安全 |
| DB 驱动 | pymysql + DBUtils.PooledDB | pymysql 与原 SQLite 代码差异最小（仅 `?`→`%s`）；连接池 maxconnections=20 |
| Agent 模式 | Function Calling（Tool Use） | LLM 只决策调用哪个函数，SQL 执行结果反馈给 LLM 再生成回复，杜绝幻觉 |
| 并发安全 | `SELECT ... FOR UPDATE`（InnoDB） | 最后一个号源并发抢占时，行锁保证只有一人成功 |
| 前端 | 纯 HTML + Vanilla JS | 无构建工具，file:// 和 http:// 均可打开；零依赖 |
| 服务通信 | REST（GET /slots, /appointments, /schedule）+ POST /chat | 纯查询走 REST 直查 DB（<500ms）；挂号/取消走 Agent（含 LLM） |

## 六、代码质量评审（Codex 中等力度）

本次代码通过 8 角度并行评审（正确性×4 + 安全×1 + 清理×1 + 错误路径×1 + 设计×1），共发现并修复 **6 条 CONFIRMED 问题**：

| # | 文件 | 问题描述 | 修复方式 |
|---|---|---|---|
| 1 | agent.py:330 | `json.dumps` 无法序列化 MySQL `date` 对象，导致 LLM 全部失败退回简易模式 | 添加 `cls=logger._DateEncoder` |
| 2 | agent.py:343 | `_pre_validate` 使用 SQLite 风格 `conn.execute()` + `?` 占位符，DBUtils 不支持 | 改为 `cur = conn.cursor(); cur.execute(..., %s)` |
| 3 | agent.py:488 | book-guard 盲选 `schedules[0]`，忽视用户实际时间偏好 | 仅当结果恰好1条时自动选；多条时放弃guard让LLM重试 |
| 4 | agent.py:489 | `except Exception: pass` 静默吞掉所有解析错误，不写日志 | 改为 `log_warning` 记录异常 |
| 5 | tools.py:119 / app.py:102 | `query_schedule` 无日期上界，`GET /slots` 日期参数无格式验证 | 强制 `date_end ≤ today+MAX_FUTURE_DAYS`；加 `date.fromisoformat()` 验证，非法返回 422 |
| 6 | app.py:32 | CORS `allow_origins` 含 `"null"`，允许任意本地 HTML 文件跨域调用所有接口 | 移除 `"null"`，仅保留明确的 localhost 开发源 |
