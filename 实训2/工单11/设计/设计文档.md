# 工单11 挂号管理 - 设计文档

> 版本: v1.0 | 日期: 2026-07-05

---

## 一、系统概述

挂号管理模块是医疗智能体系统的第一个工单，负责通过自然语言对话完成号源查询、挂号预约、取消预约等操作。系统采用 **Function Calling（工具调用）** 模式，LLM 作为意图解析层，SQL 层负责数据操作，保证数据准确性。

---

## 二、整体架构

```
用户（浏览器）
    │  HTTP REST / POST /chat
    ▼
FastAPI 应用层 (app.py, 端口 8011)
    │  依赖注入：API Key 鉴权、CORS
    ├── GET /slots          → 直查 DB（不过 LLM，<500ms）
    ├── GET /appointments   → 直查 DB
    ├── GET /schedule       → 直查 DB
    └── POST /chat          → Agent 层
             │
             ▼
        Agent (agent.py)
             │  Function Calling 循环（最多 8 轮）
             ├── 调用 LLM (llm_client.py)
             │      主模型(1): 百炼 qwen3.7-plus
             │      兜底(2):   硅基流动 Qwen2.5-32B-Instruct
             │      兜底(3):   硅基流动 Qwen2.5-14B-Instruct
             │      降级:      规则正则（简易模式）
             └── 调用 Tools (tools.py)
                      │  pymysql + DBUtils.PooledDB
                      ▼
                MySQL 8.0 (medical_agent)
```

## 三、数据库设计

### 核心表

| 表名 | 说明 | 关键字段 |
|---|---|---|
| `user_account` | 登录用户 | `ua_id`, `ua_name` |
| `patient` | 患者（可为家属） | `p_ID`, `p_Name` |
| `family_relation` | 用户-患者绑定 | `user_id`, `patient_id`, `alias` |
| `department` | 科室 | `dep_ID`, `dep_Name` |
| `doctor` | 医生 | `d_ID`, `d_Name`, `d_Profession`, `dep_ID` |
| `schedule` | 排班号源 | `sch_id`, `d_id`, `sch_date`, `sch_time_slot`, `sch_type`, `sch_available`, `sch_total` |
| `register` | 挂号记录 | `reg_ID`, `p_ID`, `sch_id`, `reg_Status`, `reg_Fee`, `reg_Time`（申请时间） |

### 关键约束

- `schedule.sch_available`：InnoDB 行锁保护，并发挂号时 `SELECT ... FOR UPDATE`
- `register.reg_Status`：1=正常，0=已取消
- `family_relation.alias`：`我`固定指向用户本人的 patient 记录

## 四、Agent 设计

### 4.1 工具清单

| 工具函数 | 用途 | 核心 SQL 操作 |
|---|---|---|
| `get_family_member` | 按昵称查患者 ID | SELECT family_relation + patient |
| `query_schedule` | 查可用号源 | SELECT schedule WHERE available>0 |
| `book_appointment` | 挂号 | SELECT FOR UPDATE + UPDATE available-1 + INSERT register |
| `cancel_appointment` | 取消挂号 | UPDATE reg_Status=0 + UPDATE available+1 |
| `get_user_history` | 查历史记录 | SELECT register JOIN schedule |
| `get_doctor_schedule` | 查医生排班 | SELECT schedule（含已满） |

### 4.2 Function Calling 循环

```
用户输入
  → 构建 system prompt（含工具描述 + 业务规则）
  → LLM 返回 tool_calls / content
  → 若 tool_calls：执行工具 → 追加 tool result → 继续循环
  → 若 content：最终回复用户
  → 循环上限 8 轮，超出则返回超时提示
```

### 4.3 降级策略（四级）

| 级别 | 触发条件 | 处理 |
|---|---|---|
| 主模型(1) | 正常 | 百炼 qwen3.7-plus（MoE，激活170B，速度快） |
| 兜底(2) | 主模型HTTP错误/超时 | 硅基流动 Qwen2.5-32B-Instruct |
| 兜底(3) | 32B也失败 | 硅基流动 Qwen2.5-14B-Instruct |
| 简易模式 | 三级模型均失败 | 规则正则匹配意图，返回预设模板回复 |

**注意**：Qwen3系列默认开启CoT思考模式，已在调用时传入 `enable_thinking=False` 关闭，避免无效推理延迟。

## 五、API 接口设计

### 5.1 POST /chat

```json
// 请求
{"user_id": 1, "query": "帮我挂一个明天上午儿科的号"}

// 响应
{"reply": "已为您预约...", "trace_id": "abc-123", "trace": [...]}
```

`trace` 字段：每个工具调用步骤的列表，前端用于渲染"🔍 查看执行过程"折叠面板。每步含 `step/tool/label/input/output/ok`。

### 5.2 GET /slots

```
GET /slots?dept=儿科&date_start=2026-07-06&date_end=2026-07-08&slot_type=专家

// 响应
{
  "ok": true,
  "slots": [{"sch_id":1, "doctor_name":"张医生", "date":"2026-07-06", ...}],
  "total": 5
}
```

### 5.3 GET /appointments/{user_id}

```
GET /appointments/1?bucket=upcoming

// 响应
{
  "ok": true,
  "appointments": [{..., "bucket": "upcoming", "reg_time": "2026-07-01 08:45:00"}, ...],
  "stats": {"pending": 2, "total": 3, "canceled": 1}
}
```

`bucket` 查询参数：`upcoming`=待就诊（就诊日未到），`history`=历史（已过期或已取消）。  
每条记录附带 `bucket` 字段和 `reg_time`（申请时间），前端据此分 Tab 展示并控制"取消"按钮显示。

### 5.4 GET /schedule

```
GET /schedule?doctor=李华&date_start=2026-07-06

// 响应
{"ok": true, "doctor": "李华", "schedules": [...]}
```

## 六、前端设计

### 6.1 挂号管理模块结构（在 index.html 中）

```
挂号管理 (mod=reg)
├── 挂号规则横幅（首屏展示最早/最晚可挂日期、费用规则）
├── 统计卡片行：待就诊 / 总预约 / 今日号源
├── 号源筛选表格（GET /slots）
│   └── 操作列：预约按钮 → openBookDialog(sch_id)
├── 我的预约
│   ├── 子Tab：待就诊（GET /appointments/1?bucket=upcoming）
│   └── 子Tab：历史预约（GET /appointments/1?bucket=history）
│       └── 取消按钮仅在 bucket=upcoming && reg_status=1 时显示
├── 医生排班查询（GET /schedule）
└── AI 对话框（POST /chat）
    ├── 对话返回后自动刷新：统计卡片 + 预约列表 + 号源表 + 排班表
    └── 每条AI回复上方有"🔍 查看执行过程（N步）"折叠面板（trace）
```

### 6.2 状态管理

- `_slotRegistry`：全局 dict，`sch_id → slot 对象`，避免 onclick 中 JSON 双重序列化
- `currentModule`：当前激活模块，默认 `'reg'`
- `CONFIG.USER_ID`：当前登录用户 ID，硬编码为 1（演示环境）

### 6.3 关键设计决策

- 纯查询（看号源/排班/历史）走 REST 直查 DB，不过 LLM，保证响应 <500ms
- 挂号/取消走 POST /chat，由 LLM 解析意图后调工具执行
- 对话后强制刷新所有相关视图，保证号源数量实时更新

## 七、安全设计

| 项目 | 方案 |
|---|---|
| API 鉴权 | X-API-Key 请求头，`verify_api_key` 依赖注入所有接口 |
| CORS | 白名单仅限 localhost 开发源，不含 `"null"` |
| 输入验证 | 日期格式 `date.fromisoformat()` 校验；科室/号源类型白名单 |
| 日期上界 | `date_end` 强制 ≤ today + MAX_FUTURE_DAYS（14天） |
| 并发安全 | `SELECT ... FOR UPDATE` + `rowcount==0` 双重兜底 |
| SQL 注入 | 全部使用参数化查询（`%s` 占位符），无字符串拼接 |
