# 工单11 - 挂号管理 需求分析报告

> **工单编号**: 人工智能 NLP-Agent 数字人项目-医疗智能体-挂号管理任务

## 一、需求概述

### 1.1 业务背景
患者在就医过程中，挂号是首要环节。传统的挂号方式（窗口排队、电话预约）效率低下，用户体验差。本模块旨在通过 **AI Agent + 医院门诊管理 DB** 的方式，让用户通过自然语言对话完成挂号全流程，包括号源查询、预约挂号、取消预约、医生排班查询等。

### 1.2 目标用户
- **主要用户**: 患者及家属（尤其是需要为家人挂号的情况，如'帮我大宝挂...'）
- **用户特征**: 对医院科室、医生信息有一定了解，但可能不熟悉线上操作流程
- **使用场景**: 移动端为主，随时随地查询和预约

## 二、功能需求

### 2.1 核心功能矩阵

| 功能模块 | 功能点 | 优先级 | 说明 |
|----------|--------|--------|------|
| 号源查询 | 按科室查询 | P0 | '牙科最近的号哪天的?' |
| 号源查询 | 按医生查询 | P0 | '帮我查下张建国医生下周的坐诊时间' |
| 号源查询 | 按时间查询 | P0 | '今天下午2点的儿科专家号' |
| 预约挂号 | 为自己挂号 | P0 | 关联当前用户档案 |
| 预约挂号 | 为家人挂号 | P0 | 通过昵称/姓名识别家属（如'大宝''二宝'） |
| 预约挂号 | 专家号/普通号 | P1 | 区分号源类型 |
| 取消预约 | 按时间取消 | P0 | '取消我上周三挂的消化内科普通号' |
| 取消预约 | 智能推荐替代 | P1 | 号源不足时推荐其他时间/医生 |
| 历史记录 | 查询历史挂号 | P1 | '我之前挂过眼科的一个专家' |
| 异常处理 | 无效输入处理 | P0 | 错误时间、不存在的科室等 |

### 2.2 业务流程

#### 2.2.1 号源查询流程
```
用户输入查询意图
    |
    v
Agent 解析实体（科室/医生/时间/就诊人）
    |
    v
查询门诊管理 DB 号源表
    |
    +-- 有号源 --> 展示号源列表（时间、医生、剩余数量）
    |
    +-- 无号源 --> 推荐替代方案（其他时间/同科室其他医生/普通号）
```

#### 2.2.2 预约挂号流程
```
用户输入挂号意图
    |
    v
Agent 解析实体（就诊人、科室、医生偏好、时间偏好）
    |
    v
查询就诊人信息（通过 userid 关联家属档案）
    |
    v
查询目标号源
    |
    +-- 有号源 --> 确认预约信息 --> 生成挂号记录 --> 号源-1 --> 返回成功
    |
    +-- 无号源 --> 推荐替代 --> 询问用户是否接受
```

#### 2.2.3 取消预约流程
```
用户输入取消意图
    |
    v
Agent 解析（时间范围、科室、医生）
    |
    v
查询历史挂号记录
    |
    +-- 找到匹配记录 --> 确认取消 --> 删除/标记取消 --> 号源+1 --> 返回成功
    |
    +-- 未找到记录 --> 提示用户确认信息
```

## 三、数据模型设计

### 3.1 核心实体

```
患者用户 (User)
├── user_id (PK)
├── name
├── phone
├── id_card
└── 家属列表 (FamilyMember[])

家属 (FamilyMember)
├── member_id (PK)
├── user_id (FK)
├── name (如'大宝'、'二宝')
├── relation (关系: 子女/配偶/父母)
├── birth_date
└── gender

科室 (Department)
├── dept_id (PK)
├── name (如'儿科'、'眼科'、'牙科')
├── category (专家/普通/特需)
└── location

医生 (Doctor)
├── doctor_id (PK)
├── name (如'张建国')
├── dept_id (FK)
├── title (职称: 主任医师/副主任医师)
└── specialty

号源 (AppointmentSlot)
├── slot_id (PK)
├── doctor_id (FK)
├── dept_id (FK)
├── date
├── time_start
├── time_end
├── total_quota
├── remaining_quota
├── type (专家号/普通号)
└── status (可约/已满/停诊)

挂号记录 (Appointment)
├── appointment_id (PK)
├── user_id / member_id (就诊人)
├── slot_id (FK)
├── status (已预约/已完成/已取消)
├── create_time
└── cancel_time
```

### 3.2 ER 关系图

```
User ||--o{ FamilyMember : 拥有
User ||--o{ Appointment : 预约
FamilyMember ||--o{ Appointment : 被预约
Doctor }o--|| Department : 所属
Doctor ||--o{ AppointmentSlot : 出诊
AppointmentSlot ||--o{ Appointment : 被预约
```

## 四、Agent 交互设计

### 4.1 对话示例 - 为家人挂号
```
用户: 帮我大宝挂一个今天下午2点儿科专家的号

Agent 思考过程:
1. 意图识别: 预约挂号
2. 实体提取:
   - 就诊人: 大宝 --> 查询 user_id=xxx 的家属列表 --> member_id=101（大宝）
   - 科室: 儿科
   - 时间: 今天下午2点 --> 2026-07-05 14:00
   - 类型: 专家号
3. 查询号源: SELECT * FROM AppointmentSlot
   WHERE dept_id='儿科' AND date='2026-07-05' AND time_start='14:00'
   AND type='专家号' AND remaining_quota > 0
4. 结果: 有号源（李医生，剩余3个）
5. 执行: INSERT INTO Appointment ...; UPDATE AppointmentSlot SET remaining_quota = remaining_quota - 1
6. 回复: 已为您的大宝（张小明）成功预约今日下午2:00 儿科专家号 - 李华主任医师，请提前15分钟到院取号。
```

### 4.2 号源不足示例
```
用户: 帮我大宝挂一个今天下午2点儿科专家的号

Agent: 今日下午2:00 儿科专家号已约满。为您推荐:
1. 今日下午2:30 儿科专家号 - 王芳副主任医师（剩余2个）
2. 今日下午3:00 儿科专家号 - 李华主任医师（剩余1个）
3. 今日下午2:00 儿科普通号 - 张明医师（剩余5个）

请问您选择哪一个? 或者我可以帮您查看其他日期的号源。
```

### 4.3 异常处理策略

| 异常类型 | 处理策略 | Agent 回复示例 |
|----------|----------|----------------|
| 无效用户ID | 提示登录/注册 | '请先登录您的账号，以便我为您查询号源。' |
| 错误时间格式 | 引导确认 | '您说的是今天下午2点对吗?（2026年7月5日 14:00）' |
| 不存在的科室 | 模糊匹配+推荐 | '没有找到口科，您是指口腔科吗?' |
| 号源已满 | 推荐替代 | 见上方示例 |
| 重复预约 | 冲突检测 | '您已预约了今日下午2点的儿科号，是否需要取消后重新预约?' |
| 家属未找到 | 引导添加 | '未找到三宝的信息，是否需要添加家属档案?' |

## 五、非功能需求

### 5.1 性能要求
- 响应时间 < 500ms（Agent 意图识别）
- 挂号事务处理 < 1s（含数据库操作）
- 支持并发: 50+ 用户同时查询

### 5.2 质量要求
- 能处理 6 个测试案例及 30+ 变体场景
- 准确识别用户 query 中的时间、科室、医生、就诊人实体
- 检索/操作精度 >= 95%

### 5.3 安全要求
- 用户数据脱敏存储
- 挂号操作需二次确认
- 敏感操作（取消）记录审计日志
