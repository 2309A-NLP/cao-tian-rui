## 1. WebSocket 协议 vs HTTP 协议

### 1.1 核心差异

| 维度 | HTTP | WebSocket |
|---|---|---|
| **连接模型** | 请求-响应，短连接 | 一次握手，长连接 |
| **通信方向** | 单向（客户端发起） | 全双工（双向同时收发） |
| **握手开销** | 每次请求 TCP+TLS 握手 | 只在建立时握手一次 |
| **消息边界** | HTTP 报文分隔 | 帧（Frame）边界，text/binary 混流 |
| **服务端推送** | 需要轮询或 SSE 折中 | 服务端可主动推送 |
| **状态语义** | 无状态 | 连接维持状态（会话 ID、上下文） |
| **典型协议头** | `Content-Type/Length` | `Sec-WebSocket-Key/Accept` |
| **调试友好度** | 高（curl 即可） | 低（需专用工具） |

### 1.2 本工单如何选用

```
┌─────────────────────┬───────────┬─────────────────────────────────┐
│ 用途                 │ 协议      │ 原因                             │
├─────────────────────┼───────────┼─────────────────────────────────┤
│ 音频推流+实时字幕     │ WebSocket │ 全双工、低延迟、帧级增量下推      │
│ 会话创建/停止        │ HTTP      │ 一次性动作，无需长连接           │
│ 轮询结果            │ HTTP      │ 客户端定时拉，短连接足够          │
│ 接收异步回调         │ HTTP      │ 服务端接受 webhook，POST 一次即可 │
│ 健康检查            │ HTTP      │ 无状态 GET                       │
│ 咨询转发（→工单12）   │ HTTP      │ 服务端间调用，标准 REST          │
└─────────────────────┴───────────┴─────────────────────────────────┘
```

**关键设计**：本工单**只在音频推流用 WebSocket**，其它一律 HTTP。理由：把长连接的复杂度（心跳、重连、有序保证）局限在最需要的地方。

### 1.3 WebSocket 消息设计

浏览器 ↔ FastAPI：混用 text/binary 帧减少序列化开销。

| 方向 | 帧类型 | 内容 | 说明 |
|---|---|---|---|
| 客户端 → 服务端 | text | `{"type":"init","lang":"zh_cn"}` | 首帧握手 |
| 客户端 → 服务端 | binary | PCM 16kHz 16bit mono | 每 40ms 一帧（1280 字节） |
| 客户端 → 服务端 | text | `{"type":"stop"}` | 结束指令 |
| 服务端 → 客户端 | text | `{"type":"transcription","text":"...","is_final":false}` | 中间识别 |
| 服务端 → 客户端 | text | `{"type":"sentence_end","text":"...","begin_ms":0}` | 句末 |
| 服务端 → 客户端 | text | `{"type":"translation","text":"...","sentence_index":n}` | 句级翻译 |
| 服务端 → 客户端 | text | `{"type":"completed"}` | 全部完成 |

## 2. 异步（asyncio）

### 2.1 为什么用协程而不是多线程

需求分析报告 §4.3 原稿列了"线程1/2/3/4"多线程模型，本工单**改用 asyncio 协程**，理由：

| 维度 | 多线程 | asyncio 协程（选用） |
|---|---|---|
| 上下文切换 | 内核级，重 | 用户态，轻 |
| 并发数 | 数十~百 | 上千~万 |
| 共享状态 | 需锁 | 单线程事件循环，无锁 |
| WebSocket 库支持 | 需第三方 | Python 原生 `websockets`/`starlette` |
| I/O 阻塞 | 阻塞整线程 | 只阻塞当前协程 |
| 调试复杂度 | 死锁/竞态难查 | 显式 `await` 边界 |

**核心结论**：本场景瓶颈是 I/O（等讯飞返回、等 LLM 返回），CPU 计算量很小，用协程是正解。

### 2.2 上下行并发（gather）

音频推流场景需要**同时**做两件事：
- 上行：把浏览器 PCM 转发到讯飞 WebSocket
- 下行：把讯飞返回的识别结果推回浏览器

用 `asyncio.gather` 让两个协程共存于同一事件循环：

```python
async def run_iat_session(browser_ws, task_id, sessions, lang):
    async with websockets.connect(url) as xf_ws:
        async def _browser_to_xf():   # 上行
            while True:
                msg = await browser_ws.receive()
                await xf_ws.send(build_payload(msg))

        async def _xf_to_browser():   # 下行
            async for raw in xf_ws:
                await browser_ws.send_json(parse(raw))

        await asyncio.gather(_browser_to_xf(), _xf_to_browser())
```

只要有一路收到 `stop` 或对端关闭，另一路的 `await` 会因 WebSocket 关闭而抛出 `ConnectionClosed`，自然收敛。

### 2.3 后台任务（create_task）

**句级翻译**不应阻塞识别流。用 `asyncio.create_task` 把翻译推到后台：

```python
if is_last_sentence:
    await browser_ws.send_json({"type": "sentence_end", ...})
    # 翻译异步跑，不阻塞下一句
    asyncio.create_task(_translate_and_push(browser_ws, text, "en", idx))
```

翻译失败静默降级（记 warn 日志，不推 error 事件），保证识别流不中断。

## 3. 回调（Callback / Webhook）

### 3.1 语义

通义听悟风格：客户端提交任务时携带 `CallbackUrl`，服务端异步处理完毕后 POST 到该 URL。

```
Client                        Tingwu                   Analysis Cluster
  ├── CreateTask(CB=url) ────►│                              │
  │◄── {TaskId} ──────────────┤                              │
  │                            ├─── dispatch ────────────────►│
  │                            │                              │
  │                            │◄── result ready ─────────────┤
  │◄── POST url {Result} ──────┤                              │
```

本工单实现：`POST /api/callback`，接受 `TaskId + TaskStatus + Result` 载荷，写入内存 session。

### 3.2 回调 vs 轮询

| 指标 | 回调（Webhook） | 轮询（Polling） |
|---|---|---|
| 实时性 | 事件驱动，秒级 | 依赖 poll interval，通常 3s+ |
| 客户端复杂度 | 需暴露公网 URL | 简单 GET |
| 网络成本 | 一次 POST | N 次 GET（大部分空转） |
| 生产适用 | 是 | 兜底 |
| 开发调试 | 需 ngrok/内网穿透 | 直接跑 |

**PDF 明确要求二者都实现**，我们两者并存：
- 回调：`POST /api/callback` — 生产/Agent 集成路径
- 轮询：`GET /api/session/{id}/poll` — 开发/前端简化路径

回调完成会**同时**触发工单12 咨询（`asyncio.create_task(_auto_consult())`），不阻塞回调 200 响应。

## 4. 多线程？何时才用

本工单**没有用多线程**。以下场景才需要：

| 场景 | 为什么用线程 |
|---|---|
| CPU 密集：音频编解码（如 Opus→PCM） | Python GIL 下需 `concurrent.futures.ThreadPoolExecutor` 才能并行 |
| 同步库桥接：调用只有同步 API 的 SDK | 用 `run_in_executor` 避免阻塞事件循环 |
| 后台 batch：不影响响应的重计算 | 独立线程 + 队列 |

本工单三方 SDK 都有 async 版本（`websockets`、`httpx`），无需多线程。

## 5. 性能与验收

| 指标 | 目标 | 现状 | 说明 |
|---|---|---|---|
| 帧级识别延迟 | <500ms | ~300ms（讯飞公开数据） | 网络 RTT 是主要变量 |
| 句末翻译延迟 | <1s | ~600ms（Qwen2.5-7B 短 prompt） | 句子越长越慢，可换更快模型 |
| 摘要生成 | <5s | ~2-3s（500 字对话） | LLM 单次调用 |
| 并发 WS 连接 | 100+ | 未压测 | asyncio 单进程理论支持 |

响应时间 <500ms 的**含义边界**：指帧级识别推送延迟，不含摘要生成（后者本身就是异步任务）。

## 6. 一句话总结

本工单用 **WebSocket 长连接** 做实时音频推流+事件下推，用 **HTTP** 做会话管理/结果获取/回调接收，用 **asyncio 协程** 替代传统多线程并发模型，靠 **create_task** 把非关键路径（翻译、摘要触发咨询）推到后台不阻塞主流程。所有对外可选路径（回调 vs 轮询、真实 ASR vs mock）都用**环境变量切换**，保证同一份代码支持生产、演示、测试三种运行模式。
