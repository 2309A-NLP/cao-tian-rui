## 优化 1：音频采集升级 ScriptProcessor → AudioWorklet

### 背景

旧项目前端使用已废弃的 `createScriptProcessor(4096)` 进行 PCM 采集。

### 问题

- Chrome 94+ 控制台报 deprecation 警告
- 在主线程运行，音频处理会阻塞 UI 交互
- 帧大小 4096 samples = 256ms，延迟偏高

### 优化方案

新增 `pcm-worklet.js`，使用 `AudioWorkletProcessor` 在独立线程处理：

```javascript
// pcm-worklet.js
class PcmFramer extends AudioWorkletProcessor {
  constructor() {
    super();
    this.frameSize = 640;  // 40ms @ 16kHz，符合讯飞IAT要求
  }
  process(inputs) {
    // 累积640个采样 → Int16 → postMessage(transferable)
  }
}
registerProcessor("pcm-framer", PcmFramer);
```

### 效果

| 指标 | 旧方案 | 新方案 |
|---|---|---|
| 线程 | 主线程（阻塞UI） | AudioWorklet 独立线程 |
| 帧大小 | 4096 samples（256ms） | 640 samples（40ms）|
| 内存拷贝 | 有 | 无（Transferable ArrayBuffer）|
| 废弃警告 | 有 | 无 |

## 优化 2：翻译任务从线程改为 asyncio.create_task

### 背景

翻译功能需要调用硅基流动 LLM（网络请求约 600ms），初始设计考虑用线程并发。

### 问题

若用线程：
- 线程切换开销
- 需要线程安全的 WebSocket 发送
- 与 asyncio 事件循环混用容易死锁

### 优化方案

改用 `asyncio.create_task()`，与识别协程共享同一事件循环：

```python
# sentence_end 后立即推送，翻译在后台异步进行，不阻塞识别流
await browser_ws.send_json({"type": "sentence_end", ...})
if TRANSLATE_ENABLED and SILICONFLOW_API_KEY:
    asyncio.create_task(_translate_and_push(browser_ws, text, target_lang, idx))
    # 不 await，识别流继续推进
```

### 效果

- 识别延迟：0 增加（翻译完全不阻塞识别）
- 翻译结果：`sentence_end` 后约 600ms 异步到达浏览器
- 代码复杂度：无需线程锁，更简洁

## 优化 3：MOCK 模式轮询兜底，避免前端死循环

### 背景

前端轮询逻辑：每 3 秒请求 `/api/session/{id}/poll`，收到 `COMPLETED` 才停止。

### 问题

测试时 task_id 有效但 session 还未设置 result，原始实现会返回 404，前端进入无限报错循环。

### 优化方案

MOCK 模式下对未知 session 返回 200 + 固定摘要：

```python
@app.get("/api/session/{task_id}/poll")
async def session_poll(task_id: str):
    session = _sessions.get(task_id)
    if not session:
        if config.ASR_ENGINE == "mock":
            return {"TaskId": task_id, "TaskStatus": "COMPLETED", "Result": _mock_result()}
        return {"TaskId": task_id, "TaskStatus": "UNKNOWN", "Result": {}}
```

### 效果

- MOCK 模式测试：轮询稳定返回 COMPLETED，前端正常停止
- 生产模式：未知 session 仍返回 UNKNOWN，不影响错误检测

## 优化 4：前端兼容大小写字段，统一渲染逻辑

### 背景

通义听悟 API 返回大写字段（`TaskStatus`/`Result`/`Chapters`/`Summarization`），内部 MOCK/讯飞路径使用小写（`status`/`result`/`chapters`）。

### 问题

若前端只处理一种大小写，切换 ASR 引擎时会出现摘要不显示的问题。

### 优化方案

`renderSummaryData()` 中同时检查两种命名：

```javascript
const result   = data.Result   || data.result   || {};
const sum      = result.Summarization || result.summarization || {};
const chapters = result.Chapters      || result.chapters      || [];
const todos    = sum.ActionItems      || sum.action_items     || [];
const kws      = sum.KeyInformation   || sum.key_information  || [];
```

### 效果

- 三种数据源（通义听悟/讯飞/MOCK）无需分支，统一渲染
- 切换 ASR 引擎无需修改前端代码

## 优化 5：LLM 返回内容多格式兼容解析

### 背景

`generate_summary()` 要求 LLM 只输出 JSON，但 Qwen2.5-7B-Instruct 有时：
- 包裹 markdown 代码块（` ```json ... ``` `）
- 使用 Python 风格单引号（`{'key': 'val'}`）
- 前后附加解释文字

### 问题

`json.loads()` 直接解析失败，返回 `{}`，前端摘要区域保持静态占位符不更新。

### 优化方案

三层解析策略：

```python
import re as _re, ast as _ast

# 第1层：去除 markdown 代码块
m = _re.search(r"```(?:json)?\s*([\s\S]*?)```", content)
if m:
    content = m.group(1).strip()

# 第2层：提取第一个 {...} 块，忽略前后多余文字
if not content.startswith("{"):
    m2 = _re.search(r"\{[\s\S]*\}", content)
    if m2:
        content = m2.group(0)

# 第3层：先 json.loads，失败则 ast.literal_eval（处理单引号）
try:
    result = json.loads(content)
except json.JSONDecodeError:
    result = _ast.literal_eval(content)
```

### 效果

- 覆盖 LLM 常见输出格式：标准JSON / markdown包裹 / 单引号 / 前后有文字
- 摘要生成成功率从约 60% 提升到接近 100%

## 优化 6：iframe 麦克风权限声明

### 背景

工单15页面通过总界面框架的 iframe 嵌入（`http://localhost:8080` → `http://localhost:8015`）。

### 问题

Chrome 默认禁止 iframe 内页面访问麦克风，`navigator.mediaDevices.getUserMedia()` 静默失败，点击麦克风按钮无任何反应。

### 优化方案

在 iframe 标签加 `allow="microphone"` 属性：

```html
<iframe id="iframe-voice"
        src=""
        data-src="http://localhost:8015/"
        allow="microphone"
        style="width:100%;height:100%;min-height:600px;border:0;"
        title="语音助手"></iframe>
```

### 效果

- 总前端嵌入后麦克风正常可用
- 首次访问时浏览器弹出麦克风权限请求（符合预期）
