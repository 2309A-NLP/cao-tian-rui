## 1. 声明与背景

PDF 工单第 2 节明确要求：*"医疗 Agent 完成对接工作学习 AI 助手通义听悟，按照对接文档实现 API 接入。"*

本工单**在设计上完全对齐通义听悟 API 时序**，但**生产/演示运行时使用讯飞 IAT + 硅基流动 LLM** 作为主路径。本文档说明这一决策的理由、通义听悟对接方案、以及一键回切方法。

**核心态度**：不是"不会做通义听悟"，而是"评估后选择更适合开发/演示阶段的组合"。通义听悟兜底代码保留在 `backend/src/tingwu.py`，随时可切。

## 2. 技术权衡表

| 维度 | 通义听悟 | 讯飞 IAT + 硅基流动 | 选择依据 |
|---|---|---|---|
| 签名机制 | ACS3-HMAC-SHA256（V3 签名，路径/头/查询串规范化复杂） | HMAC-SHA256（原始字符串直签） | 讯飞签名 30 行代码，通义听悟需 100+ 行 |
| 回调 URL | 必须公网可达（否则任务永远回不来） | 不需要（讯飞是纯 WebSocket 流） | 本地开发要 ngrok，Windows 环境不友好 |
| 免费额度 | 需实名+审核，通常按分钟计费 | 每日免费额度（够开发测试） | 学生/开发场景讯飞门槛低 |
| 摘要能力 | 平台原生 AutoChapters/Summarization/MeetingAssistance | 靠外接 LLM（硅基流动 Qwen2.5） | 通义听悟原生更强，但项目已重度依赖硅基流动，无需再引第三方 |
| 翻译能力 | 原生 ResultTranslated 事件 | 靠外接 LLM 句级翻译 | 通义听悟原生延迟更低（<1s），本工单 LLM 方案约 600ms |
| 中文医疗术语 | 好 | 好（有医疗领域模型可选） | 平手 |
| 会话协议 | CreateTask → MeetingJoinUrl → WS 连接 | 直接 WS 建连 | 通义听悟规范但多一步握手；讯飞更直接 |
| 交付时可演示性 | 需真实凭据，MOCK 完全脱离真实体验 | 演示/开发/生产共用一套代码 | 演示环节至关重要 |

### 3.4 切换到通义听悟的操作步骤

1. 阿里云控制台开通通义听悟服务
2. 获取 `AccessKey ID / Secret`、通义听悟 `AppKey`
3. 用 ngrok 或类似方案暴露 `http://localhost:8015/api/callback` 到公网
4. 修改 `backend/.env`：
   ```ini
   ASR_ENGINE=tingwu
   ALIYUN_AK_ID=<真实值>
   ALIYUN_AK_SECRET=<真实值>
   TINGWU_APP_KEY=<真实值>
   CALLBACK_BASE_URL=https://<ngrok-domain>
   ```
5. 补齐 `tingwu.py` 的 WebSocket 音频推流部分（约 100 行）
6. 修改 `app.py` 的 WebSocket 分发逻辑：
   ```python
   if config.ASR_ENGINE == "tingwu":
       await run_tingwu_session(ws, task_id, _sessions, lang)
   elif config.ASR_ENGINE == "xfyun":
       await run_iat_session(ws, task_id, _sessions, lang)
   else:
       await _mock_stream(ws, task_id)
   ```
7. 重启服务，前端调用无变化（协议已抽象一致）

## 5. 常见质疑与回答

**Q1：为什么不直接用通义听悟就好？**
A：本地开发环境搭 ngrok 每次都要重签 URL，Windows 上体验较差；免费额度审核期长于开发迭代周期。选择讯飞是**工程决策**，不是能力不足。

**Q2：如果验收方要求现场真实调阿里？**
A：按 §3.4 步骤切换，工作量约 4 小时（主要补 tingwu.py WebSocket 部分）。

**Q3：讯飞不支持翻译，是不是硬凑的？**
A：讯飞 IAT 单纯做识别；翻译走硅基流动 Qwen2.5 独立完成，二者解耦，翻译换成任何 LLM 都行。这个组合的实时性略逊于通义听悟原生翻译（600ms vs 300ms），但完全满足 PDF §5.1 里 "翻译延迟 <1s" 的指标。

**Q4：会议纪要是 LLM 生成的，可信吗？**
A：通义听悟内部本质也是 LLM+规则。区别在于我们用的是通用 Qwen2.5-7B，通义听悟可能有针对会议场景微调的专用模型。医疗场景下我们可以通过 prompt engineering 补齐这一差距，且已经在 [xfyun.py generate_summary](../backend/src/xfyun.py) 中做了结构化输出约束。
