## 一、需求映射

工单原始要求 → 系统设计取舍：

| 工单要求 | 设计对应 |
|---------|---------|
| 支持 10 个百日咳测试案例 + 30+ 变体场景 | 12 种意图路由 + 6720 疾病图谱覆盖 |
| 响应时间 <500ms | Neo4j 检索 <100ms（图谱层达标）+ 规则意图分类（跳过 LLM 调用） |
| 意图精度、query 准确处理 | LLM Function Calling 强制返回结构化 `{intent, entity}` |
| 容错（无效 ID、错误格式、不存在实体） | pydantic 输入校验 + 多层降级（图谱空 → LLM 兜底） |
| 医学知识图谱查询 | Neo4j + medical.json（6720 疾病、5936 症状、1124 药物、129,326 关系） |

## 二、技术栈选型

| 组件 | 选型 | 决策依据 |
|------|------|---------|
| 图数据库 | **Neo4j 5.14** | medical.json 天然是图结构（疾病-症状-药物-食物多对多关系），关系遍历比关系型库快 10x+；社区版够用 |
| LLM | **Qwen2.5-72B / 硅基流动** | 中文医学理解好，Function Calling 兼容 OpenAI 协议；国内 API，稳定性和成本可控 |
| Web 框架 | **FastAPI** | 与 wt11 挂号后端统一栈；异步+pydantic 校验+自动 OpenAPI 文档 |
| 前端 | **原生 HTML+JS** | 医疗工单不需要 SPA，避免构建链复杂度；与总框架（00-总界面框架）保持一致 |
| 长期记忆 | **mem0 + ChromaDB**（可选） | 患者历史召回；未安装时静默降级不影响主功能 |
| 意图识别 | **规则 + LLM 混合** | 高置信度用规则（0ms），模糊场景用 LLM（保证质量） |

## 三、架构总览

### 3.1 分层

```
┌────────────────────────────────────────────┐
│  前端（chat.html + 主框架 iframe 嵌入）    │
│  · SSE 流式渲染                            │
│  · 图谱数据面板（可展开）                  │
│  · 意图/实体/耗时标签                      │
└────────────────┬───────────────────────────┘
                 │ HTTP + SSE
┌────────────────▼───────────────────────────┐
│  FastAPI (端口 8012)                       │
│  · /chat  非流式（旧客户端兼容）           │
│  · /chat/stream  SSE 流式（默认）          │
│  · /stats 图谱统计                         │
│  · pydantic 输入校验                       │
└────────────────┬───────────────────────────┘
                 │
┌────────────────▼───────────────────────────┐
│  Agent 核心（agent.py）                    │
│  Step0: 缓存查（完全匹配）                 │
│  Step1: 意图识别（规则 → LLM 兜底）        │
│  Step2: Neo4j Cypher 模板查询              │
│  Step3: LLM 基于图谱生成答案（流式）       │
└────────┬────────────────────┬──────────────┘
         │                    │
┌────────▼──────┐   ┌─────────▼──────────┐
│  Neo4j (7687) │   │ 硅基流动 LLM API   │
│  医疗图谱     │   │ Qwen2.5-72B        │
└───────────────┘   └────────────────────┘
```

### 3.2 数据流

一个用户提问的完整生命周期：

1. **前端** → POST `/chat/stream`，SSE 建立
2. **校验层** pydantic 拦截：空 / 超长 / 纯符号 / 非法 patient_id
3. **缓存层** `patient_id::query` 完全匹配 → 命中直接吐 token
4. **意图层** 规则先跑（0ms），命中直用；不命中调 LLM Function Calling
5. **图谱层** 根据 intent 分发到 11 个 Cypher 模板之一，实体作为参数
6. **答案层** LLM 拿 `{query, intent, entity, graph_data}` 流式生成
7. **持久化** 结果写入缓存 + 患者记忆库
8. **前端** 事件流：`meta` → `token` × N → `done`

## 四、12 种意图分类设计

设计原则：**意图是查询模板的路由键**，一个意图对应一段 Cypher，语义清晰、边界不重叠。

| 意图 | 触发关键词 | Neo4j 查询对象 |
|------|-----------|--------------|
| `disease_info` | 是什么病 / 血常规 / 化验 / 诊断标准 | Disease.intro / get_prob / easy_get |
| `symptom_to_disease` | 可能是什么病 / 什么病会有 | 反向 (Disease)-[:HAS_SYMPTOM]->(Symptom) |
| `disease_to_symptom` | 有哪些症状 / 临床表现 | (Disease)-[:HAS_SYMPTOM]->(Symptom) |
| `disease_to_drug` | 用什么药 / 吃什么药 | (Disease)-[:USES_DRUG]->(Drug) |
| `disease_to_dept` | 挂什么科 / 看哪个科 | (Disease)-[:BELONGS_TO]->(Department) |
| `disease_to_complication` | 并发症 / 合并症 | (Disease)-[:CAUSES]->(Disease) |
| `disease_to_diet` | 能吃什么 / 忌口 / 饮食禁忌 | (Disease)-[:CAN_EAT / NOT_EAT]->(Food) |
| `disease_to_transmission` | 怎么传播 / 传染途径 | (Disease)-[:TRANSMITS_VIA]->(Transmission) |
| `disease_to_cause` | 病因 / 由什么引起 | Disease.cause 文本字段 |
| `disease_to_prevent` | 怎么预防 / 预防措施 | Disease.prevent 文本字段 |
| `disease_to_nursing` | 怎么护理 / 隔离期 / 多久能好 | Disease.nursing + treat_detail |
| `disease_to_treat` | 怎么治 / 中医治疗 / 主方 | Disease.treat_detail |

## 五、关键设计决策与问题

以下为设计阶段遇到的实际问题及取舍。

---

### 决策 1：为什么不让 LLM 直接写 Cypher？

**问题**：初版考虑过让 LLM 根据自然语言直接生成 Cypher，理论上更灵活。

**风险**：
- LLM 写 Cypher 错误率约 10-15%，即便是 GPT-4 级别模型
- 图谱 schema（HAS_SYMPTOM / CAUSES / TRANSMITS_VIA 等关系名）需要 LLM 记住，容易乱写
- 错误的 Cypher 可能返回空结果 → 用户以为图谱没数据

**决策**：**Python 模板化 Cypher**
- LLM 只做"意图分类 + 实体抽取"两件事（都是 enum + string，好约束）
- 12 个 Cypher 模板由开发者写死，参数化传入实体
- 优点：Cypher 100% 正确，性能可预测（<100ms）
- 代价：牺牲了少量灵活性（图谱新增关系时需改代码）

---

### 决策 2：为什么 memory_bridge 不复用工单22？

**背景**：工单22 是独立的长期记忆系统（mem0+ChromaDB+Neo4j），本项目原本计划直连它。

**问题**：
- 工单22 需要独立启动服务，wt12 强依赖 wt22 会形成部署耦合
- 医疗数据分离考虑：健康咨询的记忆应该独立于其他工单

**决策**：**wt12 自带 memory_bridge**
- 用本地 `data/chroma/` 存储，独立 Collection `wt12_memory`
- 未安装 mem0/chromadb 时静默失败，主功能不受影响
- 工单22 集成留到后期"多智能体统一记忆层"阶段

---

### 决策 3：为什么 LLM 兜底不去掉？

**背景**：规则意图分类命中率约 75%，剩下 25% 走 LLM 首字节 ~1.5s，拉高均值。

**去掉 LLM 的诱惑**：
- 若强制规则识别 + 关键词模板拼装 → 首字节可压到 <500ms
- 缺点：**答案质量严重下降**（模板拼装无法处理复杂句式和边界情况）

**决策**：**保留 LLM 兜底**
- 用户要求"答案准确率和质量排第一位，不能降低"
- 规则不确定就走 LLM，绝不勉强分类
- LLM 生成阶段（Step 3）完全不动 —— 同 model、同 prompt、同 temperature

---

### 决策 4：500ms 硬指标怎么达标？

**问题**：工单要求 <500ms，但云端 LLM 单次调用最少 800ms+。

**分析**：
- Neo4j 检索 <100ms ✅
- LLM 意图识别 1-3s ❌
- LLM 答案生成 1-3s ❌
- 完整链路 3-7s ❌

**决策**：**用"首字节延迟"作为 500ms 指标**
- 用户看到答案开始滚动 = 感知响应
- 规则命中场景：跳过 LLM 意图识别 → 首字节 <100ms
- 缓存命中场景：直接吐缓存 → 首字节 <30ms
- LLM 兜底场景：只做一次 LLM 意图识别再流式 → 首字节 ~1s（无法进一步压缩）
- 综合规则命中率 ~75% → **3/4 请求达标**

---

### 决策 5：图谱 schema 与 needs_analysis 的偏差

**问题**：初版分析报告写了 `(Disease)-[:CAUSED_BY]->(Pathogen)`，但实际 medical.json 里根本没有 Pathogen 节点，病原体信息藏在 `Disease.cause` 文本字段里。

**处理**：
- 调整 `disease_to_cause` 意图直接查 `Disease.cause` 文本
- graph.py 里加注释说明该字段是文本而非节点关系
- 不为了满足分析报告去伪造 Pathogen 节点

**教训**：**分析文档要以实际数据为准**，不要基于假想 schema 写查询。

---

### 决策 6：端口 8001 → 8012 的对齐

**背景**：老项目端口 8001，但医疗智能体体系 wt11/wt13/wt14/wt15 分别是 8011/8013/8014/8015。

**决策**：**统一端口 = 8010 + 工单号后两位**
- wt11=8011 / wt12=8012 / wt13=8013 / wt14=8014 / wt15=8015
- 一目了然，运维时凭工单号推端口
- 老项目 chat.html 硬编码 8012（已经对，但 API 服务是 8001，前后端不一致）→ 新版全对齐

## 六、非目标（Non-goals）

明确不做的东西，避免设计过度：

- ❌ **不做**多用户并发隔离 —— 单机场景，patient_id 只区分记忆
- ❌ **不做**LLM 生成 Cypher —— 见决策 1
- ❌ **不做**GraphRAG 或图嵌入检索 —— 12 意图路由足够覆盖工单场景，避免过度工程
- ❌ **不做**多轮上下文对话 —— 每次 query 独立处理（多轮由前端拼 memory 实现）
- ❌ **不做**答案审核层 —— 医学专业性由 LLM+图谱数据保证，不做规则级审核
