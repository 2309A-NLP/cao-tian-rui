## 二、核心模块实现

### 2.1 `agent.py` — 三步流水线

**整体流程**（`run_agent()` / `run_agent_stream()`）：

```
Step0: 缓存查（完全匹配 patient_id::query）
  ↓ miss
Step1: 意图识别
  ├─ 规则分类器（intent_rules.classify）0ms
  └─ 规则不命中 → LLM Function Calling（Qwen2.5-72B）
Step2: Cypher 模板查询（graph.py 分发到对应模板）
Step3: LLM 流式生成答案（基于图谱数据）
  ↓
写缓存 + 写患者记忆（memory_bridge）
```

**LRU 缓存实现**（用 `collections.OrderedDict` 手写，不依赖 functools）：

```python
_cache: OrderedDict = OrderedDict()
_CACHE_MAX = 256

def _cache_get(key):
    if key in _cache:
        _cache.move_to_end(key)   # LRU 更新
        return _cache[key]
    return None

def _cache_set(key, value):
    _cache[key] = value
    _cache.move_to_end(key)
    if len(_cache) > _CACHE_MAX:
        _cache.popitem(last=False)  # 淘汰最旧
```

缓存键 = `f"{patient_id}::{query}"` ，完全匹配（大小写/空格敏感），不做模糊归一，避免错误命中。

**SSE 流生成器**（`run_agent_stream`）：

```python
yield {"type": "meta",  "intent": intent, "entity": entity, "intent_source": src}
yield {"type": "token", "content": chunk}   # × N，每个流式 token
yield {"type": "done",  "total_ms": ..., "cache_hit": False}
# 或
yield {"type": "error", "message": "..."}
```

### 2.2 `graph.py` — Cypher 模板分发

**连接池**：启动时建立单例 `GraphDatabase.driver`，复用连接；`/health` 端点可探活。

**12 个 Cypher 模板**（全部参数化，无拼接，防注入）：

```python
INTENT_HANDLERS = {
    "disease_to_symptom": lambda entity, tx: tx.run(
        "MATCH (d:Disease {name: $n})-[:HAS_SYMPTOM]->(s:Symptom) RETURN s.name",
        n=entity
    ).values(),
    "symptom_to_disease": lambda entity, tx: tx.run(
        "MATCH (s:Symptom {name: $n})<-[:HAS_SYMPTOM]-(d:Disease) RETURN d.name LIMIT 10",
        n=entity
    ).values(),
    # ... 其余 10 个同理
    "disease_to_cause": lambda entity, tx: tx.run(
        "MATCH (d:Disease {name: $n}) RETURN d.cause",   # 文本字段，非关系节点
        n=entity
    ).single(),
}
```

**Schema 偏差问题**（见问题记录）：`disease_to_cause` 原计划查 `(Disease)-[:CAUSED_BY]->(Pathogen)` 关系，但 medical.json 无 Pathogen 节点，改为直接读 `Disease.cause` 文本字段。

### 2.3 `intent_rules.py` — 规则分类器

**关键词表**（12 组，每组 3-8 个关键词）：

```python
_INTENT_KEYWORDS = {
    "disease_to_symptom":     ["有哪些症状", "临床表现", "症状是什么"],
    "disease_to_drug":        ["用什么药", "吃什么药", "药物治疗"],
    "disease_to_prevent":     ["怎么预防", "如何预防", "预防措施"],
    # ...
}
_SYMPTOM_TO_DISEASE_KEYWORDS = ["可能是什么病", "什么病会有", "引起", "导致什么病"]
```

**保守策略**：
1. 触发词命中两个不同意图 → 返回 `None`（降级 LLM）
2. 匹配到意图但提取不到实体 → 返回 `None`
3. 只有一个意图命中且有实体 → 返回 `(intent, entity)`

**实体抽取**：`re.search(r'[一-龥a-zA-Z0-9]{2,8}')`，提取最后一个中文词组作为疾病/症状名，后缀过滤去掉功能词（"什么"/"哪些"/"怎么"）。

### 2.4 `app.py` — 输入校验

**pydantic 模型**：

```python
class ChatRequest(BaseModel):
    query: str
    patient_id: str = "anonymous"

    @field_validator("query")
    def validate_query(cls, v):
        v = v.strip()
        if not v:
            raise ValueError("问题不能为空")
        if len(v) > 500:
            raise ValueError("问题过长，请精简后提问")
        if not re.search(r'[一-龥a-zA-Z]', v):
            raise ValueError("请输入有效的医学问题")
        return v

    @field_validator("patient_id")
    def validate_patient_id(cls, v):
        if not re.match(r'^[A-Za-z0-9_\-]+$', v):
            raise ValueError("patient_id 只允许字母数字下划线中划线")
        return v
```

校验失败 → FastAPI 自动返回 HTTP 422，前端统一展示错误消息。

## 三、实现过程中遇到的问题与解决

### 问题1：端口不一致导致前后端断开

**现象**：`chat.html` 硬编码 `localhost:8001`，但服务实际跑在 8012。首次测试时所有请求 404。

**原因**：历史遗留端口 8001，医疗工单体系统一命名规则 `8010 + 工单号后两位`（wt12 → 8012）未同步到前端文件。

**解法**：全局搜索 `8001` 替换为 `8012`，同时对齐 `.env` 的 `PORT=8012`。事后规范：端口只在 `.env` 里定义，前端读 `window.location.origin` 而不硬编码 IP:PORT。

---

### 问题2：`Disease.cause` 是文本字段而非关系节点

**现象**：`graph.py` 写 `MATCH (d:Disease)-[:CAUSED_BY]->(p:Pathogen)` 查病因，执行结果永远空。

**排查**：`MATCH (n) RETURN labels(n), count(n)` 枚举图谱节点类型，发现根本没有 `Pathogen` 标签。翻 `medical.json` 确认病因信息存在 `disease.cause` 字段（字符串），不是图关系。

**解法**：改 Cypher 为 `MATCH (d:Disease {name: $n}) RETURN d.cause`，加注释说明该字段来源。教训：**以实际数据 schema 为准，不依赖分析文档假设**。

---

### 问题3：SSE 在 Windows 上被 uvicorn 默认 gzip 压缩导致首字节延迟虚高

**现象**：SSE 流式响应，客户端实测首字节 ~800ms，但服务端打印日志显示 10ms 内已吐第一个事件。

**排查**：抓包发现响应头含 `Content-Encoding: gzip`，浏览器缓冲等待凑包后才解压渲染。

**解法**：在 `StreamingResponse` 响应头强制加：
```python
headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"}
```
同时在路由前加 `GZipMiddleware` 排除 `text/event-stream`（或不安装 gzip 中间件）。修复后首字节恢复 <50ms。

---

### 问题4：规则分类器对"可能是什么病"误判为 `disease_info`

**现象**："头痛可能是什么病？" 被分类为 `disease_info`（查疾病详情），但应该是 `symptom_to_disease`（症状反查疾病）。

**原因**：`disease_info` 关键词表包含"是什么"，与"可能是什么病"的"是什么"重叠，触发歧义判断但保守策略返回 None，退化为 LLM 分类。

**解法**：将 `symptom_to_disease` 优先级提到最前面单独处理（`if any(kw in query for kw in SYMPTOM_KEYWORDS): ...`），不进入通用意图匹配流程，避免与 `disease_info` 竞争。

---

### 问题5：LRU 缓存命中但流式 `done` 事件 `cache_hit` 字段为 `False`

**现象**：第二次相同问题首字节 <30ms，但前端状态栏显示"LLM"而非"缓存命中"。

**原因**：`run_agent_stream` 缓存命中路径直接 `yield` token，但 `done` 事件的 `cache_hit` 字段忘记设置为 `True`。

**解法**：缓存命中分支的 `done` 事件：
```python
yield {"type": "done", "cache_hit": True, "total_ms": ..., "first_byte_ms": ...}
```

---

### 问题6：PowerShell 启动命令含 `→` 符号报语法错误

**现象**：用户复制文档中 `cd "path" → python ...` 到 PowerShell，报 `unexpected token '→'`。

**原因**：文档用 `→` 作为视觉分隔，不是 shell 分隔符；PowerShell 不认识该符号。

**解法**：文档中将单行命令改为分两行书写，并注明"`→` 为文档分隔符，实际执行需分两条命令"。

## 四、关键代码设计模式

### 4.1 静默降级（graceful degrade）

所有可选依赖（mem0/chromadb/Neo4j 连接）均用 `try/except` 包裹，失败时：
- 打印 warning 日志
- 返回空结果 / 静默跳过
- **不抛异常打断主流程**

```python
def _save_memory(patient_id, query, answer):
    try:
        memory_bridge.add(patient_id, query, answer)
    except Exception as e:
        logger.warning(f"memory save failed (non-fatal): {e}")
```

### 4.2 类型强制（Function Calling 约束意图输出）

LLM 意图识别通过 Function Calling 强制返回：
```json
{"intent": "disease_to_symptom", "entity": "百日咳"}
```
`intent` 字段为枚举（12 个合法值），`entity` 为字符串。LLM 若返回非法 intent 名，统一降级到 `disease_info`。

### 4.3 参数化 Cypher（防注入）

所有 Cypher 查询使用 `$param` 占位符，**不做字符串拼接**：
```python
tx.run("MATCH (d:Disease {name: $n}) ...", n=entity_from_llm)
```
即使 entity 含特殊字符也不影响查询安全性。
