## 每个 `.py` 的定位与流程位置

| 文件               | 角色        | 流程中的位置                                          |
| ------------------ | ----------- | ----------------------------------------------------- |
| `config.py`        | 配置读取    | 最先加载，从 `.env` 拿 API Key / Neo4j 密码           |
| `auth.py`          | 门卫        | 每次 HTTP 请求进来第一关（校验 X-API-Key）            |
| `app.py`           | 入口/路由   | 接收 HTTP 请求，调用 agent，返回 JSON 或 SSE 流       |
| `intent_rules.py`  | 快速分类器  | agent 内部第一步，正则规则判断意图（0ms，命中率~55%） |
| `graph.py`         | 知识来源    | 意图确定后，查 Neo4j 图谱，返回结构化数据             |
| `memory_bridge.py` | 患者记忆    | 每次对话前召回历史，对话后异步写入，跨会话个性化      |
| `agent.py`         | 大脑/主流程 | 统筹以上所有模块，最终调 LLM 生成答案                 |

## 一次问答的完整流程

> 以用户问"**百日咳有哪些症状？**"为例



```
1. [auth.py]         验证 API Key，通过 ✓
2. [app.py]          解析 POST /chat 请求，校验 query/patient_id
3. [agent.py]        检查 LRU 缓存（首次未命中）
4. [memory_bridge]   召回该患者历史对话记忆（语义检索）
5. [intent_rules.py] 正则匹配 "有哪些症状" → 意图: disease_to_symptom，实体: 百日咳  ✓（0ms）
6. [graph.py]        用 Cypher 查 Neo4j：(百日咳)-[:HAS_SYMPTOM]->(症状节点)
7. [agent.py]        将图谱数据 + 患者记忆 注入 Prompt，调 Qwen2.5-72B 生成答案
8. [memory_bridge]   后台异步把本次对话写入 ChromaDB
9. [agent.py]        结果写入 LRU 缓存
10.[app.py]          返回 {reply, intent, entity, graph_data, elapsed_ms}
```

## PPT 讲解建议的三个重点

1. **双层意图分类**（规则 + LLM）：规则层 0ms 命中常见问题，LLM 兜底处理长尾，平衡了速度与准确率

## 问题二：真实业务逻辑是什么？

你的理解有一处关键错误需要纠正：

> "如果没有提取成功，就用自然语言转 Neo4j 查询语句"

**不对。** 系统完全没有 NL2Cypher（自然语言转查询语句）。Neo4j 查询用的是**写死的 Cypher 模板**，不是 LLM 动态生成的。

### 正确的完整流程



```
① 鉴权（auth.py）
    ↓ 验证 X-API-Key，开发模式直接跳过

② LRU 缓存查询（agent.py）
    ↓ 完全相同的 patient_id + query → 直接返回，跳过后续所有步骤

③ 记忆召回（memory_bridge.py）
    ↓ [实际上禁用，返回空列表]

④ 意图分类（两层）
    ├─ 第一层：正则规则（intent_rules.py）
    │    命中 → 直接得到 (intent, entity)，0ms
    │    例：问题含"有哪些症状" + 实体 → disease_to_symptom + "百日咳"
    │
    └─ 未命中 → 第二层：LLM Function Calling（agent.py 第208-226行）
         ↓ 调大模型，强制返回结构化 JSON：{"intent": "...", "entity": "..."}
           不是让 LLM 自由回答，是让 LLM 填一张有限选项的表单

⑤ 图谱查询（graph.py）—— 关键！
    ↓ 根据 intent 调对应的 Python 模板函数，用参数化 Cypher 查 Neo4j
      例：disease_to_symptom → q_disease_to_symptom("百日咳")
      → MATCH (d:Disease)-[:HAS_SYMPTOM]->(s:Symptom) WHERE d.name CONTAINS $name
      LLM 根本不参与这一步！全是硬编码模板。

      分支A：查到数据 → 走 ⑥A
      分支B：查不到   → 走 ⑥B

⑥A LLM 生成答案（有图谱数据）
    把图谱数据 + 原始问题塞给 LLM，让它把 JSON 数据翻译成自然语言回答
    temperature=0.3，max_tokens=512

⑥B LLM 兜底（无图谱数据）
    告诉 LLM "图谱里没有"，让它用通用医学知识回答
    temperature=0.3，max_tokens=400

⑦ 异步写入记忆（后台线程，实际禁用）

⑧ 写入 LRU 缓存，返回结果
```

### 最重要的一点（PPT 讲解时的核心亮点）

LLM 在这个系统里被调用**两次**，但作用完全不同：

| 调用时机          | 目的                 | 方式                              | 特点                              |
| ----------------- | -------------------- | --------------------------------- | --------------------------------- |
| 第④步（意图分类） | 理解用户问的是什么   | Function Calling，返回结构化 JSON | temperature=0，确定性，不自由发挥 |
| 第⑥步（答案生成） | 把图谱数据翻译成人话 | 普通对话，自然语言输出            | temperature=0.3，有一点灵活性     |

**Neo4j 的查询语句完全由 Python 代码控制**，LLM 永远不碰 Cypher，这样既防止了 SQL/Cypher 注入，也保证了图谱查询的稳定性。

## 1. 为什么设计了 mem0 却不用？

这是**典型的"设计超前于实现"**，在实训/演示项目里非常常见，有几个现实原因：

**成本问题是主因。** mem0 每次 `remember()` 都要调两次 API：一次 LLM 做摘要，一次 Embedding 模型做向量化。每轮对话多花 2 次 API 调用，硅基流动不是免费的。对演示项目来说不划算。

**依赖链很重。** 要装 `mem0ai` + `chromadb`，chromadb 在 Windows 上有时有编译问题，注释掉是最省事的选择。

**对演示影响不大。** PPT 展示时很难体现"跨会话记忆"的效果（需要同一个 patient_id 多轮对话才能看出差异），所以砍掉它对演示没损失。

**代码设计是对的：** 用 `try/except` + `if mem is None: return []` 做优雅降级，主流程完全不感知记忆是否启用。这个模式本身值得肯定。

------

## 2. 大模型在这个项目里的作用真的有限吗？

**说有限，是对的，但这是刻意设计的，不是缺陷。**

LLM 在这里做的事：

| 调用                         | 实际作用                   | 能不能替代                        |
| ---------------------------- | -------------------------- | --------------------------------- |
| 意图分类（Function Calling） | 把自然语言归类到 12 个槽位 | 规则能覆盖 55%，LLM 兜底 45%      |
| 答案生成                     | 把 JSON 图谱数据翻译成人话 | 不能，这是 LLM 真正不可替代的地方 |

LLM 的核心价值在**答案生成**这步：



```
图谱原始数据（JSON）：
{"symptoms": ["阵发性痉挛性咳嗽", "鸡鸣样回声", "呕吐"]}

↓ 经过 LLM 翻译后：

"百日咳的典型症状为阵发性痉挛性咳嗽，咳嗽末尾伴随特征性的鸡鸣样回声，
 常引发呕吐。病程一般持续 6-8 周，建议及时就医。"
```

没有 LLM 你只能把 JSON 直接扔给用户，体验很差。

但你的直觉也是对的：**这个系统本质上是"图谱检索 + LLM 润色"，LLM 不是大脑，是嘴巴。** 真正的知识来源是 Neo4j 里 33000 个节点、130000 条关系。

------

## 3. 为什么不做 NL2Cypher？

这是最有价值的讨论点。NL2Cypher 确实是更"AI"的方案，但这个项目选模板是有充分理由的：

**选模板 Cypher 的理由：**



```
NL2Cypher 的问题：
  用户问："百日咳的症状" 
  LLM 可能生成：MATCH (d:Disease {name:"百日咳"})-[:HAS_SYMPTOM]->(s) RETURN s
              或者生成错的：MATCH (d:Disease)-[:SYMPTOM]->(s)...  ← 关系名写错，查出空
              或者更糟：MATCH (n) DELETE n  ← 极端情况的风险

模板 Cypher 的优势：
  - 永远语法正确，不会查出空（模糊匹配 CONTAINS 容错）
  - 不存在注入风险（参数化查询 $name）
  - 不需要额外一次 LLM 调用（省钱、省时间）
  - 12种意图完全覆盖图谱里所有关系类型，没有遗漏
```

**但 NL2Cypher 能做什么模板做不到的：**



```
复杂查询：
  "哪些疾病既通过飞沫传播，又会引发肺炎并发症，同时属于儿科？"

模板系统：直接崩，没有这个槽位
NL2Cypher：可以生成多跳查询，真正发挥图谱的优势
```

**一句话总结这个设计取舍：**

> 当前系统把问题限定在 12 种意图内，模板完全够用，且稳定可控。NL2Cypher 值得做，但它的收益（复杂查询）在医疗问答这个场景下并不常见，而它的风险（LLM 生成错误 Cypher）却是实实在在的。这是一个合理的工程决策，不是懒。

## 整体评价（PPT 可以用的角度）

这个项目的架构核心思想是**"用规则和模板控制可控的部分，用 LLM 处理不可控的部分"**：



```
可控的（模板/规则处理）：
  ✓ 高频意图分类（正则，0ms）
  ✓ Neo4j 查询（Cypher 模板，稳定）
  ✓ 输入校验、缓存、鉴权

不可控的（LLM 处理）：
  ✓ 长尾意图理解（Function Calling）
  ✓ 自然语言答案生成
```

这是目前工业界 RAG 系统的主流设计思路，不是图省事，是务实。

## 问题一：单窗口内有多轮对话记忆吗？

**没有。这个系统每条消息都是独立请求，完全无状态。**

看 `ChatRequest`（app.py 第60-93行）：



```python
class ChatRequest(BaseModel):
    query: str       # 只有当前这一句话
    patient_id: str  # 患者ID
    # ← 没有 history，没有 messages 数组，没有上下文
```

每次点发送，前端只把**当前那一句话**发给后端，之前说了什么完全不传。

所以：

- **窗口内多轮对话**：大模型看不到上文，每条回答都是从零开始
- **跨会话记忆（mem0）**：依赖包没装，也是禁用的

**这个系统的多轮感知能力实际上是零。** 你在界面上看到的聊天气泡只是前端 JS 在本地累积显示，后端完全不知道你说过什么。

这是一个真实存在的设计缺口，跟 mem0 没关系——mem0 也只是做语义检索历史摘要，它解决不了"你刚才说的那个病"这种指代问题，因为那需要在请求里带上下文 `messages` 数组才能实现。

## 问题二：12 种意图是什么？

对照图谱里实际存在的关系类型，12 种意图完整覆盖了图谱所有边：

| 意图                      | 用户问法举例                        | 查图谱的哪条边                             |
| ------------------------- | ----------------------------------- | ------------------------------------------ |
| `disease_info`            | "百日咳是什么病？" "血常规怎么看？" | Disease节点属性（intro/cause等）           |
| `symptom_to_disease`      | "我发烧咳嗽可能是什么病？"          | (Symptom)←[:HAS_SYMPTOM]-(Disease) 反查    |
| `disease_to_symptom`      | "百日咳有哪些症状？"                | (Disease)-[:HAS_SYMPTOM]->(Symptom)        |
| `disease_to_drug`         | "百日咳吃什么药？"                  | (Disease)-[:USES_DRUG]->(Drug)             |
| `disease_to_dept`         | "百日咳挂哪个科？"                  | (Disease)-[:BELONGS_TO]->(Department)      |
| `disease_to_complication` | "百日咳会引起哪些并发症？"          | (Disease)-[:CAUSES]->(Disease)             |
| `disease_to_diet`         | "百日咳能吃什么？忌口什么？"        | (Disease)-[:CAN_EAT / :NOT_EAT]->(Food)    |
| `disease_to_transmission` | "百日咳怎么传染的？"                | (Disease)-[:TRANSMITS_VIA]->(Transmission) |
| `disease_to_cause`        | "百日咳由什么引起？"                | Disease.cause 属性                         |
| `disease_to_prevent`      | "百日咳怎么预防？"                  | Disease.prevent 属性                       |
| `disease_to_nursing`      | "百日咳怎么护理？隔离多久？"        | Disease.nursing 属性                       |
| `disease_to_treat`        | "百日咳怎么治疗？"                  | Disease.treat_detail 属性                  |

**本质就是图谱里有多少种关系/属性，就有多少种意图，一一对应，不多不少。**

## 串起来的完整认知



```
这个系统的真实状态：

优点：
  ✓ 图谱 + LLM 润色，回答有数据支撑，不瞎编
  ✓ 规则分类快，LLM 兜底准
  ✓ 容错降级设计好，挂一个模块不影响全局

实际缺口：
  ✗ 单窗口内无多轮上下文（每条消息独立）
  ✗ 跨会话记忆未启用（mem0 禁用）
  ✗ 只能回答12类问题，超出范围靠LLM通用知识兜底
  ✗ 不支持复杂组合查询（"既...又...还..."）
```

PPT 讲的时候这几个缺口可以主动说出来，反而显得你理解很深，不是只会吹项目。
