# 工单12 · 健康咨询 · 优化文档

> 定位：记录性能和质量优化的完整过程——发现问题、提出方案、实施、效果对比、结论。

---

## 一、优化背景

工单原始版本（v1）采用"每次调用 LLM 两次"模式：
- **Step1**：LLM 识别意图（~1.5s）
- **Step2**：Cypher 查询（<100ms）
- **Step3**：LLM 生成答案（~2s，非流式等全部完成才返回）

**首次响应时间**：用户点击发送后看到任何内容需等待 4-7 秒。

工单要求 `<500ms` 响应，v1 明显不达标。用户明确：**答案质量排第一，响应速度其次**。

---

## 二、优化历程（按时间顺序）

### 优化1：SSE 流式输出（最大体感改善）

**问题**：v1 用 `/chat` POST + JSON 等待完整答案，用户等 4-7s 才看到内容。

**方案**：新增 `/chat/stream` SSE 端点，Step3 LLM 答案改为流式 token 逐字输出。

**实现**：
```python
# app.py
@app.post("/chat/stream")
def chat_stream(req: ChatRequest):
    def event_gen():
        for evt in run_agent_stream(req.query, patient_id=req.patient_id):
            yield f"data: {json.dumps(evt, ensure_ascii=False)}\n\n"
    return StreamingResponse(event_gen(), media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})
```

```python
# agent.py run_agent_stream()
yield {"type": "meta", "intent": intent, ...}      # Step1/2 完成后立即发
for chunk in llm_stream_response:                   # Step3 流式 token
    yield {"type": "token", "content": chunk}
yield {"type": "done", "total_ms": ...}
```

**效果**：
- 用户感知"看到第一个字"的延迟 = **首字节延迟**（而非总耗时）
- LLM 兜底场景：总耗时不变（还是 ~6s），但用户在 1.5s 后就开始看到内容滚动
- 体感改善显著，用户报告"感觉快了很多"

---

### 优化2：规则意图分类器（最大延迟改善）

**问题**：LLM 意图识别（Step1）是最大瓶颈，每次 1-3s，且对于"百日咳有哪些症状？"这类明显问题没必要用 LLM。

**方案对比**：

| 方案 | 首字节延迟 | 质量影响 | 评价 |
|------|:--------:|:-------:|------|
| A：完全去掉 Step1，直接用 LLM 生成 Cypher | ~3s | 高错误率 | ❌ 不可行 |
| B：强制规则分类所有 query | <50ms | 25% 查询分类错/降质 | ❌ 质量不可接受 |
| C：规则先跑，不确定走 LLM（混合） | <50ms（规则命中）| 质量不变 | ✅ 采用 |

**方案 C 实现要点**：

`intent_rules.py` 保守策略：
- 只有一个意图词命中 + 能提取到实体 → 返回结果
- 多个意图词冲突（歧义）→ 返回 None（走 LLM）
- 匹配不到实体 → 返回 None（走 LLM）

`agent.py` 调用：
```python
result = intent_rules.classify(query)
if result:
    intent, entity = result
    intent_source = "rule"
else:
    intent, entity = llm_classify(query)   # Function Calling
    intent_source = "llm"
```

**效果**：
- 规则命中率：**~75%**（约 3/4 请求跳过 LLM Step1）
- 规则命中首字节：**avg 28ms**（从 ~1500ms → 28ms）
- 质量：**无损**（规则不确定一律走 LLM，不强行分类）

### 优化3：LRU 缓存（重复查询加速）

**问题**：同一患者反复问相同问题（如演示场景），每次都走完整链路。

**方案**：内存 LRU 缓存，键 = `patient_id::query`（完全匹配），容量 256 条。

**实现**（不依赖外部库）：
```python
from collections import OrderedDict

_cache: OrderedDict = OrderedDict()
_CACHE_MAX = 256

def _cache_get(key: str):
    if key in _cache:
        _cache.move_to_end(key)
        return _cache[key]
    return None

def _cache_set(key: str, value):
    _cache[key] = value
    _cache.move_to_end(key)
    if len(_cache) > _CACHE_MAX:
        _cache.popitem(last=False)
```

**设计原则**：
- **完全匹配**：大小写/空格敏感，避免错误命中不同语义的 query
- **患者隔离**：`patient_id` 作为 key 前缀，不同患者不共享缓存
- **质量零影响**：缓存命中直接返回上次 LLM 生成的完整答案，内容完全相同

**效果**：
- 缓存命中首字节：**avg 26ms**（从 ~4000ms → 26ms）
- 缓存命中总耗时：**28ms**（几乎瞬间）

### 优化4：pydantic 输入校验前置

**问题**：无效输入（空字符串、超长 query）会进入 Agent 流程，浪费 LLM 调用。

**方案**：在 `app.py` 路由层用 pydantic `@field_validator` 拦截，400/422 立即返回，不进入 Agent。

**实现**：见实现文档 2.4 节。

**效果**：
- 容错用例响应时间：**avg 12ms**（5-20ms），远优于原来走完整链路的 3-7s
- 减少了无效 LLM 调用，降低 API 成本

---

### 优化5：gzip 压缩冲突修复（首字节虚高问题）

**问题**：服务部署后实测首字节 ~800ms，但预期 <50ms（规则命中场景）。

**排查过程**：
1. 服务端打点日志显示 Step1+Step2 完成后立即 yield，耗时 ~15ms
2. 客户端收到首字节却是 800ms
3. 抓包发现响应头 `Content-Encoding: gzip`
4. 确认：gzip 中间件对 SSE 流按缓冲区攒够 4KB 才压缩输出，不是逐 token 输出

**解法**：
```python
return StreamingResponse(event_gen(), media_type="text/event-stream",
    headers={
        "Cache-Control": "no-cache",
        "X-Accel-Buffering": "no"    # 告知 Nginx/代理不缓冲
    })
```
同时确认 uvicorn 未安装 `GZipMiddleware`（默认无，除非手动 `app.add_middleware(GZipMiddleware)`）。

**效果**：首字节恢复至 <50ms。

## 四、未采纳方案及原因

### 方案A：本地小模型做意图识别

**描述**：部署 Qwen2.5-1.5B 本地模型做 Step1 意图分类，消除网络延迟。

**优点**：意图识别延迟 <100ms，所有场景均可达 <500ms 首字节。

**未采纳原因**：
- 工单环境无 GPU，CPU 推理 Qwen2.5-1.5B ~2s，比云端 API 还慢
- 部署复杂度高（模型文件 3GB+），增加部署门槛
- 规则分类器已覆盖 75% 场景，ROI 不够

---

### 方案B：Redis 分布式缓存

**描述**：用 Redis 替换内存 LRU，支持重启持久化和多进程共享。

**未采纳原因**：
- 工单为单机单进程，内存缓存完全够用
- 引入 Redis 增加部署依赖（又一个 Docker 服务）
- 医疗问答缓存价值低（用户倾向问新问题而非复查），256 条 LRU 足够覆盖演示场景

---

### 方案C：向量相似度缓存（模糊匹配）

**描述**：用嵌入向量做语义相似匹配，语义相近的问题命中同一缓存。

**未采纳原因**：
- 用户明确"质量第一"，模糊缓存有错误命中风险（如"高血压症状"和"低血压症状"向量相近）
- 实现复杂（需向量库），收益有限
- 完全匹配缓存对演示场景已够用
